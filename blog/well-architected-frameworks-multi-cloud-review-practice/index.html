One Well-Architected Review Practice Across AWS, GCP and Azure

Cesar A. Nogueira
April 22, 2025 · 9 min read

Why Three Frameworks, One Idea

AWS, Google Cloud and Microsoft Azure each publish a Well-Architected Framework, and each presents it as vendor-specific guidance. Read them side by side, though, and the convergence is striking. The AWS Well-Architected Framework describes itself as a way to "understand the pros and cons of decisions you make while building systems on AWS" — architecture as explicit trade-off, evaluated through a consistent set of foundational questions. The Azure Well-Architected Framework frames itself around quality-driven tenets, architectural decision points, and supporting review tooling. The Google Cloud Architecture Framework organises the same concerns into pillars with an operational, SRE-influenced flavour.

The pillar structures map almost one-to-one:

| Concern | AWS | Azure | Google Cloud | |---|---|---|---| | Reliability | Reliability | Reliability | Reliability | | Security | Security | Security | Security, privacy, and compliance | | Cost | Cost Optimization | Cost Optimization | Cost optimization | | Operations | Operational Excellence | Operational Excellence | Operational excellence | | Performance | Performance Efficiency | Performance Efficiency | Performance optimization | | Sustainability | Sustainability | (woven into pillars) | (woven into pillars) |

AWS has six pillars; Azure and Google Cloud each have five. The differences are taxonomic, not conceptual. Every framework asks the same fundamental questions: what happens when this fails, who can reach this data, what does this cost to run, how do you know it's healthy.

That convergence creates an obvious problem for multi-cloud platform teams. If you run three separate governance processes — an AWS review board, an Azure assessment cycle, a GCP architecture checklist — you triple the review effort, and worse, you get three subtly different standards. A workload that passes the Azure review might fail the AWS one not because the architecture differs but because the questions do. The fix is to recognise that the frameworks are three dialects of one language, and to build a single provider-agnostic review practice that maps onto each vendor's tooling.

What Is Genuinely Portable Across the Frameworks

Strip the vendor vocabulary away and a stable set of portable principles remains:

  • Blast-radius thinking. Every framework asks how failures are contained — zones, regions, fault domains, cells. The principle is identical; only the nouns change.
  • Failure-mode analysis. All three expect you to enumerate dependencies, reason about their failure modes, and design degradation behaviour.
  • Least privilege and data classification. Identity-centric access control and sensitivity-tiered data handling appear in every security pillar.
  • Elasticity over static capacity. All three prefer autoscaling and demand-matched provisioning over fixed sizing.
  • Cost as an architectural input. The AWS cost optimization pillar defines cost optimization as delivering business value at the lowest price point — a design concern, not a finance afterthought. Azure and GCP say the same in their own words.

The practical move is to express these as provider-agnostic review questions. Instead of "did you configure multi-AZ deployment?", ask "what is the recovery objective for this tier, and which failure domains does the design survive?" Instead of "is S3 bucket encryption on?", ask "is all data at this sensitivity level encrypted at rest, and who holds the keys?" The first form checks a checkbox; the second forces the trade-off into the open, and it works identically whether the workload runs on EC2, AKS or GKE.

Anchor the practice in a canonical workload record — a single artefact per workload, independent of cloud:

workload: payments-ledger
tier: critical
rto: 15m
rpo: 0
data_sensitivity: regulated-financial
cost_guardrails:
  monthly_budget_usd: 42000
  unit_cost_target: 0.003  # per transaction
  required_labels: [team, env, cost-center]
sustainability_notes: "Batch reconciliation shifted to low-carbon windows where region allows."
review:
  last_reviewed: 2025-11-14
  next_trigger: "major schema change or incident sev1"

This record is the unit of governance. Cloud-specific evidence attaches to it; the record itself never mentions a vendor.

Where the Frameworks Genuinely Differ

Honesty requires acknowledging real differences — they just aren't differences of standard.

Style. AWS is prescriptive and question-driven: the framework is literally a list of foundational questions, and the review is a structured conversation against them. AWS also extends the core framework with domain lenses (serverless, SaaS, and others) that tailor the questions to specific workload types. Azure leans toward design principles and checklists per pillar, with service guides that drill into individual offerings. Google Cloud's framework is more opinionated about operations, reflecting its SRE heritage — SLOs, error budgets and toil reduction are first-class citizens rather than implied outcomes.

Emphasis. Sustainability is a full pillar on AWS, woven into the other pillars on Azure and GCP. Operational excellence on GCP carries stronger software-engineering expectations (progressive delivery, SLO-driven alerting) than the equivalent Azure material.

Steering. Each vendor's tooling naturally steers findings toward its own services. An AWS review's remediation links point at AWS products; Azure Advisor recommendations land on Azure SKUs. That's fine — as long as the finding is recorded in your canonical vocabulary and only the remediation is vendor-specific.

Treat all of this as vocabulary and tooling mapping, not as three standards. When a GCP review says "error budget" and your canonical record says "reliability target," that's a translation, not a conflict.

Building the Provider-Agnostic Review Workflow

A single lifecycle serves all three clouds:

  1. Intake. A workload team creates or updates the canonical workload record. This is the only mandatory artefact.
  2. Trade-off assessment. The team answers the canonical question set — derived from the portable principles above — in writing. Short answers, explicit trade-offs: "we accept 4-hour RTO for the analytics tier to keep standby costs near zero."
  3. Findings. Gaps between stated objectives and observed architecture become findings, each with severity and owner.
  4. Remediation tracking. Findings land in the same backlog as feature work, not a separate governance tracker nobody reads.
  5. Re-review. Triggered by events (see section 7), not by calendar.

Each finding then maps to the native tooling of whichever cloud hosts the workload. On AWS, the Well-Architected Tool lets you record the review against the framework's question structure and track improvement plans. On Azure, the Well-Architected assessment and Azure Advisor surface posture and recommendations. On GCP, architecture guidance plus the various recommender surfaces (idle resource, security, cost) provide the evidence. The platform team owns the canonical framework and question set; workload teams answer once, and engineers attach per-cloud evidence as links and exports. Nobody fills in three questionnaires.

Encoding Reviews as Policy: A Concrete Example

The strongest way to keep one standard across three clouds is to stop relying on humans remembering it. Encode portable principles as policy as code, evaluated against Terraform plans in CI. Open Policy Agent — a CNCF graduated project — with Conftest is the standard toolchain here.

Take two portable rules: object storage must carry a cost-allocation label, and regulated-data storage must use customer-managed encryption keys. Note the second rule's framing: all three providers encrypt object storage at rest by default (AWS S3 with SSE-S3, Azure Storage, and Google Cloud Storage all encrypt automatically with provider-managed keys), so "encrypted at rest" is baseline everywhere and needs no policy. What a regulated data tier typically adds is key custody — a customer-managed key (CMEK) — and that is worth enforcing. In Rego:

package wellarchitected.storage

import rego.v1

storage_resources contains r if {
	some r in input.resource_changes
	r.type in {"aws_s3_bucket", "azurerm_storage_account", "google_storage_bucket"}
}

has_cost_label(r) if {
	labels := object.get(r.change.after, "tags",
		object.get(r.change.after, "labels", {}))
	labels["cost-center"] != ""
}

deny contains msg if {
	some r in storage_resources
	not has_cost_label(r)
	msg := sprintf("%s: missing cost-center label (canonical cost guardrail)", [r.address])
}

# CMEK requirement for regulated tiers. Provider-default encryption at rest
# is baseline on all three clouds; this rule enforces customer-managed keys
# where the canonical record marks the data as regulated.
deny contains msg if {
	some r in storage_resources
	r.type == "google_storage_bucket"
	not r.change.after.encryption
	msg := sprintf("%s: regulated tier requires CMEK (encryption block with KMS key)", [r.address])
}

Two caveats worth knowing before you copy this. First, the CMEK rule above shows the GCP shape; extend it with equivalent checks for AWS (server_side_encryption_configuration referencing a KMS key) and Azure (customer-managed key configuration) if your regulated tiers span providers. Second, the label check fails closed: if tags/labels are unknown at plan time (computed values), object.get returns {} and the deny fires. That's usually the safe default, but if it produces false positives on legitimately computed labels, add an explicit guard to skip resources whose label values are unknown rather than denying them.

Run it in CI with conftest test --policy policy/ tfplan.json against the plan output of any of the three providers. One policy file, three clouds, zero drift between standards. Every CI pass or fail is also review evidence: when the periodic re-review happens, the policy results answer a chunk of the canonical question set automatically, shrinking the manual questionnaire to the genuinely judgement-based questions.

Where FinOps Fits in the Same Practice

Cost is a pillar in every framework, which means it belongs inside the review practice — not in a parallel FinOps ceremony that discovers architectural decisions after the bill arrives. The FinOps Framework organises cost work into capabilities like allocation, anomaly management and commitment-based discount coverage; each of those maps cleanly onto fields and findings in the canonical workload record.

Concretely: tagging and label standards live in the record and are enforced by the same OPA policies shown above (allocation). Unit-cost targets and budgets are declared per workload, so a cost finding — "this tier's cost per transaction doubled after the caching change" — sits next to the reliability and security findings in the same review, owned by the same team. Commitment coverage decisions (Savings Plans, reserved instances, committed use discounts) become documented trade-offs: "we accept one-year lock-in on the baseline fleet because the workload's shape is stable."

The failure mode to avoid is cost review run entirely from finance tooling, disconnected from architecture. A dashboard can tell you spend went up; only the review practice can tell you whether that was a deliberate, documented trade-off or an accident.

Rolling It Out Without a Governance Bureaucracy

Start small and calibrate. Pick one workload per cloud — ideally three that share a shape, like a web API with a database — and run them through a draft canonical question set. You'll find questions that are redundant, questions nobody can answer, and gaps where a real incident taught you something the frameworks didn't ask. Fix the set before scaling.

Then scale through artefacts, not meetings: the workload record template, the OPA policy pack, and a short written guide on how findings map to each cloud's native tooling. New workloads inherit the whole practice by copying a directory.

Keep the cadence trigger-based rather than calendar-driven. Reviews happen when: a new workload is intake'd, a major architectural change is proposed, a severity-1 incident closes, or a cost anomaly breaches the guardrail. Calendar-driven annual audits decay into box-ticking; trigger-driven reviews stay attached to real decisions.

That is the whole thesis in operational form: one review practice, three tool mappings, trade-offs made explicit and reviewable — regardless of which cloud's logo is on the bill.

What to Do Next

  • Draft your canonical workload record (the YAML above is a workable starting point) and pilot it on one workload per cloud this quarter.
  • Extract 15–25 portable review questions from the three framework documents, phrased as trade-offs, not checkboxes.
  • Write your first three OPA policies — CMEK for regulated tiers, cost labels, and one reliability rule — and wire them into Terraform CI for all three providers.
  • Map one real finding through each vendor's native tool (AWS Well-Architected Tool, Azure Advisor, GCP recommenders) to validate the translation layer before scaling.
