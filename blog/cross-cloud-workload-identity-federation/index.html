Federating Workload Identity Across AWS, Azure, and GCP

Cesar A. Nogueira
April 22, 2025 · 11 min read

The long-lived-secret problem in a multi-cloud pipeline

Any pipeline that touches more than one cloud provider eventually accumulates a small pile of standing secrets. A GitHub Actions workflow that deploys infrastructure to AWS and also pushes container images to Google Artifact Registry typically ends up with an IAM user access key sitting in one secret store and a GCP service account JSON key sitting in another. A workload running on-prem or in Kubernetes that needs to write to an Azure Storage account gets a client secret on an app registration. An IAM access key and an unmanaged GCP service account JSON key don't expire on their own — they're valid until someone rotates or revokes them. They get copied into CI secret managers, sometimes into .env files during debugging, occasionally into a teammate's local shell history, and from that point on they are a liability whether or not anyone ever misuses them — someone has to rotate them, someone has to notice if they leak, and someone has to explain during an audit why a ten-month-old access key still has full S3 access.

The pattern that eliminates this class of problem is workload identity federation: instead of minting a cloud-native credential and storing it somewhere, the workload authenticates with a token it already has — one issued by its own platform, whether that's a CI system's OIDC token, a Kubernetes service account token, or another cloud's identity token — and exchanges that token at request time for temporary, scoped credentials in the target cloud. No secret is generated ahead of time, nothing sits in a vault waiting to be rotated, and a leaked exchange only yields a credential that's bounded by a session lifetime far shorter than the lifespan of the static key it replaces — typically well under it, though the exact ceiling varies by provider and configuration, as covered below. All three major providers now support this, which is the good news. The mechanics of establishing that trust relationship, however, are not interchangeable, and a design that treats AWS, Azure, and GCP as offering "the same feature with different button labels" will misconfigure at least one of them.

The federation pattern, in the abstract

Strip away provider-specific naming and the same three actors show up every time: an external token issuer that the workload already trusts (a CI platform, an OIDC-compliant identity provider, or a foreign cloud's IAM), a federation broker inside the target cloud that validates incoming tokens, and a target identity — a role, a managed identity, or a service account — that actually carries permissions.

The sequence is consistent too. First, an administrator registers the issuer and its expected audience with the target cloud, establishing a trust anchor. Second, a trust condition is defined that says which token claims are acceptable — which issuer, which subject, which audience, sometimes which additional claims like a repository or environment name. Third, at runtime, the workload presents its externally issued token to the cloud's federation endpoint. Fourth, the cloud validates the token's signature against the issuer's published keys and checks the claims against the configured trust condition. Fifth, if everything matches, the cloud issues a short-lived, scoped credential — not the original token reused, but a new cloud-native credential with its own expiry.

What differs between AWS, Azure, and GCP is how the trust anchor is represented as a resource, the syntax used for claim matching, the default and maximum lifetime of the issued credential, and — critically — whether the flow grants a session under the identity itself or impersonates a separate identity. Those differences are exactly where cross-cloud designs go wrong if each provider isn't mapped on its own terms.

AWS: OIDC/SAML identity providers bound to an IAM role

AWS makes the trust anchor an explicit, standalone resource: an IAM identity provider object, created once per external issuer, holding the issuer URL, the accepted audience, and (for OIDC) a certificate thumbprint. This lines up with AWS's guidance on identity providers and federation into AWS, which frames federation as the recommended alternative to individual IAM users for both human and workload access. Once the provider resource exists, the actual scoping decision lives in the IAM role's trust policy, using condition operators like StringEquals or StringLike against token claims such as sub and aud.

A minimal Terraform setup looks like this:

resource "aws_iam_openid_connect_provider" "ci" {
  url             = "https://token.actions.githubusercontent.com"
  client_id_list  = ["sts.amazonaws.com"]
  thumbprint_list = ["6938fd4d98bab03faadb97b34396831e3780aea1"]
}

resource "aws_iam_role" "ci_deploy" {
  name = "ci-deploy-role"

  assume_role_policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect = "Allow"
      Principal = {
        Federated = aws_iam_openid_connect_provider.ci.arn
      }
      Action = "sts:AssumeRoleWithWebIdentity"
      Condition = {
        StringEquals = {
          "token.actions.githubusercontent.com:aud" = "sts.amazonaws.com"
        }
        StringLike = {
          "token.actions.githubusercontent.com:sub" = "repo:my-org/my-repo:environment:production"
        }
      }
    }]
  })

  max_session_duration = 3600
}

The workload calls sts:AssumeRoleWithWebIdentity with the OIDC token and gets back temporary credentials capped by max_session_duration, and every permission granted downstream is whatever's attached to the role's policy — federation only changes how the role is assumed, not what it can do once assumed.

Azure: Entra Workload ID federated credentials

Azure skips the separate provider-object step entirely. The trust relationship is attached directly to an app registration or a user-assigned managed identity as a federated credential resource, described in Microsoft's workload identity federation documentation as a way to let workloads outside Azure — GitHub Actions runs, Kubernetes pods, other clouds — obtain Entra tokens without a client secret at all. Each federated credential specifies an issuer, a subject identifier, and an audience, and per Microsoft's documentation these values "must case-sensitively match the corresponding issuer, subject and audience values contained in the token" for the exchange to be authorized — there's no wildcard or pattern-matching mechanism in the trust condition itself, unlike AWS's StringLike or GCP's CEL expressions.

az identity federated-credential create \
  --name "gha-federated-cred" \
  --identity-name "ci-deploy-identity" \
  --resource-group "platform-rg" \
  --issuer "https://token.actions.githubusercontent.com" \
  --subject "repo:my-org/my-repo:environment:production" \
  --audiences "api://AzureADTokenExchange"

The equivalent azurerm_federated_identity_credential Terraform resource takes the same three fields. At runtime, the workload uses MSAL's client-credential flow, passing the external token as an assertion, and gets back a normal Entra access token scoped to whatever roles are assigned to that managed identity or app registration. Because the subject string has to match exactly — including case and the precise claim format the issuer emits — a likely failure mode here isn't a permissions problem at all, it's a mismatch between the sub claim the CI platform actually issues and the subject identifier typed into the federated credential. Debugging usually means decoding the actual token (e.g., at the CI run) and diffing it claim-by-claim against the configured value, rather than assuming the documented format is exactly what's produced.

GCP: Workload Identity Federation pools and providers

GCP's model introduces two chained resources: a Workload Identity Pool, and one or more Providers registered under it. Per Google Cloud's Workload Identity Federation documentation, the provider carries an attribute mapping that translates claims from the external token into Google-recognized attributes, most importantly google.subject. The typical pattern for CI use cases binds the external identity to impersonate a service account via the roles/iam.workloadIdentityUser role, with permissions living on that service account; GCP also supports granting IAM roles directly to the external principal or principalSet without a service-account hop, per the same documentation, but the impersonation pattern remains the more common and more thoroughly documented approach, so it's what the rest of this section assumes.

gcloud iam workload-identity-pools create "ci-pool" \
  --location="global" --display-name="CI federation pool"

gcloud iam workload-identity-pools providers create-oidc "github-provider" \
  --location="global" \
  --workload-identity-pool="ci-pool" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" \
  --attribute-condition="assertion.repository == 'my-org/my-repo' && assertion.ref == 'refs/heads/main'"

gcloud iam service-accounts add-iam-policy-binding "ci-deploy@my-project.iam.gserviceaccount.com" \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/123456789/locations/global/workloadIdentityPools/ci-pool/attribute.repository/my-org/my-repo"

The CEL expression in --attribute-condition is where scope actually gets enforced, and it's also where it most often gets left too loose — an expression that only checks assertion.repository without also checking assertion.ref or an environment claim lets any branch or workflow in that repository mint the same impersonation grant.

Where the three providers actually diverge

Laid side by side, the divergence is concrete rather than cosmetic. AWS represents the trust anchor as a standalone IAM Identity Provider object and expresses scope through role trust-policy condition operators. Azure attaches a federated credential directly onto the identity that will be used, with case-sensitive exact subject matching. GCP interposes a Pool and Provider pair with a CEL-based attribute mapping and condition, and typically routes access through service account impersonation rather than direct role assumption. That last point matters operationally: AWS and Azure hand the workload a session or access token tied to the role or app identity being assumed, while GCP's common path produces a token that impersonates a separate service account — meaning the audit trail and the effective identity are one hop removed from the federation config itself.

Session lifetimes vary too, and they're not just a convenience knob — they define how long a mis-issued or intercepted credential exchange stays exploitable. AWS role sessions are capped by MaxSessionDuration, which AWS's IAM roles and federation documentation covers as a configurable setting on the role — set it as low as the workflow allows rather than relying on the default. Azure Entra tokens obtained through this flow follow standard Entra ID token lifetimes, refreshable only by repeating the federated exchange rather than by extending the existing token, per Microsoft's workload identity federation documentation. GCP's impersonated service account tokens are similarly time-bounded, with the exact default and maximum lifetime governed by org policy per Google Cloud's Workload Identity Federation documentation. Treat the specific hour counts as something to check against current provider docs and your own org policy rather than as fixed values to design around — none of these defaults are interchangeable across providers.

Wiring one CI/CD identity to three clouds

A pipeline that needs to reach all three clouds from one CI job doesn't need three different issuers — it needs one OIDC-issuing platform (a CI system's built-in token endpoint is the common case) federated separately into each cloud, with each cloud's trust resource pointing at the same underlying claims but expressed in that cloud's own syntax: an AWS IAM identity provider plus trust-policy condition, an Azure federated credential on the target managed identity, and a GCP workload identity pool/provider plus service account binding.

The design decision that matters most here is which claims the trust condition checks. Scoping only on the repository claim is a risky simplification: any workflow in that repository — including a pull request from a fork, or a stale branch nobody's looked at in months — inherits the same trust. Production-grade trust conditions check repository, deployment environment, and branch/ref together, so a workflow running against a feature branch can't obtain the same credentials as one running against main in the production environment. AWS expresses this as multiple StringLike/StringEquals conditions on the trust policy; Azure requires a separate federated credential per environment/subject combination, since its exact-match subject leaves no other way to scope multiple environments; GCP folds it into a single CEL expression.

With this shape in place, no cloud-native secret exists anywhere in the system. The CI platform's token is short-lived and reissued by the platform itself for every run; each cloud's federation step independently produces a credential that expires on its own schedule. A compromise of the CI token has a blast radius bounded by that token's own lifetime and by however tightly the receiving cloud's trust condition was scoped — not by whatever a leaked static key would have allowed.

Operational pitfalls and a hardening checklist

The recurring failure pattern across all three providers is the same shape even though the syntax differs: a trust condition that's broader than intended. A wildcard in an AWS StringLike condition that matches more repositories than expected, an Azure subject identifier that was set to a loose value during initial testing and never tightened, a GCP attribute condition that checks repository but not ref — all produce the same outcome, a federation trust boundary that's wider than whoever configured it believed.

Federation removes the standing-secret problem, but it does nothing to fix an overly broad authorization design sitting behind it. A role, managed identity, or service account still needs least-privilege scoping on its own terms — narrow policies, scoped resource access, no wildcard Action: * grants "because it's federated now so it's fine." Treat the elimination of the secret and the tightening of permissions as two separate hardening tasks, not one.

Trust configuration itself is also IAM configuration, and it drifts the same way security groups or bucket policies do. An IAM identity provider edited by hand in the AWS console, a federated credential added directly in the Entra portal, a workload identity pool provider tweaked via gcloud outside of Terraform state — each of these needs the same change-review and drift-detection treatment as any other access-control change, because a change here directly redefines who can obtain credentials, not just what those credentials can do.

Before applying a new federation trust relationship to a production role, managed identity, or service account, validate it in a non-production project, subscription, or account first. This matters especially for GCP's CEL-based attribute conditions: a malformed --attribute-condition is rejected at creation time, but a condition that's syntactically valid yet logically too loose — one that doesn't actually check the claims you think it does — deploys without error and silently over-grants access. Test the exchange against a real token from a scoped-down non-production service account before pointing the same provider configuration at anything that matters.

What to do next

Start by inventorying every long-lived cloud credential currently sitting in a CI secret store or a workload's environment variables, and for each one, identify which cloud it targets and what CI platform or workload identity is using it. For each pairing, work through the provider-specific setup above — an aws_iam_openid_connect_provider and trust policy for AWS, an azurerm_federated_identity_credential for Azure, a workload identity pool and provider for GCP — and validate the exchange in a non-production account before touching the credential that's actually in use. Once a federated path is confirmed working end to end, delete the static key it replaces rather than leaving it as a fallback; a long-lived credential that's merely unused is still a long-lived credential that needs rotation and audit. Finally, review the AWS, Azure, and Google Cloud Well-Architected security guidance for each provider you're federating into, since identity federation is one control among several that these frameworks expect to see applied together with least-privilege role design and change auditing.
