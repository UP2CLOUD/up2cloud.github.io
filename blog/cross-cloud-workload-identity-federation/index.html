Cross-Cloud Identity Federation: Replacing Static IAM Keys

Cesar A. Nogueira
April 22, 2025 · 12 min read

The standing risk of long-lived cloud credentials

Every static IAM access key or service-account JSON file shares the same structural flaw: once it exists, it exists indefinitely. It sits in a CI secret store, a .env file, a config map, or worse, a laptop's home directory, and it remains valid until someone actively revokes it. Encrypting the secret at rest, restricting who can read the vault, and rotating it on a schedule all reduce the odds of exposure, but none of them change the fundamental shape of the risk: a single leaked value grants access for as long as it takes someone to notice.

That "as long as it takes someone to notice" clause is the real problem. Rotation policies are typically calendar-driven rather than event-driven. A key copied into a build log, committed to a public repo by accident, or exfiltrated from a compromised CI runner keeps working until an audit catches it, a security scanner flags it, or an attacker's use of it triggers an alert. There is no expiry built into the credential itself. The blast radius is bounded only by the scope of the IAM policy attached to it, and in practice those policies tend to accrete permissions over time rather than shed them.

This becomes acute the moment a workload needs to reach across a trust boundary — a GitHub Actions pipeline deploying to AWS, a GKE workload reading from an on-prem database, a CI job pushing artifacts to a different cloud than the one it runs in. Each of these crossings historically meant minting a durable secret and distributing it: an AWS access key pasted into GitHub Secrets, a GCP service-account JSON key downloaded and stored as a CI variable. Every one of those is a standing liability that didn't need to exist, because the actual requirement was never "a permanent secret" — it was "prove who I am, right now, for the next few minutes."

Cross-cloud identity federation exists to close that gap: replace the durable secret with a short-lived, cryptographically verifiable assertion that a trusted party issues and the target cloud checks on the spot.

The federation pattern: trading a token for a credential

Strip away the vendor-specific naming and every identity federation implementation reduces to the same three-step exchange:

  1. A trusted identity provider (an OIDC issuer) mints a short-lived signed token — a JWT — that asserts facts about the calling workload: which repository triggered it, which branch, which service account, which SPIFFE trust domain.
  2. The workload presents that token to the target cloud's token-exchange endpoint (AWS STS, Google's Security Token Service).
  3. The cloud verifies the token's signature against the issuer's published public keys, checks the token's claims against a pre-configured trust policy, and — if everything matches — issues scoped, temporary cloud credentials that expire in minutes to hours.

The property that makes this materially different from static keys is not just that the resulting credential is short-lived — it's that no long-lived secret exists at any point in the chain. There's nothing to leak from a secret store, because there's no secret in the secret store. The OIDC token's own value is bounded by a short expiry window — typically minutes — rather than being single-use: it's a bearer credential, so anyone holding a valid, unexpired copy could present it again within that window. The security benefit comes from that short TTL plus the fact that a fresh token is minted per job, not from the token being consumed on use, which is why protecting it in transit and keeping it out of logs still matters for as long as it remains valid. Trust is established exactly once, when an administrator registers the identity provider and writes the trust policy; every subsequent request is verified cryptographically against that configuration, with no human back in the loop.

AWS's documentation on OIDC federation frames this directly: applications should be configured "to request temporary AWS security credentials dynamically when needed using OIDC federation" rather than storing AWS credentials long-term outside AWS. AWS's OIDC federation, Google Cloud's Workload Identity Federation, and the open SPIFFE/SPIRE project are three independent implementations of this same token-for-credential trade. None of them requires a company to run its own centralized identity broker — each cloud validates tokens against whatever OIDC issuer it's told to trust, whether that's GitHub Actions, GitLab CI, a Kubernetes cluster's service account issuer, or a self-hosted SPIRE server.

AWS: OIDC identity provider and IAM role trust policies

Setting up federation in AWS starts with registering the external OIDC issuer as an IAM identity provider. For GitHub Actions, that means registering token.actions.githubusercontent.com as a trusted issuer, either through the console, Terraform, or the CLI:

aws iam create-open-id-connect-provider \
  --url https://token.actions.githubusercontent.com \
  --client-id-list sts.amazonaws.com

The --thumbprint-list flag is optional and can be omitted, as it is above: IAM retrieves the top intermediate CA thumbprint automatically, and AWS validates OIDC endpoints with trusted TLS certificates — which GitHub's is — directly against its library of root CAs. Thumbprint matching only comes into play as a fallback for issuers that don't present a certificate from a trusted root. A hardcoded thumbprint copied from an older tutorial can also simply be wrong, since GitHub has rotated its signing CA before.

That registration alone grants nothing — it just tells AWS which issuer's signatures to trust. The actual authorization lives in the IAM role's trust policy, which constrains which tokens from that issuer are allowed to assume the role:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com"
        },
        "StringLike": {
          "token.actions.githubusercontent.com:sub": "repo:octo-org/octo-repo:ref:refs/heads/main"
        }
      }
    }
  ]
}

The aud condition confirms the token was minted for AWS specifically, but it's the sub condition that does the real access control. GitHub's OIDC tokens encode the repository, and optionally the branch or environment, into the sub claim. A trust policy that only checks aud and skips sub — or worse, uses a wildcard like repo:octo-org/*:* — effectively lets any workflow in any repository under that org assume the role, which recreates the same standing-risk problem federation was supposed to eliminate, just with an extra network hop. Scoping sub down to a specific repo and branch (or a specific environment: claim, when GitHub Environments are used) is what keeps the blast radius of a compromised workflow file contained to that one pipeline.

Once the trust policy is scoped correctly, the credentials returned by AssumeRoleWithWebIdentity are ordinary temporary session credentials — an access key, secret key, and session token, all expiring on a timer with no rotation or lifecycle to manage. Nothing was ever written to a secret store on the AWS side.

GCP: Workload Identity Federation and service account impersonation

Google Cloud's take on the same pattern is Workload Identity Federation, and it deliberately routes around the older approach it replaces: downloading a service account's JSON key file, storing it in CI, and using it directly. That legacy pattern has exactly the standing-risk profile described above — a downloadable, non-expiring private key that grants whatever the service account can do, for as long as the key exists.

Workload Identity Federation instead maps an external token to a Google identity that's allowed to impersonate a service account, never to hold its key. Setting it up means creating a workload identity pool, then a provider inside that pool with an attribute mapping and condition that filters which external tokens are honored:

gcloud iam workload-identity-pools create "github-pool" \
  --location="global" \
  --display-name="GitHub Actions pool"

gcloud iam workload-identity-pools providers create-oidc "github-provider" \
  --location="global" \
  --workload-identity-pool="github-pool" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" \
  --attribute-condition="assertion.repository=='octo-org/octo-repo'"

The attribute-mapping flag translates claims from the external OIDC token into attributes Google IAM can reason about, and attribute-condition is the enforcement point equivalent to AWS's sub restriction — without it, any token from the registered issuer would map through. The service account itself then needs a binding that only allows impersonation from principals matching that specific repository and, ideally, a specific ref:

gcloud iam service-accounts add-iam-policy-binding \
  "deploy-sa@my-project.iam.gserviceaccount.com" \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/123456789/locations/global/workloadIdentityPools/github-pool/attribute.repository/octo-org/octo-repo"

Google's Workload Identity Federation documentation frames the entire mechanism around this impersonation model rather than key issuance. At no point in this flow does GCP generate a downloadable long-lived key — the CI job exchanges its GitHub-issued OIDC token for a short-lived Google access token scoped to exactly the service account it's permitted to impersonate, and that token expires on its own within the hour.

Beyond CI/CD: SPIFFE/SPIRE for workloads outside any cloud IAM boundary

CI/CD pipelines are the easiest place to introduce federation because GitHub, GitLab, and similar platforms already act as convenient OIDC issuers. But plenty of workloads don't run inside a CI system at all — a service running on-prem, a VM in a colo, a pod in a Kubernetes cluster that needs to authenticate to a cloud it isn't running in. None of these have a natural OIDC issuer handed to them by a SaaS platform.

This is the gap SPIFFE and its reference implementation, SPIRE, fill. SPIFFE defines a cloud-agnostic identity format — a SPIFFE ID, expressed as a URI like spiffe://example.org/ns/payments/sa/worker — and a corresponding signed document, the SVID (SPIFFE Verifiable Identity Document), that a workload can present as proof of that identity. Critically, SPIFFE doesn't depend on any single cloud's notion of an identity provider; a SPIRE server issuing SVIDs to workloads on bare metal is functionally equivalent, from the perspective of a verifier, to GitHub Actions issuing OIDC tokens to a workflow run.

Extending this across a cloud boundary involves two distinct mechanisms that are easy to conflate but solve different problems. The first is trust domain federation proper: a SPIRE server in one trust domain (say, an on-prem data center) can be configured to federate with a SPIRE server in a different SPIFFE trust domain, exchanging trust bundles so that each side can validate SVIDs minted by the other. This is a peer relationship between two systems that both implement SPIFFE — it's how two independently operated SPIRE deployments come to trust each other's workload identities directly. AWS and GCP don't implement SPIFFE and aren't SPIFFE trust domains, so they can't be a party to this kind of federation.

The second mechanism is what actually lets a SPIRE-issued identity reach AWS or GCP: SPIRE's separate OIDC Discovery Provider plugin, which exposes the SPIRE server's JWT-SVIDs through a standard JWKS and openid-configuration endpoint. Once that plugin is deployed, the SPIRE server looks like any other OIDC issuer from AWS's or GCP's point of view, and can be registered as a trusted issuer in an AWS IAM OIDC identity provider or a GCP workload identity pool the same way token.actions.githubusercontent.com is registered for GitHub Actions — with the same sub/attribute-condition scoping described above governing which SVIDs are actually allowed to assume a role or impersonate a service account. This is what makes the pattern useful for hybrid and multi-cloud estates: no single cloud's built-in identity concept covers workloads running outside it, but a SPIRE server fronted by the OIDC Discovery Provider can stand in as the issuer for all of them, generalizing the token-exchange pattern past any one vendor's implementation — without requiring AWS or GCP to join a SPIFFE trust domain that they have no mechanism to participate in.

Scoping trust: attribute conditions and least privilege

Federation removes the standing-secret problem only if the trust configuration is scoped tightly. A federated setup with a wildcard sub claim, an unrestricted attribute-condition, or a SPIFFE trust domain that accepts any workload identity within it reintroduces exactly the risk federation exists to remove — it just moves the point of failure from "a leaked key" to "a misconfigured trust policy that treats an entire identity provider as equally trustworthy."

The scoping discipline that matters here operates on multiple axes simultaneously:

  • Repository and branch (or environment) for CI-issued tokens — restrict sub to the specific workflow that legitimately needs the role, not the whole org.
  • SPIFFE path segments for SPIRE-issued identities — a trust policy that matches spiffe://example.org/ns/payments/* is meaningfully different from one that matches all of spiffe://example.org/*.
  • Audience — confirming the token was minted for the specific cloud being called, not just any recipient.

None of this substitutes for scoping the IAM role or service account itself. A perfectly scoped trust condition attached to an over-permissioned role — one with AdministratorAccess or broad roles/editor bindings — still hands out excessive access the moment the trust condition is satisfied. Federation and least-privilege IAM are separate controls that need to be applied together: narrow the who can assume this condition, and separately narrow the what this role can do policy. The goal the whole pattern is chasing isn't just temporary credentials — it's temporary and scoped. Either one alone leaves a gap.

Migrating pipelines off static keys without breaking them

Ripping out static keys in one pass is how outages happen. A phased cutover keeps the pipeline working throughout:

  1. Stand up federation alongside existing keys. Register the OIDC provider, write the trust policy or workload identity pool config, and grant the target role or service account the same permissions the static key currently has. Don't touch the existing key yet.
  2. Cut pipelines over one at a time. Update each workflow to request federated credentials (aws-actions/configure-aws-credentials with role-to-assume for GitHub Actions, or google-github-actions/auth with workload_identity_provider for GCP) and verify it runs successfully end to end before moving to the next pipeline.
  3. Watch for stragglers. AWS surfaces an access key's last-used timestamp directly in IAM (aws iam get-access-key-last-used), and CloudTrail records every API call's credential type. On GCP, key usage isn't reliably visible without Data Access audit logs enabled on the relevant APIs, which are off by default — without that, the logs will show no trail at all, not confirmation the key is idle. The IAM "unused service account key" Recommender surfaces stale keys without requiring that audit-log configuration and is the more reliable first check. Don't rely on documentation or memory of "which pipelines still use the old key" — check the logs or the Recommender.
  4. Deprecate in order, not all at once. First disable the ability to create new static keys for the account or service account. Then, once usage data confirms zero recent activity, deactivate (don't immediately delete) the existing keys — deactivation is reversible if something was missed. After a quiet period, delete the keys outright, then finally remove the IAM permissions that allowed key creation in the first place.

A few operational failure modes are worth planning for rather than discovering in production. Audience mismatches are the most common first-run failure — a trust policy checking for aud: sts.amazonaws.com will silently reject a token minted with a different audience string, and the error message from STS doesn't always make the mismatch obvious. Clock skew matters because OIDC tokens carry short validity windows; a CI runner or SPIRE agent with a badly drifted clock can have its tokens rejected as expired or not-yet-valid. And identity provider outages are a new failure mode that didn't exist with static keys — if GitHub's OIDC issuer or the SPIRE server is unreachable, no new credentials can be minted at all, which is a real availability trade-off against the security gained and worth accounting for in pipelines that can't tolerate any downtime.

What to do next

Start by auditing what's actually using long-lived credentials today — pull access-key-last-used data from IAM and service-account key usage from GCP's Recommender or Cloud Audit Logs (if enabled) before assuming which pipelines matter most. Pick the single highest-value pipeline (the one with the most sensitive target permissions, not necessarily the most-used one) and federate it first, using it to validate the trust policy scoping before rolling the pattern out further. For anything running outside CI/CD entirely — on-prem services, cross-cluster workloads — evaluate whether a SPIRE deployment is warranted before reaching for cloud-specific workarounds. Whichever path is chosen, treat the trust policy's sub/aud/attribute conditions as the security boundary they are, and review them with the same scrutiny given to the IAM policy on the other end.
