AWS PrivateLink vs Azure Private Link: Egress Without NAT

Cesar A. Nogueira
April 22, 2025 · 13 min read

Why NAT gateways and public IPs stopped being the default egress path

For most of the last decade, the default answer to "how does a workload in a private subnet reach anything" was a NAT gateway or NAT instance sitting on a public subnet, forwarding traffic through an internet gateway. If the destination was an AWS-managed service, a SaaS API, or a partner integration, the request left the VPC, traversed the public internet (or at best AWS's edge), and arrived at a public IP or public DNS name. The reverse case — a partner reaching into your environment — usually meant standing up a public-facing load balancer with an allowlist of source IPs, or negotiating a VPC peering connection or Transit Gateway attachment.

That model concentrates every egress decision at the perimeter: the NAT gateway's route table entry, the security group attached to the instance, and whatever the destination happens to publish as reachable. The problem is granularity. A security group can restrict egress to a CIDR block and a port, but it has no concept of "this workload may call the S3 API for one specific bucket" or "this workload may reach Secrets Manager but nothing else in the account." Once traffic is allowed to leave via NAT, it can reach anything at that IP/port, and the actual authorization happens downstream, in IAM policy or the receiving service's ACL — which is the right place for authorization, but leaves the network layer unable to express intent.

Interface endpoints invert that model. Instead of asking "what can leave this subnet," the question becomes "what is this specific elastic network interface (ENI) or NIC allowed to resolve and reach." That's the shift this article works through: AWS PrivateLink and Azure Private Link move the primary control point from the perimeter firewall to the endpoint itself, and the perimeter firewall becomes a backstop rather than the only line of defense.

How AWS PrivateLink actually routes traffic

An AWS interface VPC endpoint provisions an ENI directly inside a chosen subnet, with a private IP address drawn from that subnet's CIDR range. When private_dns_enabled is turned on, AWS also associates a Route 53 private hosted zone with the VPC so that the standard service DNS name (for example, secretsmanager.us-east-1.amazonaws.com) resolves to that private IP instead of a public one. Applications don't need to change a single connection string — they call the same hostname they always did, and DNS resolution is what redirects them onto the private path.

Critically, AWS PrivateLink documentation is explicit that this traffic does not need an internet gateway, NAT device, public IP address, Direct Connect connection, or Site-to-Site VPN connection — it stays on AWS's internal network end to end, and "you control the specific API endpoints, sites, services, and resources that are reachable from your VPC."

It's worth separating the distinct things that all get lumped under "VPC endpoints":

  • Gateway endpoints — only available for S3 and DynamoDB. These don't create an ENI at all; they add a route table entry that points traffic at a managed prefix list, and they're free.
  • Interface endpoints for AWS services — the ENI-based model described above, used for everything else (Secrets Manager, KMS, SSM, ECR, CloudWatch Logs, and dozens more).
  • PrivateLink endpoint services (NLB-backed) — a customer or partner runs a Network Load Balancer behind an endpoint service, and consumers reach it by creating an interface endpoint pointing at that service — the same ENI-with-private-DNS mechanism described above. This is the cross-account access pattern, not an AWS-managed service at all — it's how SaaS vendors and internal platform teams expose an API without VPC peering.
  • Gateway Load Balancer endpoints (GWLB-backed) — when the endpoint service instead fronts a Gateway Load Balancer, consumers provision a distinct resource type, a Gateway Load Balancer endpoint (vpc_endpoint_type = "GatewayLoadBalancer"), and reference it as a target in a route table the way a gateway endpoint is referenced — it has no application-facing private DNS name the way an interface endpoint does. This is the resource used to transparently insert a firewall, IDS/IPS, or traffic-mirroring appliance into a path.

That third and fourth category matter for architecture decisions later in this article: the provider side controls an allowlist of which AWS principals may create a connection to the endpoint service, and the consumer side still needs to provision the matching endpoint type — an interface endpoint for an NLB-backed service, a Gateway Load Balancer endpoint routed via a route table for a GWLB-backed one — plus, for interface endpoints, the ENI's security group and endpoint policy to lock down what's actually usable once connected.

How Azure Private Link mirrors and differs from the AWS model

Azure's equivalent primitive, the private endpoint, does almost the same thing structurally: it attaches a NIC with a private IP from the consumer's VNet, mapped either to a specific PaaS resource (a Storage account, a Key Vault, an Azure SQL server) or to a Private Link Service that a provider has published. Per Microsoft's own framing, Azure Private Link lets you access PaaS services and partner services "over a private endpoint in your virtual network," with traffic traveling the Microsoft backbone network rather than the public internet — "exposing your service to the public internet is no longer necessary."

Name resolution works differently in mechanics but identically in intent. AWS uses Route 53 private hosted zones tied to the VPC; Azure uses Private DNS zones tied to each service, following a privatelink.* naming pattern whose exact suffix varies per resource type and has to be looked up rather than inferred — Blob Storage uses privatelink.blob.core.windows.net, Key Vault uses privatelink.vaultcore.azure.net, and Azure SQL uses privatelink.database.windows.net. Whichever zone applies, it must be explicitly linked to every VNet that needs to resolve the private endpoint's name to its private IP. There's no automatic "enable private DNS on this endpoint and you're done" — the correct DNS zone, the zone group linking the private endpoint to that zone, and the virtual network link are three separate resources that all have to be wired up correctly.

One nuance worth calling out for anyone mapping mental models across clouds: Azure Load Balancer has a Gateway Load Balancer SKU that is the direct analog to AWS Gateway Load Balancer endpoints for inline appliance insertion — it uses the same bump-in-the-wire, VXLAN-encapsulated chaining model to transparently route traffic through firewalls, IDS/IPS, or traffic-mirroring NVAs. The wiring differs from AWS's endpoint-service pattern, though: rather than a consumer creating an endpoint that points at the appliance fleet, a Standard Public Load Balancer's frontend (or a VM's NIC) is configured to reference the Gateway Load Balancer's frontend IP configuration directly, chaining the appliance into the path before traffic reaches its destination. Anyone who has stood up an AWS Gateway Load Balancer endpoint for inline inspection should recognize the shape of the Azure equivalent, even though the specific resource references and provisioning flow differ.

Choosing the right primitive for the use case

For first-party managed services, the decision tree is mostly free of ambiguity. On AWS, if the target is S3 or DynamoDB, use a gateway endpoint — it's free, requires no ENI, and only needs a route table update plus an endpoint policy. For every other AWS service (Secrets Manager, KMS, ECR, SSM, CloudWatch, Bedrock, and so on), use an interface endpoint. On Azure, there's no gateway-endpoint equivalent — Storage, Key Vault, SQL Database, and everything else all go through private endpoints uniformly.

For cross-account or cross-subscription access to internal services your own teams operate, AWS endpoint services (PrivateLink) and Azure Private Link Service serve the same purpose: a provider team exposes a service without requiring full VPC peering or VNet peering between every consumer and provider. This matters at scale — peering is fundamentally a many-to-many mesh problem (transitive routing isn't supported, so N accounts wanting to reach one service still need N peering connections plus route table entries on both sides), while an endpoint service is a hub that any approved consumer can attach to without touching the provider's route tables at all.

A number of SaaS and data-platform vendors publish PrivateLink or Private Link endpoint aliases specifically so customers don't need to open public egress for the integration. When evaluating a new SaaS vendor, checking for a published endpoint service is worth doing before defaulting to a NAT-routed integration.

Where PrivateLink/Private Link is the wrong tool: bulk data transfer to public internet destinations (there's no per-service endpoint for "the internet"), any service that simply hasn't published an endpoint offering, and dense many-to-many service meshes where the operational overhead of provisioning and approving dozens of endpoint connections exceeds the cost of a properly scoped peering topology or a service mesh with mTLS.

Configuring a locked-down interface endpoint (AWS Terraform example)

The endpoint itself is only half the control — the endpoint policy is what actually restricts which API calls are permitted through it. A default "allow all principals, all actions" endpoint policy means anything in the VPC with network access to the ENI can call any action against any resource that IAM otherwise permits, which defeats much of the purpose of scoping the endpoint in the first place.

resource "aws_vpc_endpoint" "secretsmanager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.us-east-1.secretsmanager"
  vpc_endpoint_type    = "Interface"
  subnet_ids           = [aws_subnet.private_a.id, aws_subnet.private_b.id]
  security_group_ids   = [aws_security_group.secretsmanager_endpoint.id]
  private_dns_enabled  = true

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [
      {
        Effect    = "Allow"
        Principal = "*"
        Action    = ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"]
        Resource  = [
          "arn:aws:secretsmanager:us-east-1:123456789012:secret:app/prod/*"
        ]
      }
    ]
  })
}

resource "aws_security_group" "secretsmanager_endpoint" {
  name_prefix = "vpce-secretsmanager-"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
  }
}

This endpoint policy narrows the reachable action set to two read operations against one secrets path prefix — an application on this ENI cannot call PutSecretValue, cannot list unrelated secrets, and cannot touch a different environment's prefix, regardless of what its IAM role otherwise permits. The security group narrows who can even open a TCP connection to the ENI in the first place.

The Azure shape is structurally parallel: an azurerm_private_endpoint resource pointing at the target resource's private_connection_resource_id, paired with an azurerm_private_dns_zone_group to handle the privatelink.* zone association, and NSG rules on the subnet controlling which sources can reach the private endpoint's NIC. Azure's private endpoint doesn't carry an equivalent to AWS's endpoint policy document — access control instead lives in the target resource's own network rules (e.g., a Key Vault firewall or Storage account network rule set) plus the private endpoint connection approval step described below.

DNS resolution is where most PrivateLink/Private Link deployments break

The single most common failure mode in production PrivateLink and Private Link rollouts isn't a missing route or a misconfigured security group — it's DNS. Both platforms depend on redirecting the standard public hostname to a private IP, and if that redirection isn't wired up everywhere it needs to be, the client falls back to public DNS resolution, gets the public IP, and routes out through NAT or fails outright if there's no NAT path — all while looking like a working connection from the application's perspective.

On AWS, the private hosted zone created by an interface endpoint has to be associated with every VPC that needs to resolve it — including VPCs reaching the endpoint through Transit Gateway or VPC peering, which don't automatically inherit the association. A workload in a peered VPC with no explicit hosted zone association will silently resolve the AWS service's public IP and either route out over NAT (if permitted) or fail with a timeout if NAT egress has already been locked down — the worst-of-both-worlds outcome where the security team assumes traffic is private and it isn't.

On Azure, Private DNS zone virtual network links are required per-VNet in the same way, and hybrid environments add another layer: on-premises resolvers reaching Azure resources need conditional forwarding rules pointed at Azure DNS (or a DNS forwarder VM) specifically for the privatelink.* zones, or on-prem clients will resolve the public endpoint every time.

The operational lesson is to treat DNS association as a first-class part of the endpoint rollout checklist, not an afterthought — verify resolution from each consuming network segment with dig or nslookup against the actual service hostname (not the endpoint's own DNS name) before declaring an endpoint "done."

Layering egress control: endpoint policies, security groups/NSGs, and VPC/VNet-wide restrictions

None of these controls should be relied on in isolation — they answer different questions and are meant to stack. On AWS: the endpoint policy answers "which API actions against which resources," the security group on the ENI answers "which source (by security group reference or CIDR) can even open a connection," and the route table / lack of a NAT gateway answers "can this subnet reach the internet at all." Once every service dependency has an interface endpoint, it becomes possible to remove the 0.0.0.0/0 route through NAT entirely for that subnet, which turns "no route to the internet" into a structural guarantee rather than a policy statement someone has to remember to enforce.

On Azure, the equivalent stack is private endpoint network policies (which govern whether NSGs and UDRs apply to private endpoint traffic at all — they're disabled by default on the subnet), NSG rules on the subnet housing the private endpoint's NIC, and Azure Firewall with FQDN or service tags for anything that genuinely still needs internet egress.

This is defense in depth in the literal sense: a misconfigured endpoint policy that's too permissive is still constrained by the security group; a security group that's too permissive is still constrained by the fact that the subnet has no route to the internet at all. Both the AWS Well-Architected and Azure Well-Architected frameworks frame this kind of layered network control as a core reliability and security practice rather than a one-off hardening step, and it's worth revisiting each layer whenever a new service dependency is added, not just at initial rollout.

When NAT and perimeter firewalls still belong in the architecture

Not every dependency has a PrivateLink or Private Link offering — plenty of smaller SaaS vendors, public APIs, and package registries are internet-only. For those, a NAT gateway still belongs in the architecture, but it should be paired with an explicit egress firewall doing FQDN or IP allowlisting — AWS Network Firewall or Azure Firewall — rather than a NAT gateway with a security group that just permits port 443 to anywhere. A security group can't distinguish "traffic to api.stripe.com" from "traffic to an attacker's exfiltration endpoint" on the same port; an FQDN-aware firewall rule can.

There's also a cost dimension that makes "endpoint everything" the wrong default. AWS interface endpoints bill per-AZ per-hour plus a per-GB data processing charge, and Azure private endpoints have a comparable hourly-plus-data-processed model. For a handful of high-value, high-traffic service dependencies, that cost is trivial next to the security benefit. For a long tail of low-volume, rarely-called third-party APIs, provisioning a dedicated interface endpoint for each one adds operational surface (DNS associations, security groups, policies to maintain) without a proportional security win — a well-scoped NAT-plus-firewall egress path with FQDN allowlisting is often the more maintainable choice for that tail.

The practical framing: treat PrivateLink/Private Link as the default for named, high-value, frequently-used service dependencies, and treat NAT-plus-firewall as the explicitly audited exception path for everything else — not the fallback nobody looks at.

Rolling this out without breaking existing egress

Retrofitting PrivateLink or Private Link onto an existing environment with an established NAT gateway habit works best as an incremental migration rather than a cutover. Start by pulling VPC Flow Logs (or NSG flow logs on Azure) filtered to traffic through the NAT gateway, and aggregate by destination to find the handful of services accounting for most egress volume — this is almost always a short list dominated by a few AWS/Azure services and one or two SaaS integrations. Stand up interface endpoints or private endpoints for those first, confirm via flow logs or connection logs that traffic has actually shifted onto the endpoint's ENI/NIC (not just that the endpoint exists), and only then tighten route tables or remove the NAT dependency for that traffic class.

Cross-account and cross-subscription access adds a governance step that's easy to treat as a one-time Terraform apply and then forget: AWS endpoint services require the provider to maintain an allowlist of principals permitted to create a connection, and Azure Private Link Service connections require explicit approval on the provider side for each consumer's private endpoint. Both are ongoing access-review surfaces — someone needs to own periodically auditing who's connected and revoking stale connections, the same way IAM role trust policies or NSG rules get reviewed.

The endpoint policy and DNS-association checklist items throughout this article compound: each new consumer VPC or VNet, each new peered network, and each new service dependency reopens the question of whether resolution and policy are actually wired correctly, not just whether the endpoint resource exists.

What to do next

  • Pull a week of NAT gateway or NAT instance flow logs and rank destinations by byte volume — that's the priority list for the first wave of interface/private endpoints, not a guess.
  • For each endpoint created, write an explicit endpoint policy (AWS) or confirm the target resource's network ACLs (Azure) before enabling private_dns_enabled — don't ship a default full-access policy and tighten it later.
  • Test DNS resolution from every consuming subnet, including peered and Transit-Gateway-attached VPCs or cross-VNet paths, with a direct dig/nslookup against the service's real hostname — don't assume the private hosted zone or DNS zone link propagated.
  • Before removing a NAT gateway's default route, confirm via flow logs that all previously NAT-routed traffic for that subnet is now flowing through an endpoint, not silently failing.
  • Assign an owner for endpoint service allowlist and private endpoint connection approvals — treat it as a recurring access review, not a Terraform apply you run once.
