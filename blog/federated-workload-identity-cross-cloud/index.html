Federated Workload Identity: Cross-Cloud Auth Without Secrets

Cesar A. Nogueira
April 22, 2025 · 12 min read

The static credential problem in multi-cloud environments

Most multi-cloud estates still run on a foundation of standing secrets. A CI runner holds a cloud provider's access key so it can push a container image or apply Terraform. A pod holds a service account key so it can call a managed database API. A SaaS integration holds an API key so it can pull billing data into a FinOps dashboard. Each of these is a long-lived credential, minted once and left to sit — in a CI secrets store, a Kubernetes Secret, a .env file, or worse, a config file that ends up in a repository.

The problem isn't that these credentials exist — it's that they don't expire on their own. A static key or downloaded service account JSON file is valid until someone explicitly revokes it. If it leaks — through a misconfigured log, a compromised build agent, a public S3 bucket, or a careless commit — its blast radius is bounded only by how quickly the leak is detected. There is no cryptographic mechanism forcing it to stop working after an hour; detection and rotation are manual, reactive processes bolted on after the fact.

This gets worse, not better, as environments become multi-cloud. Each platform an integration touches has to issue its own long-lived credential for every other platform that needs to call into it: AWS access keys handed to a GCP-hosted CI pipeline, GCP service account keys handed to an Azure Function, GitHub Actions secrets holding credentials for three different clouds simultaneously. Every one of those credentials needs its own inventory entry, its own rotation schedule, and its own revocation runbook, and the number of pairwise trust relationships grows with the number of platforms in play. Secret sprawl isn't a hygiene footnote here — it's a structural consequence of static credentials being the default cross-cloud trust mechanism. The AWS Well-Architected security pillar, the Google Cloud Architecture Framework, and the Azure Well-Architected Framework all converge on minimizing standing credentials as a security design principle, independent of which cloud is home turf.

What federated workload identity actually changes

Federated workload identity replaces the "provision a key, store it, rotate it" model with a token-exchange model. Instead of a workload holding a secret that a relying party must also know, the workload's home platform — the CI system that's running the job, the Kubernetes cluster the pod is scheduled on, the cloud account that owns the compute — issues a short-lived, cryptographically signed token that asserts the workload's identity. That token typically takes the shape of an OIDC ID token or a SAML assertion.

The relying party — a different cloud, or a SaaS control plane — never needs to have provisioned or stored anything about that workload in advance. It only needs to trust the issuer: it fetches the issuer's published signing keys (via an OIDC discovery document and JWKS endpoint), verifies the token's signature and claims, and if everything checks out, exchanges the token for its own short-lived, scoped access credential. No shared secret is created at any point in this exchange — the whole thing rests on asymmetric cryptography and a one-time trust configuration between issuer and relying party.

The practical difference shows up in what an attacker can steal. Compromise a build log or a debug endpoint and grab a live federated token, and it's only useful for the few minutes before it expires and only for the audience it was minted for. Compromise the same surface under the static-key model and you have a credential that works indefinitely until someone notices. Federation doesn't eliminate the need for careful handling of tokens in flight, but it collapses the "leaked secret works forever" failure mode down to "leaked token works briefly, for a narrow purpose."

How the major cloud-native implementations work

The three major clouds have each built a version of this pattern, with different naming but the same underlying trust-exchange shape.

Microsoft Entra Workload ID uses federated credentials: an Entra application or managed identity is configured to trust an external OIDC issuer — a Kubernetes cluster's service account issuer, GitHub Actions' issuer, or another external IdP. At runtime, the workload presents its external OIDC token to Entra ID, which validates it against the configured issuer and subject, then exchanges it for a normal Entra access token. This works for GitHub Actions, Kubernetes workloads, and workloads running on compute platforms outside Azure entirely, all without an application secret or certificate ever being generated or stored.

Google Cloud Workload Identity Federation uses workload identity pools and providers. A pool is a container for external identities; a provider inside that pool maps claims from an external OIDC or SAML assertion into Google's attribute namespace. A GitHub Actions job, an AWS-hosted workload, or an on-prem SPIFFE-issued token can all authenticate through a provider mapping, be matched against an attribute condition, and be granted permission to impersonate a Google service account — all without downloading a service account key file.

AWS doesn't market a single unified brand for this the way Google and Microsoft do, but it has the equivalent pieces: OIDC identity providers registered in IAM for external issuers such as GitHub Actions' token service, and certificate-based options for workloads running outside AWS entirely. Different terminology, same shape: register an external issuer as trusted, define a role trust policy that checks issuer/audience/subject, and let the workload assume a role by presenting a token instead of a stored key.

Strip away the branding and all three converge on identical mechanics: trust an external issuer once via configuration, verify a signed token per request, and mint a short-lived internal credential scoped to exactly what's needed. That convergence is what makes the pattern portable across a multi-cloud estate — an engineer who understands the shape in one cloud can recognize it immediately in another.

SPIFFE/SPIRE as the portable, cross-cloud identity layer

Vendor-native federation is powerful but still fundamentally tied to each cloud's IdP. That's fine when the relying party is that cloud, but it doesn't help a workload that needs a portable identity independent of any single vendor — one that's equally valid whether the workload is running in a Kubernetes cluster on GKE, a VM on Azure, or bare metal in a colo. That's the gap SPIFFE fills.

SPIFFE defines a URI-based identity format — a SPIFFE ID, like spiffe://example.org/ns/payments/sa/checkout — and a document format for proving it: the SVID (SPIFFE Verifiable Identity Document), issued either as an X.509 certificate (X.509-SVID, usable for mTLS) or a signed JWT (JWT-SVID, usable for API calls and token exchange, which is the form that matters for cloud federation). Neither format requires the workload to ever handle a long-lived secret.

SPIRE is the reference runtime that makes this real. A SPIRE agent runs alongside the workload and attests its identity — verifying node identity, process attributes, Kubernetes pod metadata, or similar signals — before issuing an SVID over the local SPIFFE Workload API. The workload never sees a password or a static key; it just asks the local agent "who am I" and gets back a short-lived, automatically rotated identity document.

The part that matters most for cross-cloud architectures is trust domain federation: a SPIRE deployment running in one cloud can be configured to validate SVIDs issued by a SPIRE deployment running in a different cloud, without either side needing to be the other's native IdP. This turns SPIFFE into a neutral trust layer that sits above any single vendor's workload identity system — the tool platform teams reach for when workloads need to carry one consistent identity across clouds, on-prem infrastructure, and anything vendor-specific federation doesn't reach.

Configuring federation: a concrete cross-cloud example

The clearest way to see the pattern is to wire up GitHub Actions to GCP, since it only takes a few resources on each side.

On the GitHub Actions side, the workflow requests an OIDC token implicitly — permission just needs to be granted:

name: deploy
on:
  push:
    branches: [main]

permissions:
  id-token: write
  contents: read

jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - id: auth
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: projects/123456789/locations/global/workloadIdentityPools/gh-pool/providers/gh-provider
          service_account: deployer@my-project.iam.gserviceaccount.com

On the GCP side, the pool and provider that this workflow references need to be created and scoped tightly — matching the workflow trigger above, that means restricting by both repository and branch:

gcloud iam workload-identity-pools create "gh-pool" \
  --location="global" \
  --display-name="GitHub Actions pool"

gcloud iam workload-identity-pools providers create-oidc "gh-provider" \
  --location="global" \
  --workload-identity-pool="gh-pool" \
  --issuer-uri="https://token.actions.githubusercontent.com" \
  --attribute-mapping="google.subject=assertion.sub,attribute.repository=assertion.repository,attribute.ref=assertion.ref" \
  --attribute-condition="assertion.repository=='my-org/my-repo' && assertion.ref=='refs/heads/main'"

gcloud iam service-accounts add-iam-policy-binding \
  deployer@my-project.iam.gserviceaccount.com \
  --role="roles/iam.workloadIdentityUser" \
  --member="principalSet://iam.googleapis.com/projects/123456789/locations/global/workloadIdentityPools/gh-pool/attribute.repository/my-org/my-repo"

Notice the three fields that recur across every implementation of this pattern: issuer (token.actions.githubusercontent.com), audience (the workload identity pool provider's own resource name under iam.googleapis.com, set automatically as the token's aud claim by the google-github-actions/auth action — distinct from the sts.googleapis.com endpoint the token is later exchanged at), and subject/attribute conditions (the repository and ref claims, restricted to my-org/my-repo on refs/heads/main). Entra federated credentials and AWS OIDC provider trust policies ask for the exact same three things, just in different configuration syntax. Full details of the attribute mapping and condition syntax are in Google's Workload Identity Federation documentation; the equivalent Entra federated credential setup — issuer, subject, audience — is documented in Microsoft's workload identity federation concepts.

What has to be locked down here is exactly those three fields. Skip the attribute-condition entirely and the IAM binding's principalSet becomes the only thing standing between the org's other repositories and this identity — the condition is a defense-in-depth layer on top of that binding, not a substitute for it. Leave the audience unrestricted and a token minted for an unrelated purpose could be replayed against this provider. Drop the ref clause and condition on repository alone, and a workflow on a feature branch gets the same trust as one on main. None of this is exotic — it's the same least-privilege discipline the well-architected frameworks from AWS, Google, and Azure all call out — but federation makes it a configuration-time decision instead of an operational afterthought.

Chaining federation across cloud boundaries

Real multi-cloud architectures rarely stop at a single hop. A representative scenario: a pod running in a Kubernetes cluster on one cloud needs to reach a resource in a second cloud, or a third-party SaaS control plane.

In a SPIFFE-enabled cluster, the pod first requests a JWT-SVID from the local SPIRE agent over the Workload API — no external call yet, just local attestation. That JWT-SVID, scoped to an audience matching the target cloud's workload identity provider, is then presented to that cloud's STS-equivalent endpoint (GCP's sts.googleapis.com token exchange, or Entra's token endpoint), which validates it against the SPIRE server's published JWKS and mints a short-lived native credential. That native credential is what actually calls the target resource.

This is worth distinguishing from direct two-party federation, where cloud A's workload identity provider trusts cloud B's native IdP directly (GitHub's issuer trusted by GCP, in the earlier example). Chaining through SPIFFE instead makes SPIRE the neutral intermediary trust domain: the workload's identity isn't tied to "I happen to run on cloud B's compute" but to a portable SPIFFE ID that any cloud's federation config can be pointed at. That's the difference between rebuilding trust relationships every time a workload moves and configuring it once against a stable identity.

The failure mode to watch for when chaining is confused deputy: a token minted for audience X being replayed against relying party Y because nobody re-checked the audience at the second hop. Every exchange point in the chain — the SPIRE-to-cloud exchange and the cloud-to-SaaS exchange, if there is one — needs its own audience and scope validation. A token that's valid for "call cloud B's STS" should not be implicitly trusted as valid for "call this SaaS API," even if it technically satisfies signature verification. Each hop needs its own explicit trust configuration, not inherited trust from the hop before it.

Operational guardrails: what federation doesn't solve automatically

Federated identity removes stored secrets, but it introduces its own operational surface that needs active management.

Token lifetime is a tuning problem, not a solved one. Too long and a leaked token has more room to do damage; too short and the exchange endpoints (STS, Entra's token endpoint, SPIRE server) take on re-issuance load that can become its own availability concern under high request volume. Most implementations default to short-lived tokens by design, precisely because the whole point of the pattern is bounding exposure — but that default should be checked against actual workload call patterns rather than assumed.

Trust anchor rotation replaces key rotation as the thing that must not silently break. JWKS endpoints rotate their signing keys periodically, and both sides of a federation relationship need to handle that rollover — the issuer publishing new keys with adequate overlap, the relying party refreshing its cached JWKS rather than pinning a single key indefinitely. Get this wrong and instead of a slow key-leak problem, there's a sudden mass-authentication-failure problem.

Audit and observability shift where the useful signal lives. With static keys, security teams could reason about a credential inventory: this key exists, was created on this date, is used by this system. With federated tokens, there's no equivalent standing inventory — the meaningful audit trail lives in the issuing platform's logs (who requested a token, for what subject) and the exchange endpoint's logs (which tokens were exchanged, for what scope). Logging and alerting need to be built around those two points, not around a static secrets store that no longer exists.

Finally, and easy to overlook: federation solves the "how do we avoid a shared secret" problem, not the "how much access should this workload have" problem. A federated token that gets exchanged for an over-privileged role is exactly as dangerous as an over-privileged static key — the exchange mechanism doesn't add discipline to the resulting permission set. Least-privilege scoping on the far side of the exchange remains a separate, mandatory design decision.

Migrating from static keys to federated identity

Moving an existing multi-cloud environment onto this pattern doesn't require — and shouldn't attempt — a big-bang cutover. Start with an inventory: which long-lived keys currently cross cloud or service boundaries, and which of those carry the highest blast radius if leaked. CI/CD pipelines are usually the highest-value starting point, since they combine broad permissions (deploy access, infra changes) with public-adjacent exposure (build logs, third-party actions, dependency supply chains).

For each candidate, the safe sequencing is to stand up the federation configuration — the workload identity pool/provider, the Entra federated credential, or the IAM OIDC provider trust policy — alongside the existing static key, not in place of it. Run both paths in parallel, confirm the federated path works correctly against real production traffic and permissions, and only then revoke the static credential. Because every major vendor supports both models simultaneously, there's no forcing function requiring an all-or-nothing switch — a mixed environment where some integrations still use static keys while higher-priority ones have moved to federation is a normal, acceptable intermediate state, not a half-finished migration.

What to do next

  • Pull a list of every long-lived credential your CI systems and cross-cloud integrations currently hold, and rank them by blast radius, not by age.
  • Pick the single highest-risk integration — usually a CI/CD pipeline with deploy or infra permissions — and stand up workload identity federation for it first, following the issuer/audience/subject pattern shown above.
  • Verify the attribute or subject condition is scoped to the exact repository, branch, or service account you intend, not a broad wildcard, before revoking anything.
  • If workloads span more than one cloud plus non-cloud infrastructure, evaluate a SPIRE proof-of-concept for a single trust domain before attempting cross-domain federation.
  • Only after the federated path has run against real traffic without incident should the corresponding static key be revoked.
