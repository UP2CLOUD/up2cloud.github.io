Landing Zone Design: Governance as Code for Multi-Account AWS

Cesar A. Nogueira
April 22, 2025 · 12 min read

The revised body — I only changed the one sentence in Section 2 that misattributed governance content to Azure's Well-Architected Framework:

1. Where single-account and ad hoc multi-account setups break down

Most organizations don't design their way into an AWS account structure — they accumulate one. It starts with a single account, everything tagged by team or project, and IAM permissions granted as people ask for them. Eventually someone notices that a developer with access to the staging S3 bucket can also touch production billing alarms, or that a compromised credential in one workload has a blast radius covering every other workload in the company. The fix is usually "let's create separate accounts," which solves the isolation problem for about a quarter — until account creation itself becomes the bottleneck.

At that point, a second failure mode appears: accounts get created on request, each one hand-built by whoever picked up the ticket. One account gets CloudTrail enabled from day one; another doesn't, because the person provisioning it forgot, or didn't know it was expected. One account gets a restrictive IAM boundary; another gets AdministratorAccess because the requester was in a hurry and nobody pushed back. Six months later, a security review has to look at every single account individually because there's no guarantee any two of them were built the same way.

Both patterns — "one big account with tags" and "accounts created on request" — fail at the same root cause: governance lives in a person's memory, a wiki page, or a checklist, not in a system that enforces it. A checklist doesn't stop a misconfigured account from going live; it just documents what should have happened, after the fact. Controls applied once at account creation don't survive contact with time — teams add resources, roles, and one-off exceptions, and none of that drifts back toward the original baseline unless something is actively pulling it there. AWS Organizations treats AWS accounts as "natural boundaries for permission, security, costs, and workloads," and recommends a multi-account environment as a best practice — but the boundary only holds value if what happens inside each boundary is consistent and enforced, not improvised per account.

2. A landing zone is a system, not a setup checklist

The architecture patterns below are illustrated with AWS primitives — organizational units, service control policies, Control Tower — because they map to concrete, testable artifacts. The same structural argument applies on other clouds through different primitives: GCP's landing zone guidance and its broader architecture framework describe the equivalent resource-hierarchy and organization-policy approach, and Azure's Well-Architected Framework makes the same case at the workload level — its cost optimization, security, and operational excellence pillars all assume a consistent, enforced baseline rather than per-workload improvisation. What follows is one concrete implementation of a cloud-agnostic principle, not an AWS-only concern.

A landing zone is the codified combination of account structure, identity federation, network baseline, and policy enforcement that every new account inherits automatically, without a human re-deciding it each time. It is not a runbook that a cloud engineer follows during account creation — it's the set of policy artifacts, version-controlled and applied programmatically, that make correct configuration the only configuration a new account can have.

This is the thesis in concrete terms: durable governance requires organizational units (OUs), service control policies (SCPs), and drift-detecting controls to exist as code under version control — reviewable in a pull request, testable, and reproducible — rather than as steps someone performs once and hopes stick. AWS's own framing draws the same distinction: AWS Control Tower exists specifically because "if you are hosting more than a handful of accounts, it's beneficial to have an orchestration layer that facilitates account deployment and account governance," and it applies guardrails to keep organizations and accounts from drift — explicitly defined as "divergence from best practices."

The distinction between one-time setup and codified policy is the difference between a control that decays and a control that self-enforces. A checklist item ("enable CloudTrail on new accounts") depends on someone remembering to do it, every time, forever. An SCP that denies cloudtrail:StopLogging and cloudtrail:DeleteTrail at the OU level makes the outcome structural — it doesn't matter who created the account or whether they read the checklist. The same logic applies across identity federation, network baselines, and logging: each one is either an artifact that gets applied automatically to every account in scope, or it's a hope.

3. Designing the OU hierarchy: where account boundaries actually go

OU boundaries should follow risk and blast-radius logic, not organizational convenience. Three axes matter in practice: environment (production vs. non-production), workload sensitivity (regulated data, public-facing services, internal tooling), and team or business unit ownership. The mistake most teams make is designing OUs around whichever axis is easiest to explain in a slide — usually the org chart — rather than the axis that actually determines which policies apply.

A workable starting hierarchy looks like this:

Root
├── Security          (log archive, audit/read-only account)
├── Infrastructure     (shared networking, DNS, tooling accounts)
├── Workloads
│   ├── Prod
│   └── NonProd
└── Sandbox            (unrestricted experimentation, tightly capped spend)

The reason this shape works is that it lets policy inheritance do the enforcement instead of relying on per-account exceptions. An SCP attached to Workloads/Prod — for example, requiring MFA for any IAM changes, or denying deletion of KMS keys — applies to every account placed under it, present and future, with zero additional configuration. Compare that to a flat account list where the same policy has to be attached individually to each account and re-attached every time a new one is created; that's exactly the "someone has to remember" failure mode the landing zone is meant to eliminate.

Deeper nesting buys finer-grained policy control, but it comes at a real cost: every additional OU layer is another place SCPs can silently diverge, another thing a new engineer has to understand before they can reason about what's allowed where. The practical recommendation is to start shallow — the five OUs above are enough for most organizations at launch — and only split further when a specific SCP requirement demands it (for example, splitting Workloads/Prod into a PCI-scoped sub-OU once a payments workload actually needs stricter controls than the rest of production). Don't pre-build OU depth for hypothetical future policies; add nesting when a real, distinct control need shows up, not before.

4. Guardrails as policy: enforcing SCPs instead of asking nicely

Preventive and detective controls do different jobs and both are necessary. SCPs are preventive: they set the maximum permissions available in an account, regardless of what IAM policies inside that account grant — even a full-admin role in a member account can't take an action an SCP denies at the OU level. Detective controls, typically AWS Config rules or Security Hub findings, catch what SCPs structurally can't: third-party actions taken outside the API surface SCPs cover, resource configurations that become non-compliant after the fact, or cross-service interactions that no single SCP statement anticipated. A landing zone needs both because SCPs stop the bad API call, but they can't inspect the state of a resource that already exists.

A concrete example: denying an account from leaving the organization and restricting which regions can be used. Here's the SCP itself:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyLeaveOrganization",
      "Effect": "Deny",
      "Action": "organizations:LeaveOrganization",
      "Resource": "*"
    },
    {
      "Sid": "DenyOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "organizations:*",
        "route53:*",
        "cloudfront:*",
        "support:*",
        "sts:*",
        "kms:*",
        "waf:*",
        "wafv2:*",
        "shield:*",
        "config:*",
        "ce:*",
        "budgets:*",
        "trustedadvisor:*",
        "health:*",
        "account:*",
        "tax:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": ["us-east-1", "eu-west-1"]
        }
      }
    }
  ]
}

Treat this NotAction list as a starting point, not a finished policy. It covers the global/non-regional services most organizations rely on, but the exact set depends on which services an organization actually uses — omitting a service that's genuinely global for your workloads (a third-party marketplace integration, a less common global endpoint) will silently break legitimate cross-region calls to it once this reaches production. Audit actual API usage — CloudTrail event history is a reasonable source — before attaching this to any OU that carries production traffic.

And attached in Terraform at the OU level, not the account level:

resource "aws_organizations_policy" "region_and_org_guardrail" {
  name    = "deny-leave-org-and-region-restriction"
  type    = "SERVICE_CONTROL_POLICY"
  content = file("${path.module}/policies/region-and-org-guardrail.json")
}

resource "aws_organizations_policy_attachment" "workloads_prod" {
  policy_id = aws_organizations_policy.region_and_org_guardrail.id
  target_id = aws_organizations_organizational_unit.workloads_prod.id
}

Attaching at the OU means every account provisioned into Workloads/Prod — today or in a year — inherits the restriction automatically, with no per-account step.

The other half of this thesis matters just as much: don't block teams with organization-wide blanket denies where the risk doesn't actually live everywhere. A rule against launching oversized, expensive EC2 instance types belongs on Sandbox, where unmonitored spend is the actual risk, not on Workloads/Prod, where a legitimate capacity-planning decision would get blocked for no security reason. SCPs scoped too broadly are the fastest way to train engineers to treat governance as an obstacle to route around rather than infrastructure to build on.

5. Provisioning accounts without re-auditing each one by hand

The account vending pattern replaces manual account setup with a pipeline — a Terraform module, AWS Control Tower's Account Factory, or custom automation — that creates a new account and applies its baseline configuration atomically, as one operation rather than a sequence of manual steps someone might skip. AWS Organizations already supports this natively: accounts can be created programmatically via the CLI, SDKs, or API, with baseline resources and permissions provisioned centrally using tools like CloudFormation StackSets, as described in the AWS Organizations documentation.

The key point is that if provisioning is a codified module invocation, every account starts compliant by construction — there is no "new account" state that predates the baseline, because the baseline is part of what "new account" means. Manual review shifts from being the default gate every account has to pass through, to being exception handling for the rare case where an account genuinely needs to deviate from the standard shape.

A typical vended baseline includes: automatic OU placement based on account purpose (so SCP inheritance takes effect immediately), CloudTrail and Config delivery configured to write into a central log-archive account rather than staying local, the org's default deny-all SCP applied by inheritance before any workload resources are created, and a break-glass IAM role for emergency access that bypasses normal federation without bypassing logging. None of this requires the account requester to know anything about security configuration — it's a property of the pipeline, not of their diligence.

6. Catching drift before it becomes an incident

SCPs are not sufficient on their own, and treating them as sufficient is a common mistake. They prevent new violations going forward, but they do nothing about resources that already existed before a policy was tightened, or that were created through a legitimately granted exception that was never revisited. A public S3 bucket created before a bucket-policy SCP was written stays public; the SCP only stops the next one.

This is where detective, continuously-evaluating controls close the gap. AWS Config conformance packs bundle a set of Config rules and remediation actions that continuously check accounts against a baseline — flagging or auto-remediating things like unencrypted volumes, security groups open to 0.0.0.0/0, or IAM users without MFA — regardless of when the offending resource was created. Tools like Open Policy Agent or Cloud Custodian serve a similar function outside the AWS-native tooling, evaluating live resource state against declarative policy and either alerting or acting.

This is the mechanism that actually keeps the thesis true over time. A landing zone audited once at launch is accurate for exactly as long as nothing changes — which, in practice, is measured in days. Drift detection is what turns "we designed this to be compliant" into "we know, continuously, whether it still is." Without it, a landing zone degrades into the same wiki-and-hope governance model it was built to replace, just with better paperwork at the start.

7. Migrating from a single account without stalling delivery

Migrating an existing single-account (or ungoverned multi-account) environment into a landing zone works best sequenced, not big-banged. Stand up the OU structure, baseline SCPs, and centralized logging first, entirely independent of any workload migration — this is infrastructure that can be built and tested without touching a single running service. Only once that baseline exists should workload accounts move or get recreated into it, one at a time or in small batches, rather than as a single cutover weekend.

The real obstacle here isn't technical, it's behavioral: teams that hit a guardrail that blocks their work will either escalate for an exception or quietly find a way around it, and either outcome undermines the landing zone if it happens repeatedly. The mitigation is to scope initial SCPs conservatively — deny only the highest-risk, clearest-cut actions (leaving the organization, disabling logging, deleting audit trails) — and expand the guardrail set over time as teams adapt and as false-positive friction gets identified and resolved. A landing zone that ships maximally strict on day one generates enough exception requests to bury the team maintaining it; one that ships with a tight, well-justified initial set earns the credibility to add more later.

Track the migration itself as a backlog — which accounts are on the new baseline, which are still pending, which have open exceptions — the same way any other engineering work gets tracked, rather than relying on someone's memory of "we're mostly done." A migration that isn't itself tracked in a system tends to stall at "mostly migrated" indefinitely, which just recreates the original ungoverned-sprawl problem for the accounts that never made it across.

8. Anti-patterns that quietly undo a landing zone

A landing zone rarely fails all at once; it erodes through small, individually reasonable decisions that never get reconciled back into the policy source. The most common one is the manually granted SCP exception: someone needs a one-off carve-out to unblock a deadline, an admin attaches a narrower policy or detaches the offending statement directly in the AWS console, and it's never codified back into Terraform. Six months later nobody remembers why that account is different, and the next audit has to treat it as a special case rather than as policy.

A second anti-pattern is OU structure that mirrors the org chart instead of risk and environment boundaries — an OU per business unit, each with its own copy of roughly the same SCPs. This looks organized but forces policy duplication: a change to the logging baseline now has to be applied N times instead of once, and the N copies inevitably diverge. OU boundaries should answer "does this group of accounts need different policy," not "does this group of accounts report to a different VP."

The third is treating account-vending automation as a migration tool rather than the permanent way new accounts get created. Once the initial batch of accounts is migrated, it's tempting to let the automation lapse and go back to ad hoc account creation for the next request that doesn't quite fit the template. That's the same failure mode from section 1, reintroduced through the back door — and it guarantees a second migration project a year or two later.

What to do next

Start by writing the OU hierarchy and a minimal SCP set (deny-leave-organization, region restriction, deny-disable-logging) as Terraform under version control. Before applying the region-restriction SCP anywhere near production, audit which global services your accounts actually call and confirm the NotAction exemption list covers them — then apply the policy to a test organization first. Pick one account-vending mechanism — AWS Control Tower's Account Factory if a managed orchestration layer fits, or a custom Terraform module using AWS Organizations APIs if more control is needed — and commit to it as the only path for new accounts going forward. Add one AWS Config conformance pack scoped to the baseline you've defined, and treat every finding it produces as a signal to either fix the resource or codify the exception, never to ignore. Finally, build the migration backlog before migrating anything, so the state of "who's on the new baseline" is a query, not a guess.
