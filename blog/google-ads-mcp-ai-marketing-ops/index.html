Google Ads MCP: AI Agents for Marketing Ops

September 2, 2026 · 6 min read

Google publishes an official Google Ads MCP server — a Model Context Protocol endpoint that lets an AI agent query a Google Ads account directly. We wired it into our own toolchain here at UP2CLOUD to support keyword research and campaign auditing, and the design is worth calling out: it's read-only by construction, not by policy.

What it actually exposes

The server ships three tools, all read-only:

  • list_accessible_customers — the customer IDs and account names an authenticated user can see
  • search — arbitrary GAQL queries against metrics, budgets, and campaign status
  • get_resource_metadata — schema metadata for resource types like campaigns and ad groups

There is no mutation path. An agent connected to this server cannot pause a campaign, change a bid, or create an asset — it can only read what GAQL exposes. That's a deliberate constraint, and it's the right one for anything touching ad spend.

Why read-only-by-design matters

The same governance instinct we apply to infrastructure — least privilege, no standing write access, everything auditable — applies to marketing spend once an AI agent is in the loop. A misconfigured write-capable agent against a live Ads account is a budget incident waiting to happen, the same category of risk as an over-permissioned service account in a cloud project. Google shipping this as read-only means the blast radius of a bad prompt or a runaway loop is bounded to wasted API quota, not wasted ad spend.

That constraint doesn't make the tool less useful — diagnosis and research don't need write access. Every legitimate use case below is read-only by nature.

Setup, in short

It runs locally via pipx, or as a container on Cloud Run for shared/team access. Locally, it's one entry in an MCP client config:

{
  "mcpServers": {
    "google-ads-mcp": {
      "command": "pipx",
      "args": ["run", "--spec",
        "git+https://github.com/googleads/google-ads-mcp.git",
        "google-ads-mcp"],
      "env": {
        "GOOGLE_PROJECT_ID": "${GOOGLE_PROJECT_ID}",
        "GOOGLE_ADS_DEVELOPER_TOKEN": "${GOOGLE_ADS_DEVELOPER_TOKEN}",
        "GOOGLE_ADS_MCP_OAUTH_CLIENT_ID": "${GOOGLE_ADS_MCP_OAUTH_CLIENT_ID}",
        "GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET": "${GOOGLE_ADS_MCP_OAUTH_CLIENT_SECRET}"
      }
    }
  }
}

Credentials come from environment variables at runtime, never hardcoded in the config file — the same rule we apply to every secret in this codebase, from the chatbot's Groq key to the newsletter's Brevo key. You'll need a Google Ads developer token, a Google Cloud project with the Ads API enabled, and an OAuth client. First connection triggers the standard OAuth consent flow in the browser.

What we use it for

  • Keyword research — querying keyword_view and search_term_view for volume and CPC on terms relevant to Platform Engineering, FinOps, and DevOps consulting, to inform both blog topics and ad copy.
  • Campaign auditing — pulling Quality Score, CTR, and spend by campaign before deciding where budget goes, instead of eyeballing the Ads UI.
  • Landing page alignment — checking which search terms actually convert against which landing sections exist on the site, to close content gaps.

Any decision that follows — pausing a campaign, raising a bid, shipping new ad copy — still happens by hand in the Google Ads UI. The MCP server informs that decision; it doesn't make it.

Where this fits with organic SEO

Paid and organic aren't separate workstreams here. The keyword data this server surfaces feeds the same meta descriptions, headings, and structured data (BlogPosting, Organization, LocalBusiness) that drive this site's organic ranking — a single research pass covers both. If a term has strong CPC and search volume, it's a candidate for a landing section; if it's a long-tail question with low competition, it's a candidate for a blog post like this one.

Conclusion

Read-only MCP servers are becoming the sane default for AI agents that touch anything with financial consequences — ad accounts, billing APIs, production databases. Google Ads MCP is a clean example of that pattern done right: real diagnostic power, zero write surface. If your team is letting an AI agent anywhere near ad spend, read-only should be the starting posture, not an afterthought.
