Cross-Cloud Workload Identity: OIDC, Token Exchange, and SPIFFE

Cesar A. Nogueira
April 22, 2025 · 8 min read

Why Static Credentials Break Down Across Clouds

The moment a workload in one cloud needs to call an API in another — an AWS Lambda reading from BigQuery, an Azure Function writing to S3 — the default answer has historically been a static credential: an exported AWS access key, a Google service account JSON key, or a client secret stuffed into a secret manager and mounted at runtime. It works, and that is precisely the problem. It works well enough to spread.

The failure modes are familiar to anyone who has run a credential hygiene review:

  • Key sprawl. Each cross-cloud integration mints at least one long-lived credential. They accumulate across environments, teams, and forgotten proof-of-concepts, and nobody can say with confidence which ones are still needed.
  • Rotation toil. Rotating a key that is baked into a deployment pipeline, a Helm value, and a third-party SaaS simultaneously is a coordination exercise, so it gets deferred — sometimes indefinitely.
  • Leakage. Static keys end up in CI logs, Terraform state, container images, and accidentally committed repositories. A leaked key is valid until someone notices and revokes it.
  • Audit gaps. A static key used from an unexpected network location or at an unusual hour is hard to attribute, because the key itself carries no information about which workload presented it.

The architectural alternative is identity federation: instead of storing a secret, the workload presents a short-lived, attestable identity — issued by its home platform — and exchanges it at call time for scoped access in the target cloud. Nothing persistent exists to steal. This is not a niche concern: identity and access management is a first-class design area in the AWS Well-Architected guidance, the Google Cloud Well-Architected Framework, and the Azure Well-Architected Framework. All three providers treat identity as a foundational architectural concern, which is a strong signal that cross-cloud identity deserves the same rigor as network design.

The Three Building Blocks: OIDC, RFC 8693, and SPIFFE

Three open standards do most of the heavy lifting.

OIDC is the assertion layer. OpenID Connect Core 1.0 defines the ID token: a signed JWT carrying claims about an authenticated identity. Although designed for end-user authentication, the same mechanism now underpins workload identity everywhere — AWS issues OIDC tokens to pods via IAM Roles for Service Accounts (IRSA), Azure issues them to workloads via workload identity federation on app registrations or user-assigned managed identities with tokens issued by Microsoft Entra, and Google Cloud both issues and accepts OIDC tokens through workload identity federation. The important property is that the token is attestable: the receiving side can verify the issuer's signature against published JWKS keys and inspect claims like the subject and audience.

RFC 8693 is the brokering layer. OAuth 2.0 Token Exchange defines how a Security Token Service trades one token for another — different audience, different scope, different issuer — including impersonation and delegation semantics. This is the primitive that makes cross-cloud exchange possible: you present a token your home cloud issued, and the target cloud's STS returns a native access token. The flow is an RFC 8693 token exchange.

SPIFFE is the portability layer. SPIFFE defines a workload identity standard: a SPIFFE ID (a URI like spiffe://example.org/ns/payments/sa/api), a verifiable identity document (SVID) in X.509 or JWT form, a Workload API for fetching SVIDs, and a federation model for trust between domains. SPIRE is the reference implementation. Where provider-native federation is anchored to a specific cloud pair, a SPIFFE ID is cloud-agnostic by construction.

The decision framing:

| Concern | Provider-native federation | SPIFFE/SPIRE | |---|---|---| | Typical use | Cloud A workload calling Cloud B's APIs | Symmetric service-to-service trust across clouds | | Infrastructure to run | None (configuration only) | SPIRE servers and agents per trust domain | | Identity format | Provider-issued OIDC token | Portable SPIFFE ID / SVID | | Directionality | Asymmetric, configured per cloud pair | Uniform, mesh-like |

Pattern 1: Provider-Native Federation (AWS to Google Cloud)

The canonical flow: an AWS workload assumes an IAM role, obtains credentials attesting to that role, and exchanges them via Google Cloud Workload Identity Federation for a short-lived Google access token. No service account key is ever created.

On the Google Cloud side, you create a workload identity pool and an AWS provider within it. The provider configuration pins which AWS account(s) may federate, and an attribute condition restricts which IAM roles are acceptable:

{
  "attributeCondition": "attribute.aws_role.startsWith(\"arn:aws:sts::123456789012:assumed-role/payments-api/\")",
  "attributeMapping": {
    "google.subject": "assertion.arn",
    "attribute.aws_role": "assertion.arn.extract('assumed-role/{role}/')"
  }
}

You then grant a Google service account the roles/iam.workloadIdentityUser role, with the principal restricted to the federated identity — for example, principal://iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/aws-pool/subject/arn:aws:sts::123456789012:assumed-role/payments-api/api.

At runtime, the exchange against Google Cloud's STS is a textbook RFC 8693 token exchange:

curl -s -X POST https://sts.googleapis.com/v1/token \
  -H "Content-Type: application/x-www-form-urlencoded" \
  -d "grant_type=urn:ietf:params:oauth:grant-type:token-exchange" \
  -d "audience=//iam.googleapis.com/projects/PROJECT_NUMBER/locations/global/workloadIdentityPools/aws-pool/providers/aws-provider" \
  -d "scope=https://www.googleapis.com/auth/cloud-platform" \
  -d "requested_token_type=urn:ietf:params:oauth:token-type:access_token" \
  -d "subject_token_type=urn:ietf:params:aws:token-type:aws4_request" \
  -d "subject_token=${AWS_SIGNED_REQUEST}"

The response is a short-lived Google access token scoped to whatever the impersonated service account can do. In practice the Google Cloud client libraries perform this dance automatically given a credential configuration file, so application code never touches it.

The mirror-image patterns share the same shape: Azure-to-AWS works by registering Azure AD as an OIDC identity provider in IAM and calling AssumeRoleWithWebIdentity with an Azure-issued token; AWS-to-Azure uses a federated identity credential on a managed identity or app registration that trusts an EKS cluster's OIDC endpoint.

Pattern 2: Portable Identity with SPIFFE and SPIRE

Provider-native federation answers "how does a workload in cloud A call cloud B's control plane?" SPIFFE answers a different question: "how do two services authenticate each other regardless of where either runs?"

A typical multi-cloud SPIRE deployment runs one SPIRE server per trust domain (often one per cloud or per environment), with SPIRE agents on each node. Node attestation uses cloud-specific attestors — aws_iid, azure_msi, and gcp_iit — so an agent proves which instance, VM, or GCE node it runs on using the platform's own identity document. Workload attestation then uses Kubernetes selectors (namespace, service account, pod labels) or Unix selectors to identify individual workloads.

To create a registration entry, you can use the spire-server entry create command with the following flags:

spire-server entry create \
  -spiffeID spiffe://example.org/ns/payments/sa/api \
  -parentID spiffe://example.org/spire/agent/k8s_psat/prod-cluster/node-1 \
  -selector k8s:ns:payments \
  -selector k8s:sa:api

The ID spiffe://example.org/ns/payments/sa/api is stable whether the pod runs in EKS, AKS, or GKE — that is the entire point. A workload fetches a JWT-SVID from the local SPIFFE Workload API (a Unix socket exposed by the node agent) and presents it to a peer service in another cloud. The peer validates the JWT signature against the trust bundle, which it obtains either from a locally running agent or directly from the remote SPIRE server's bundle endpoint when SPIFFE federation is configured between the two trust domains.

For calling provider APIs, SVIDs compose with the RFC 8693 pattern: a JWT-SVID can itself be the subject token in a token exchange, yielding a cloud-native access token.

Choosing Between Provider-Native and SPIFFE-Based Identity

The decision hinges on three axes:

  1. Directionality. If the pattern is "workloads in cloud A call cloud B's APIs," provider-native federation is the direct fit — zero infrastructure, and the trust configuration lives next to your IAM code. If the pattern is mutual, mesh-style authentication between services spread across clouds, SPIFFE's uniform identity wins; modeling pairwise service trust with per-cloud-pair federation configuration does not scale.
  2. Operational appetite. SPIRE is a control plane you run, secure, upgrade, and monitor. Provider-native federation is configuration only. Be honest about which your platform team can operate well.
  3. Existing investment. If you already run a service mesh with SPIFFE integration (Envoy-based meshes commonly do), incremental adoption is cheap. If not, standing up SPIRE solely for one cross-cloud API call is over-engineering.

These compose rather than compete. A common and sensible end state is provider-native federation for cloud API access (control-plane calls, managed service access) and SPIFFE for data-plane service-to-service identity. A pragmatic migration path: eliminate the highest-risk static keys first with provider-native federation — that is usually a configuration change, not a re-architecture — then introduce SPIFFE where portable identity genuinely pays off.

Operational Guardrails: Trust Configuration as Code

Federation replaces stored secrets with trust relationships, and those relationships become your new high-value configuration surface. Treat them accordingly:

  • Trust config is code. Identity pools, OIDC provider registrations, IAM trust policies, and SPIRE registration entries should live in version-controlled Terraform or equivalent, reviewed with the same rigor as network policy. A one-line change to an attribute condition can widen who may federate.
  • Scope everything tightly. Restrict audiences on issued tokens, write attribute conditions that pin specific roles or subjects, and bind least-privilege roles on the receiving side. A federation endpoint that accepts "any role in account X" is a lateral-movement gift.
  • Observe the exchange. Log token exchange events and alert on anomalies: unexpected subject claims, exchanges from unregistered workloads, spikes in exchange volume, or federation attempts against pools that should be idle. AWS CloudTrail, Azure Monitor, and Google Cloud Audit Logs all capture these events.
  • Plan for revocation. Short token lifetimes are the default posture, but you also need a tested procedure for severing a trust relationship mid-incident — disabling a provider, deleting a pool, or removing a SPIRE registration entry — and confirming that in-flight tokens expire quickly.

What to Do Next

Start with an inventory, not an implementation. Enumerate every long-lived credential that crosses a cloud boundary: exported access keys in secret managers, service account JSON keys, client secrets in pipeline variables. Rank them by blast radius — what could an attacker reach with each one? The top of that list is your migration queue.

For each credential, ask which pattern fits: if it exists so a workload can call another cloud's APIs, replace it with provider-native federation (a trust configuration change, no new infrastructure). If your real problem is symmetric service-to-service authentication across clouds, pilot SPIRE in one trust domain pair and federate it. Either way, you are building on the same published standards — OIDC for assertion, RFC 8693 for exchange, SPIFFE for portability — that the providers themselves implement. The choice is not standards versus vendors; it is which operational model fits your platform. Replace credentials incrementally, measure the shrinking secret inventory, and let identity become the perimeter you actually control.
