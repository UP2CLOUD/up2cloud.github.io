Well-Architected Across AWS, Azure and GCP: Reconciling the Rubrics

Cesar A. Nogueira
April 22, 2025 · 11 min read

Why "well-architected" isn't one standard

Ask a platform engineer running review cycles across AWS and Azure whether they follow "the well-architected framework," and the phrasing already contains the mistake. There isn't one. AWS and Microsoft each publish a framework under a nearly identical name, and both borrow the same underlying vocabulary — reliability, security, cost, performance, operations — but the resemblance stops at the pillar names. Google Cloud publishes a comparable framework too, but it's the outlier in naming as well as mechanics: Google deliberately avoids "well-architected" branding, calling its version the Google Cloud Architecture Framework instead — a small packaging choice that turns out to be a preview of how little these three vendors agree on once you look past the shared vocabulary. A team that treats any of these as interchangeable checklists, or worse, assumes a clean improvement plan from one provider proves anything about a workload's posture on another, is comparing outputs from differently shaped instruments.

The thesis worth sitting with: AWS and Azure genuinely agree on the spirit of the review. Both explicitly frame it as a structured conversation about trade-offs, not a pass/fail audit. AWS says this outright — the review process is "a constructive conversation about architectural decisions, and is not an audit mechanism," per the AWS Well-Architected Framework. Azure doesn't use identical language, but its packaging — "quality-driven tenets, architectural decision points, and review tools," per Microsoft's framework overview — implies the same non-punitive intent. Where they diverge is packaging and mechanics: AWS ships a principles document with a companion measurement tool alongside it; Azure leads with a pillar matrix and a browser-based assessment as the primary artifact. This article is about that divergence in mechanics — not a ranking of which vendor does it better.

AWS: a principles document paired with a measurement tool

The AWS Well-Architected Framework organizes around six pillars — operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability. Each pillar is a set of design principles and foundational questions, not a rubric with point values. The framework text is explicit that its purpose is to help you "understand the pros and cons of decisions you make while building systems on AWS" — the artifact is a way of thinking about trade-offs, structured as questions like "how do you manage service quotas and constraints" or "how do you evaluate new services," not a scorecard with pass thresholds.

The companion is the AWS Well-Architected Tool, which is where the framework's questions become data. You define a workload (a logical unit of components delivering business value), associate one or more lenses (AWS's term for a framework variant — the core six-pillar lens, plus lenses for serverless, SaaS, machine learning, and others), answer the pillar questions against that workload, and the tool generates an improvement plan: a ranked list of "high risk items" and recommended remediations tied to specific best practices. You can snapshot progress with milestones, letting you diff a workload's risk profile release over release.

Crucially, the tool's output is a risk-weighted list, not a single portable score. Two workloads with the same number of flagged items aren't necessarily in the same shape — the tool doesn't collapse the review into one number you can quote externally, and the lens/workload/milestone vocabulary is AWS-specific. That's worth remembering before the next section, where Azure makes almost the opposite packaging choice — including, as it turns out, a genuine numeric score that AWS's tool has no equivalent of.

Running a workload review with the AWS Well-Architected Tool

In practice, most teams driving this from CI or a platform pipeline use the API rather than the console. Creating a workload looks like this:

aws wellarchitected create-workload \
  --workload-name "payments-api-prod" \
  --description "Customer-facing payments API, prod environment" \
  --environment PRODUCTION \
  --aws-regions "us-east-1" \
  --lenses "wellarchitected" \
  --review-owner "platform-team@example.com"

Here's a minimal version of the CreateWorkload request payload, showing the same fields in their structured form:

{
  "WorkloadName": "payments-api-prod",
  "Environment": "PRODUCTION",
  "AwsRegions": ["us-east-1"],
  "Lenses": ["wellarchitected"],
  "ReviewOwner": "platform-team@example.com"
}

Once a workload exists and its lens questions are answered (typically through the console, though the API supports programmatic answer updates), pulling the resulting recommendations is a read call:

aws wellarchitected list-lens-review-improvements \
  --workload-id abcd1234ef567890abcd1234ef567890 \
  --lens-alias wellarchitected \
  --pillar-id costOptimization

That returns improvement items scoped to a single pillar, each tied to a specific best practice ID and a risk rating. This is useful for feeding a dashboard or a periodic review cadence — you can diff improvement-plan output between milestones to show a workload trending down in high-risk items over a quarter.

What the tool does not do matters as much as what it does. It doesn't emit a single number you can put in a slide next to a competing cloud's score — there's no equivalent of a 0–100 grade. And the lens/workload/pillar taxonomy is AWS's own vocabulary; nothing in the API maps a pillar-id of costOptimization onto anything Azure exposes natively. If your organization's reporting expects one comparable score across providers, that score has to be built on top of this data, not read off it.

Azure: a pillar-based decision matrix and the Well-Architected Review assessment

Azure organizes the same underlying concerns — reliability, security, cost optimization, operational excellence, performance efficiency — into five pillars, but the packaging leads with structure rather than a standalone principles essay. The Azure Well-Architected Framework pillars page presents a literal matrix: pillar, workload concern, "apply the principles," and "strike a balance," with reliability mapped to "resiliency, availability, recovery" and paired against the explicit tension of designing for resilience "while keeping it simple." The framing treats every pillar as a set of tensions to navigate against the others, and the matrix format makes the trade-offs visible in a single table rather than requiring you to read pillar-by-pillar prose to infer them.

The operational entry point Microsoft points teams toward is the assessment tool, referenced directly from the Azure Well-Architected Framework landing page as one of the framework's core components alongside pillars, workloads, and design essentials. The assessment is a browser-based questionnaire, scoped per workload, that walks through pillar-specific questions and produces a report of guidance and risk areas. Its output is designed to connect into the operational tooling you're likely already watching — Azure Advisor recommendations for the same subscription. Advisor also rolls those recommendations up into a numeric Advisor score per subscription, a single percentage spanning cost, security, reliability, operational excellence, and performance, per the Azure Well-Architected Framework pillars page — the closest thing to a portable "grade" anywhere in this comparison. So a gap flagged in the assessment can, in principle, correspond to an actionable, always-on recommendation surfaced elsewhere in the portal, rather than a one-time snapshot that goes stale the moment you close the tab.

The packaging contrast with AWS is the useful takeaway here, not a judgment of quality. AWS leads with the Framework document — six pillars of principles and questions — and treats the Well-Architected Tool as the secondary, optional mechanism for turning those principles into tracked data. Azure inverts the emphasis: the pillar matrix and the assessment questionnaire are presented as the primary artifact from the first page a reader lands on, with the deeper design-principle prose functioning as supporting reference material underneath. Neither approach is wrong, but a team used to AWS's "read the principles, then optionally measure" flow will find Azure's "take the assessment, then read supporting guidance" flow structurally backwards on first encounter — which is exactly the kind of friction that trips up review cycles when the same platform team owns workloads on both clouds.

A brief aside: GCP doesn't converge either

Google Cloud's own Google Cloud Architecture Framework is worth a one-paragraph detour, mostly because it undercuts any temptation to treat "well-architected" as a two-out-of-three consensus. Its pillar set overlaps but doesn't mirror either competitor — operational excellence, security/privacy/compliance, reliability, cost optimization, and performance optimization, with sustainability treated as cross-cutting rather than a standalone numbered pillar — and it ships as design guidance, not a scored matrix. There's no equivalent of the AWS Well-Architected Tool or Azure's assessment questionnaire; the closest operational analog is a family of per-resource recommenders under the Active Assist umbrella, surfacing cost, security, and performance suggestions scattered across individual resources rather than aggregated into one workload-level report. The takeaway for an AWS/Azure comparison: a third vendor doesn't split the difference between the other two — it just adds a third shape.

Mapping the rubrics: where the pillars line up and where they don't

Laid side by side, the AWS/Azure alignment looks closer than it is. Security, cost optimization, and reliability appear as named pillars (or close synonyms) in both frameworks. Operational excellence appears in both by that exact name. Performance efficiency (AWS) and performance efficiency (Azure) are close enough in scope to treat as equivalent for mapping purposes. GCP's pillar set brushes up against the same territory, as noted above, but its "performance optimization" label and folded-in sustainability treatment don't slot cleanly into either AWS's or Azure's structure — one more reason to keep it out of the primary mapping exercise.

The real mismatches sit underneath the shared AWS/Azure names. AWS's sustainability pillar has no direct named counterpart as a standalone pillar in Azure's five — Azure addresses environmental efficiency as guidance woven through other pillars rather than as an independently weighted category, so an AWS improvement plan showing sustainability risk items has nothing to reconcile against on Azure without inventing the mapping yourself. Azure's reliability pillar, per its own matrix, spans "resiliency, availability, recovery" — a scope that on AWS is split across the reliability pillar (fault tolerance, recovery) and pieces of operational excellence (runbooks, operational readiness). A workload flagged clean on Azure reliability could still have gaps that would surface separately under AWS operational excellence, and a naive one-to-one pillar mapping would miss that.

The conclusion a platform team has to accept: an improvement plan from AWS's Well-Architected Tool is not evidence of Azure Well-Architected Review compliance, and an Azure Advisor recommendation resolved doesn't automatically close the analogous AWS finding. Question depth, weighting, and pillar boundaries differ enough that treating one provider's output as a proxy for another's review requires an explicit, manually maintained translation — it will never fall out of either framework's own documentation, because neither was written with that translation in mind.

FinOps: the cost dimension every framework references but none owns

Every one of these frameworks has a cost pillar, and every one of them, on inspection, points outward rather than owning the practice. AWS's cost optimization pillar principles orient toward measuring, monitoring, and modeling spend against usage; Azure's cost optimization pillar frames itself around the tension between spending efficiently and meeting other workload requirements. Neither framework specifies how to actually run showback, build unit economics, or govern budget ownership across teams — that operational machinery lives outside the architecture review entirely.

That's the gap the FinOps Framework fills, and it fills it as a genuinely cloud-agnostic practice rather than a provider-specific add-on. The FinOps Foundation's framework defines phases (inform, optimize, operate), personas, and — most relevantly here — domains and capabilities around allocation, unit economics, and rate/usage optimization that are built to apply identically whether the underlying spend is on AWS, Azure, or GCP. A tagging taxonomy, a shared definition of "unit cost per transaction," and a chargeback model don't need translating between clouds the way pillar questions do, because FinOps was designed from the outset as the cross-cutting layer that architecture frameworks assume exists but don't provide.

This is the asymmetry worth internalizing: architecture pillars are provider-specific vocabulary describing genuinely different tooling and question sets underneath similar names, but the cost-management practice referenced by all three is one portable framework with a shared vocabulary. If a platform team is going to standardize anything across providers before attempting to reconcile the rest, cost allocation and tagging discipline is the piece that will actually hold still.

A practical reconciliation approach for cross-provider review cycles

Given that the pillars won't converge on their own, the pragmatic move is to build a translation layer once and reuse it every review cycle, rather than re-deriving the mapping ad hoc each time a workload comes up for review.

Start with an internal mapping table — a spreadsheet or a small YAML file is enough — that maps each provider's pillar and representative questions onto a shared internal rubric your team controls. Something like this gives reviewers a single reference to check against instead of three framework documents open in separate tabs:

internal_pillar: reliability_and_resilience
maps_to:
  aws:
    pillar: reliability
    also_check: operational_excellence   # runbook/readiness questions live here on AWS
  azure:
    pillar: reliability
  gcp:
    pillar: reliability
notes: >
  Azure's reliability pillar folds in operational readiness questions
  that AWS splits into operational excellence. Reviewers must pull
  from both AWS pillars to get equivalent coverage.

Second, standardize tagging and cost-allocation metadata across providers independently of the architecture-pillar work — cost-center, environment, and owner tags with consistent keys and values regardless of cloud — so the FinOps layer stays coherent even while the architecture pillars stay provider-specific. This is the one dimension where cross-cloud consistency is actually achievable without inventing a translation layer, because the FinOps Framework already supplies the shared vocabulary.

Third, treat each provider's native tool output — an AWS Well-Architected Tool improvement plan, an Azure Advisor recommendation set, a GCP Active Assist recommender result — as input evidence feeding the internal rubric, not as the review's conclusion. The tool tells you what that provider's model flagged in that provider's vocabulary; your internal rubric is where the trade-off conversation actually happens across the whole estate.

The frameworks agree on the philosophy — structured trade-off conversation, not audit — which is genuinely useful common ground. But that agreement is at the level of intent, not mechanics, and mechanics are what a review cycle actually runs on. Consistent trade-off reasoning across AWS, Azure, and GCP is something a platform team builds by translation, deliberately and in writing, not something it gets by assuming the frameworks were ever meant to be interchangeable.

What to do next

Pull up your own workload's AWS improvement plan or Azure assessment report and try mapping just its top five findings onto the other provider's pillar language — the gaps you hit are exactly where your internal rubric needs explicit notes. If you run workloads on two or more of these clouds, start the mapping table now, even half-filled, rather than waiting for a "complete" version; it earns its keep the first time a stakeholder asks why an AWS-clean workload shows Azure Advisor findings. And audit your tagging schema for cost-center and environment keys across providers before your next FinOps review — that's the one layer in this whole comparison you can make genuinely portable today.
