Cross-Cloud Workload Identity: AWS IAM vs. Microsoft Entra

Cesar A. Nogueira
April 22, 2025 · 12 min read

Why both clouds are steering you away from long-lived keys

If a platform team still ships a static AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY pair or an Entra client secret into a CI runner or a container image, the failure mode is well understood: the credential outlives the job that needed it, it gets logged somewhere it shouldn't, and rotation becomes a recurring chore that someone eventually skips. AWS's own guidance is explicit that human users should reach AWS resources through federation with an external identity provider rather than through individual IAM users with long-lived keys — see AWS's identity providers and federation guidance. Microsoft Entra's workload identity federation documentation makes the equivalent case for non-human identities: workloads authenticate by presenting a token from a trusted external issuer, and Entra exchanges it for a Microsoft Entra token "without managing secrets" (see Microsoft's workload identity federation concepts).

The pattern in both cases is the same shape: an external OIDC or SAML identity provider issues a signed token asserting who the caller is, and the cloud provider's IAM layer decides whether to trust that assertion enough to hand out temporary, scoped credentials. No secret is stored anywhere; there's nothing to leak from a build log and nothing to rotate on a calendar.

That doesn't mean the work goes away — it moves. Instead of operating a secrets-rotation pipeline, the platform team is now responsible for correctly modeling a trust relationship: which issuer is trusted, which audience is acceptable, which subject claims map to which role, and how narrowly that mapping is scoped. Get the trust policy wrong and you don't get an outage — you get a workload that can either assume more privilege than intended, or a token exchange that fails closed at 2 a.m. because a subject string didn't match what you assumed it would look like. Both vendors' Well-Architected frameworks name security — and, within it, identity and access management — as a first-class pillar of the framework rather than an afterthought: see AWS's Well-Architected Framework and the Azure Well-Architected Framework. Treat federation configuration with the same design rigor the frameworks ask you to apply to the rest of your security posture, not as a default you can safely ignore once configured.

Two different trust-boundary models under the hood

The two clouds arrive at the same outcome — no static keys — through structurally different objects, and conflating them is where most cross-cloud federation bugs originate.

On AWS, you create an IAM OIDC or SAML identity provider object once per issuer (e.g., token.actions.githubusercontent.com for GitHub Actions). That object just registers the issuer and its thumbprint/signing keys with IAM. The actual trust decision lives somewhere else entirely: on the role's trust policy, as a Condition block evaluated against the claims inside the presented token at the moment sts:AssumeRoleWithWebIdentity (OIDC) or sts:AssumeRoleWithSAML (SAML) is called. AWS treats claim matching as a runtime policy evaluation — you can use StringEquals, StringLike, wildcards, and combine multiple conditions, and IAM evaluates them fresh on every assume-role call. The AWS IAM identity federation documentation describes this OIDC/SAML federation path as the mechanism for both human and workload access into a single account.

On Entra, the shape is different. You register an application (an app registration, which has a corresponding service principal), and then you attach one or more federated identity credential objects to it. Each federated identity credential is itself a static-ish object with an issuer and a subject field baked in at creation time — Entra checks the incoming token's iss and sub claims against that stored object for an exact, case-sensitive match. Microsoft's own documentation is explicit on this point: the federated identity credential's issuer, subject, and audience values "must case-sensitively match" the corresponding values in the token (see Microsoft's workload identity federation concepts) — there's no pattern or wildcard matching, and no general-purpose policy language evaluated at exchange time.

That's the conceptual mismatch worth naming plainly: AWS evaluates trust as a policy condition on claims, evaluated at assume-role time, with the flexibility of an IAM policy language (wildcards, multiple conditions, StringLike). Entra evaluates trust as an exact, case-sensitive issuer/subject match against a discrete, pre-created federated credential object, with much less runtime flexibility and no equivalent of a rich condition policy per credential. A team that designs its GitHub Actions trust relationship as "one AWS role trust policy with a StringLike condition covering repo:org/*:ref:refs/heads/*" will find there's no single Entra construct that expresses the same open-ended pattern — Entra pushes you toward provisioning more, narrower federated credential objects instead. Porting a design from one cloud to the other by analogy, rather than by re-deriving it from each provider's actual primitives, is exactly the failure mode this article is warning about.

Concrete example: wiring GitHub Actions OIDC into both clouds

Take the common case: a GitHub Actions workflow needs to deploy into both AWS and Azure without static credentials in either.

On AWS, after creating the OIDC identity provider for token.actions.githubusercontent.com, the role trust policy scopes exactly which repository and branch may assume it:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": {
        "Federated": "arn:aws:iam::123456789012:oidc-provider/token.actions.githubusercontent.com"
      },
      "Action": "sts:AssumeRoleWithWebIdentity",
      "Condition": {
        "StringEquals": {
          "token.actions.githubusercontent.com:aud": "sts.amazonaws.com",
          "token.actions.githubusercontent.com:sub": "repo:my-org/my-repo:ref:refs/heads/main"
        }
      }
    }
  ]
}

Both aud and sub are evaluated as conditions on the same statement, inside a single StringEquals map — pinning the audience alongside the subject is what stops a token minted for a different consumer from being replayed against this role.

The Entra equivalent isn't a policy — it's a distinct object, created via az ad app federated-credential create:

az ad app federated-credential create \
  --id <app-object-id> \
  --parameters '{
    "name": "github-main-deploy",
    "issuer": "https://token.actions.githubusercontent.com",
    "subject": "repo:my-org/my-repo:ref:refs/heads/main",
    "audiences": ["api://AzureADTokenExchange"]
  }'

Two things silently diverge here, and both fail closed rather than loud. First, the audience: AWS expects sts.amazonaws.com, Entra expects api://AzureADTokenExchange — a subject string copy-pasted between the two cloud definitions with the wrong audience will produce a rejected token exchange with a generic "invalid audience" error, not a helpful diagnostic pointing at the mismatch. Second, the subject claim format itself happens to look nearly identical in this GitHub Actions example (repo:org/repo:ref:refs/heads/main is GitHub's own claim shape, used verbatim by both clouds) — but that similarity is a coincidence of GitHub's token format, not a guarantee. The moment the identity provider is something other than GitHub Actions — a self-hosted OIDC IdP, GitLab CI, or a Kubernetes cluster's own issuer — the subject claim conventions AWS and Entra each expect you to match against can diverge in ways that aren't obvious from either vendor's documentation alone. Treat every subject string as provider-specific, never as a reusable template.

Kubernetes workloads: EKS IRSA/Pod Identity vs AKS workload identity federation

The GitHub Actions case is a single, well-known issuer. Kubernetes workloads make the same mismatch harder to spot because the manifests can look identical across clouds while the identity wiring underneath is not.

On EKS, IAM Roles for Service Accounts (IRSA) hinges on the cluster's own OIDC issuer URL, which is unique per EKS cluster. You register that issuer as an IAM OIDC provider, then annotate a Kubernetes service account with eks.amazonaws.com/role-arn, and the IAM role's trust policy conditions on the service account's namespace and name as encoded in the projected token's sub claim (something like system:serviceaccount:<namespace>:<service-account>).

EKS Pod Identity, the newer alternative, does not follow this pattern, and it's a mistake to treat it as a drop-in rename of IRSA. Pod Identity doesn't register a per-cluster OIDC identity provider at all: every cluster's Pod Identity Agent exchanges a token against the same static IAM principal (pods.eks.amazonaws.com), and you create a Pod Identity association (aws eks create-pod-identity-association) that maps a namespace/service-account pair on a given cluster to an IAM role. There's no eks.amazonaws.com/role-arn annotation and no IAM OIDC provider object to register per cluster — eliminating that per-cluster registration step is the specific problem Pod Identity was designed to solve. Migrating a workload from IRSA to Pod Identity is a change in trust model, not just a swapped annotation: the role's trust policy moves from conditioning on an OIDC provider ARN and sub claim to trusting the pods.eks.amazonaws.com service principal outright, with namespace/service-account scoping enforced by the Pod Identity association instead of by the trust policy's Condition block.

On AKS, workload identity federation attaches a federated identity credential to an Entra app registration, where the subject is set to the same system:serviceaccount:<namespace>:<service-account> string, and the issuer is AKS's OIDC issuer URL for that specific cluster.

The structural trap: because both IRSA and AKS use the same system:serviceaccount: subject convention (it comes from Kubernetes itself, not from AWS or Microsoft), teams that deploy the same containerized service to an EKS cluster running IRSA and an AKS cluster often assume the identity manifest is portable — same namespace, same service account name, same-looking YAML. It isn't, for either. The issuer URL is unique per cluster on both IRSA and AKS workload identity federation, so every cluster you deploy to needs its own IAM OIDC provider registration (IRSA) or its own federated identity credential (AKS) pointing at that cluster's specific issuer — copying the Kubernetes-side manifest across clusters does not carry the cloud-side trust object with it. A workload using IRSA that's redeployed to a third EKS cluster in a DR region, with an identical Helm chart, will get an AccessDenied on AssumeRoleWithWebIdentity if nobody registered that cluster's issuer with IAM — the manifest was portable, the trust relationship was not. This is precisely the failure mode EKS Pod Identity's cluster-independent service principal is designed to eliminate: a workload using Pod Identity instead only needs a new Pod Identity association created on the new cluster, not a new IAM OIDC provider object — making Pod Identity the counterexample to the per-cluster registration problem, not another instance of it.

This is the specific operational trap worth flagging to a team that treats "same YAML, same behavior" as an assumption: Kubernetes gives you a portable workload description, but IRSA and AKS workload identity federation both still require the cloud-side trust object to be re-derived per cluster — a constraint Pod Identity was built specifically to lift on the AWS side.

Building an explicit claims-to-role mapping strategy

The fix for both the CI/CD case and the Kubernetes case is the same discipline: stop treating federation config as something you write once per workload and instead track it as structured inventory. For every workload, per cloud, record:

  • Issuer URL — the exact OIDC discovery URL (GitHub's, your Kubernetes cluster's, your corporate IdP's) — or, for EKS Pod Identity, note that there is no per-cluster issuer to track at all
  • Audience — what the token's aud claim must equal for that specific cloud's exchange endpoint
  • Subject claim shape — the literal format that issuer produces (and confirm it, don't assume it)
  • Target role or app registration — the specific IAM role ARN or Entra app/federated credential this maps to
  • Scope of the condition — exact match vs. wildcard, and a written justification for any wildcard

This lines up with how both vendors frame the design problem in their own architecture guidance — not as a source of numbers to cite, but as the basis for treating identity federation as a reviewable design artifact. AWS's Well-Architected security guidance and Azure's Well-Architected Framework both position access management decisions as things you document and revisit, not settings you configure once and forget (AWS Well-Architected, Azure Well-Architected Framework).

The most important habit in that inventory-building process: validate the mapping against the actual token your IdP issues, not against a documentation example. Decode a real token from your CI provider or your cluster's projected service account token (kubectl create token <sa> --duration=10m plus a JWT decode, or inspecting the aud/sub/iss claims directly) before writing the trust policy or federated credential. Vendor docs show a representative shape; your actual IdP version, your actual cluster configuration, or a nonstandard claim added by an internal identity broker can all differ from the example in ways that only show up when the exchange fails.

Guardrails: what breaks when the mapping is sloppy

Three failure patterns show up repeatedly once teams start moving workloads across these two trust models.

Overly broad trust conditions. A StringLike condition on AWS with repo:my-org/*:ref:refs/heads/* is convenient — it lets every repo and branch in the org assume the role without touching the trust policy again. It also means any workflow in any repo in that org, on any branch, including a feature branch a contractor pushes to, can assume that role. The equivalent temptation on Entra is a federated credential subject pattern scoped to an entire organization or environment rather than a specific repo and branch. Both are the same mistake: convenience purchased with blast radius. Scope conditions to the narrowest subject that the workload actually needs, and treat any wildcard as something that needs a written justification, not a default.

Audience confusion when one IdP serves multiple clouds. If the same OIDC provider (say, a shared GitHub Actions org, or an internal identity broker) issues tokens consumed by both an AWS role and an Entra app registration, each trust relationship must check its own audience value strictly. A token minted with an overly generous aud claim — or a custom IdP configured to stamp the same audience value for every downstream consumer — collapses the separation between the two trust boundaries: a token intended for the AWS exchange could, in principle, also satisfy the Entra exchange if the audience isn't cloud-specific. Configure the IdP (or the CI provider's OIDC token request) to mint a distinct, cloud-specific audience per relationship, and verify both sides enforce it.

Audit trails don't look the same after migration, and someone has to keep watching both. On AWS, federated role assumptions show up in CloudTrail as AssumeRoleWithWebIdentity or AssumeRoleWithSAML events, carrying the federated identity's claims in the event detail. On Entra, the equivalent trail is in sign-in logs and service principal sign-in logs, structured very differently and queried through different tooling (Log Analytics / Azure Monitor rather than CloudTrail/Athena). A team that migrates a workload from one cloud to the other and doesn't update its detection rules and dashboards accordingly gets a blind spot, not an error message. And critically, federation removing the operational toil of key rotation does not remove the need for periodic trust-policy review — an overly broad condition or a stale federated credential pointing at a decommissioned repo or cluster doesn't expire the way a rotated key would; it sits there until someone audits it.

What to do next

Before moving or duplicating a workload's identity setup across AWS and Azure, pull the actual trust policy (aws iam get-role --role-name <name> --query 'AssumeRolePolicyDocument') or the actual federated credential (az ad app federated-credential list --id <app-id>) for the existing side, and write down its issuer, audience, and subject explicitly rather than inferring them from the deployment scripts. Then re-derive the other cloud's equivalent from that cloud's own primitives — don't translate the JSON trust policy into a federated credential object by pattern-matching field names, since the evaluation models genuinely differ. For any workload already running in both clouds, spend an afternoon just diffing the two configured audiences and subject scopes against each other; that's usually where the gap actually is. Finally, add both AWS's AssumeRoleWithWebIdentity CloudTrail events and Entra's service principal sign-in logs to whatever alerting already covers privileged access, since a widened trust condition on either side is a security-relevant change that won't otherwise show up until it's exploited or breaks.
