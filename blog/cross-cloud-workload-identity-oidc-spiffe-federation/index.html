Cross-Cloud Workload Identity: OIDC Federation and SPIFFE Without Static Keys

Cesar A. Nogueira
April 22, 2025 · 7 min read

Why Static Credentials Fail at Multi-Cloud Scale

The moment a workload in one cloud needs to touch resources in another — an AWS Lambda reading from BigQuery, an Azure Function writing to an S3 bucket, a GKE pod pulling an image from ECR — someone has to answer the question: what credential does it present? The path of least resistance is a long-lived secret: an IAM access key pair exported as an environment variable, a GCP service account JSON key baked into a container image, a client secret stored in a vault that nobody rotates.

This pattern fails in three compounding ways. First, rotation burden: every static credential is a scheduled operational task, and in practice rotation intervals drift from days to months to "whenever we remember." Second, blast radius: a leaked service account JSON is valid from anywhere on the internet until someone notices. There is no binding between the credential and the workload that is supposed to hold it. Third, audit gaps: when a key is shared across five workloads in two clouds, your access logs tell you which key acted, not which workload. Attribution collapses.

The design goal for cross-cloud identity is the inverse: identity should be derived from the platform the workload runs on — something the workload cannot copy off the box — and exchanged at runtime for short-lived, narrowly-scoped credentials. Nothing long-lived ever leaves the control plane that issued it. Both major building blocks below implement exactly this, and both are anchored in open standards rather than proprietary glue.

Two Building Blocks: OIDC Token Exchange and SPIFFE SVIDs

OIDC token exchange leverages the fact that every major cloud already issues signed identity tokens to its workloads. AWS issues OIDC tokens to EKS pods via IAM Roles for Service Accounts (IRSA); GKE issues them via Workload Identity; Azure issues them via managed identities; EC2 and GCE instances can retrieve signed identity documents from their metadata endpoints. These tokens conform to the claims structure defined in the OpenID Connect Core 1.0 specification: an issuer, a subject, an audience, an expiry, signed with keys published at a well-known JWKS endpoint.

The federation move is an STS-style exchange: present the signed OIDC token from trust domain A to the security token service of trust domain B, which validates the signature against A's published keys, checks the audience and subject claims against configured conditions, and mints short-lived credentials for B. No secret crosses the boundary — only a signed assertion with a TTL measured in minutes.

SPIFFE takes a different cut at the same problem. The SPIFFE specification defines a workload identity format independent of any cloud: a SPIFFE ID is a URI like spiffe://prod.example.com/ns/payments/sa/api, and a Verifiable Identity Document (SVID) carries that ID as either an X.509 certificate (X.509-SVID) or a signed JWT (JWT-SVID). A SPIRE control plane attests workloads against the node they run on and issues SVIDs with short lifetimes, rotating them automatically.

When to use which:

  • Cloud-native federation alone is sufficient when the trust domains are the clouds themselves and the access pattern is "workload in cloud A calls control-plane APIs in cloud B" — storage, queues, Pub/Sub. It requires no new infrastructure.
  • A SPIFFE control plane (SPIRE) earns its complexity when you need workload-to-workload mTLS across clouds, a uniform identity format for service mesh policy, or identity that survives portability — the same SPIFFE ID whether the workload runs on EKS today and GKE next quarter. JWT-SVIDs can also be federated into cloud STS endpoints, giving you one identity layer that fronts all three clouds.

Anchoring Assurance in NIST SP 800-63-4 and Well-Architected Security Pillars

Federation is not just a mechanism; it is a set of assurance decisions, and there is mature guidance for making them. The finalised NIST SP 800-63-4 dedicates a full volume (SP 800-63C-4) to federation and assertions. Although written primarily for human identity, its federation guidance translates directly to workload identity. Reading 800-63C-4 through that lens, the recurring themes are: assertions should be audience-restricted so a token minted for one relying party cannot be replayed at another; assertion validity windows should be short; signing keys should be managed with defined rollover procedures; and the trust relationship between issuer and relying party should be an explicit, documented agreement — not an implicit "we accepted the defaults." The revision's emphasis on continuous evaluation also maps cleanly: federation configurations should be re-reviewed as trust relationships change, not set once and forgotten.

The security pillars of the three well-architected frameworks reinforce the same posture from the cloud-architecture side. The AWS Well-Architected Framework security pillar treats identity as the primary perimeter and pushes for eliminating long-term credentials in favour of temporary, role-based access. The Azure Well-Architected Framework frames its security pillar around least privilege, zero trust, and traceability of every action to an identity. The Google Cloud Well-Architected Framework similarly centres identity and access management as a foundational security domain.

Translating these into concrete federation policy:

  • Token lifetime ceilings: cap exchanged credentials at the shortest TTL your workload's retry behaviour tolerates — typically 15–60 minutes, never days.
  • Audience pinning: the OIDC token's aud claim must exactly match the value the relying STS expects; reject wildcard audiences.
  • Subject/attribute pinning: restrict which source identities (AWS account + role, Azure tenant + managed identity object ID) can impersonate which target principals.
  • Explicit trust-domain allowlists: every federated trust relationship is declared in code, reviewed, and enumerated — nothing implicit.

Concrete Configuration: Federating an AWS Workload into Google Cloud

The canonical pattern: an AWS workload (EC2 instance or ECS task with an IAM role) needs to call Google Cloud APIs without a service account key. Google Cloud Workload Identity Federation supports AWS as a provider natively — it validates the AWS caller identity via GetCallerIdentity signed requests rather than OIDC, but the principle is identical: platform-derived identity in, short-lived Google access token out.

resource "google_iam_workload_identity_pool" "aws" {
  workload_identity_pool_id = "aws-prod-pool"
  display_name              = "AWS production workloads"
}

resource "google_iam_workload_identity_pool_provider" "aws" {
  workload_identity_pool_id          = google_iam_workload_identity_pool.aws.workload_identity_pool_id
  workload_identity_pool_provider_id = "aws-account-123456"
  attribute_mapping = {
    "google.subject"        = "assertion.arn"
    "attribute.aws_account" = "assertion.account"
    "attribute.aws_role"    = "assertion.arn.extract('assumed-role/{role}/')"
  }
  aws {
    account_id = "123456789012"
  }
  # Attribute condition: only one specific role may impersonate
  attribute_condition = "assertion.arn.startsWith('arn:aws:sts::123456789012:assumed-role/gcp-reader/')"
}

resource "google_service_account_iam_member" "impersonation" {
  service_account_id = google_service_account.gcp_reader.name
  role               = "roles/iam.workloadIdentityUser"
  member             = "principalSet://iam.googleapis.com/${google_iam_workload_identity_pool.aws.name}/attribute.aws_account/123456789012"
}

Note the two guardrails: the attribute_condition restricts impersonation to a single assumed role within the account, and the IAM binding uses principalSet scoped to the account attribute rather than the whole pool. The AWS workload then exchanges its identity for a federated token and impersonates the service account — the client libraries do this automatically when pointed at a generated credential configuration file.

The SPIFFE counterpart: a SPIRE server issues a JWT-SVID to a workload, and a relying party in another trust domain validates it against a federated trust bundle. A typical JWT-SVID payload:

{
  "sub": "spiffe://prod.example.com/ns/payments/sa/api",
  "aud": ["gcp-storage-gateway"],
  "iss": "https://spire.prod.example.com",
  "exp": 1735689900,
  "iat": 1735689600
}

The validator must check the signature against the current bundle, the aud against its own identifier, and exp/iat within skew tolerance. End-to-end verification should include deliberate failure tests: a token with a mismatched audience must be rejected, an expired token must fail closed, and credential refresh must happen before expiry under load, not after a 401.

Design Decisions and Failure Modes to Plan For

Trust domain topology. A single SPIFFE trust domain is simpler to operate but concentrates risk in one bundle-signing root. Multiple trust domains (per environment, per business unit, per cloud) contain compromise but every inter-domain federation is a new trust relationship to govern. A reasonable default: one trust domain per hard security boundary (prod vs. non-prod at minimum), with federation added only where workloads demonstrably need cross-boundary calls.

Operational failure modes. Three recur in practice. Clock skew: JWT validation fails when issuer and verifier clocks drift beyond the allowed leeway — enforce NTP discipline and configure explicit skew tolerance. Bundle rotation: if a relying party caches a trust bundle and the issuer rotates keys, validation breaks fleet-wide; automate bundle distribution and honour TTLs rather than pinning bundles in images. Control-plane availability: if SPIRE or the cloud STS is unreachable, workloads cannot mint new credentials — size SVID/token TTLs so running workloads survive a control-plane outage, and monitor issuance rates as a leading indicator.

Federation sprawl. Every new trust relationship is attack surface and audit obligation. A pool with ten providers and no attribute conditions is arguably worse than a well-managed set of static keys, because it looks modern while being permissive. Treat each federation as a reviewed architecture decision: documented purpose, pinned claims, named owner, expiry date for the review.

Decision checklist:

  1. Is the pattern workload-to-cloud-API (use native OIDC/AWS federation) or workload-to-workload across clouds (add SPIFFE/SPIRE)?
  2. Which assurance controls from SP 800-63-4 federation guidance apply — audience restriction, assertion lifetime, key rollover, documented trust agreements?
  3. Does the design satisfy the security pillar expectations of the target cloud's well-architected framework (AWS, Azure, Google Cloud) — least privilege, traceability, no long-lived secrets?
  4. What are the token TTL ceiling, the attribute conditions, and the rotation cadence — and are they all in code?

What to Do Next

Pick one cross-cloud data flow currently held together by a static key and replace it. Inventory long-lived credentials with cross-cloud scope (IAM access keys, exported service account JSONs), rank them by privilege, and migrate the highest-risk one to Workload Identity Federation or an equivalent OIDC exchange. Add the failure tests — audience mismatch, expired token, forced rotation — to your CI pipeline so the federation path is exercised continuously, not just at cutover. If you find yourself needing workload-to-workload identity across clouds, evaluate SPIRE in a non-production trust domain first, and only federate trust domains once the operational mechanics of bundle rotation are proven.
