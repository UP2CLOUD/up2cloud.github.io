Private Connectivity and Egress Control: Designing Cloud Networks That Minimise Public Exposure

Cesar A. Nogueira
April 22, 2025 · 8 min read

Why Public Endpoints Are the Default — and Why That's a Problem

Every major cloud provider ships its managed services with public endpoints by default. An S3 bucket, an Azure Storage account, a Cloud SQL instance, a Cosmos DB account — all of them are reachable over a public DNS name the moment they exist. This is a deliberate usability choice: it makes services consumable from anywhere without network plumbing. But it means that for most workloads, the network path to your data plane crosses infrastructure you don't control, and the only things standing between an attacker and your service are authentication credentials, TLS, and whatever firewall rules you remembered to configure.

The consequences compound. A public endpoint turns every misconfigured firewall rule, every overly broad service firewall exception, and every leaked access key into an internet-facing exposure. TLS protects confidentiality in transit, but it does nothing to reduce discoverability or to prevent credential replay from an arbitrary network location. And because the traffic path is the internet, you lose the ability to reason about data-plane traffic with network-layer controls — the very controls that are easiest to audit and hardest for an attacker to bypass.

Two design levers address most of this exposure. The first is private connectivity: making traffic between your workloads and managed services traverse the provider's backbone (or your own network) instead of the public internet. The second is egress control: deciding deliberately how, and whether, your workloads can initiate connections outward. Both are consistent with the network-protection guidance in the AWS Well-Architected Framework, the Azure Well-Architected Framework, and the Google Cloud Well-Architected Framework, and both follow directly from the zero-trust model described in NIST SP 800-207, which treats the network itself as untrusted and demands per-resource, explicitly authorised access.

Private Connectivity Patterns Across AWS, Azure and GCP

The three major clouds converge on the same idea with different names:

  • AWS: VPC endpoints. Gateway endpoints (S3 and DynamoDB only) add a route-table entry that directs traffic over the AWS network with no ENI and no hourly charge. Interface endpoints (powered by PrivateLink) place an elastic network interface with a private IP in your subnet for everything else — most AWS services, plus third-party and your own services exposed via endpoint services.
  • Azure: Private Link and private endpoints. A private endpoint is a network interface in your VNet with an IP from your address space, mapped to a specific PaaS resource. Per the Azure Private Link documentation, traffic between your virtual network and the service traverses the Microsoft backbone, eliminating exposure to the public internet.
  • GCP: Private Service Connect endpoints (an internal IP in your VPC that forwards to a Google API bundle or a producer service) and Private Google Access, a per-subnet setting that lets VMs without external IPs reach Google APIs over internal routes.

The gateway-versus-interface distinction in AWS matters operationally. Gateway endpoints are free and scale transparently, so there is rarely a reason not to attach them for S3 and DynamoDB. Interface endpoints carry hourly and per-GB costs per availability zone, so you scope them to the services you actually consume, and you decide deliberately whether to deploy them per-VPC or centralise them in a shared-services VPC.

DNS is where private connectivity usually breaks. When you enable an interface endpoint with private DNS, AWS overrides resolution of the public service hostname (e.g. sqs.eu-west-1.amazonaws.com) inside the VPC so it returns the endpoint's private IP. Azure requires you to integrate private endpoints with Private DNS zones (privatelink.blob.core.windows.net and friends) and link those zones to your VNets. If a workload resolves the public name through a resolver that bypasses these zones — a hardcoded upstream resolver, a container with its own dnsConfig, an on-premises client without conditional forwarding — traffic silently falls back to the public path or fails outright. Most "PrivateLink doesn't work" incidents are DNS incidents.

For hybrid estates, private connectivity extends over Direct Connect, ExpressRoute, or Cloud Interconnect: on-premises systems resolve the same private DNS names (via inbound resolver endpoints or DNS forwarding) and reach endpoints over the private circuit, so a database migration or a backup agent never needs public reachability to cloud APIs.

Egress Control: Deciding How Workloads Reach the Internet

Inbound controls get the attention, but unrestricted outbound access is what makes a compromised workload useful to an attacker: command-and-control callbacks, data exfiltration, and lateral movement to other tenants' public endpoints all ride on egress. Zero-trust guidance such as NIST SP 800-207 assumes breach and demands that every access be explicitly authorised — an assumption that is incompatible with a default 0.0.0.0/0 allow rule.

Three egress patterns cover most designs:

  1. NAT gateway with tight security groups / NSGs. Simple, low-latency, but controls are IP- and port-based only. Fine for workloads whose dependencies are a small set of known CIDRs; weak when dependencies are SaaS APIs behind CDN ranges.
  2. Centralised egress VPC/VNet with inspection. All outbound traffic routes through AWS Network Firewall, Azure Firewall, or a third-party NVA in a hub. You gain FQDN filtering, TLS inspection where justified, and a single audit point — at the cost of inspection latency, an extra failure domain, and non-trivial data-processing charges.
  3. Explicit proxy with FQDN allowlisting. Workloads have no direct route out at all; they must use a forward proxy (Squid, Envoy, a managed proxy) that enforces a domain allowlist. Strongest control and the clearest audit trail, but every workload must be proxy-aware, and HTTP_PROXY misconfiguration becomes your new outage class.

The trade-offs are real. NAT data processing charges are a classic FinOps surprise at scale. Centralised inspection adds milliseconds and a chokepoint that needs its own HA story. Allowlists rot: every new dependency is a change request, so the allowlist must live in version control with a review workflow, or teams will route around it.

One gap defeats all three patterns if ignored: DNS exfiltration. If your egress rules cover 80/443 but leave UDP/TCP 53 open to arbitrary resolvers, an attacker tunnels data out through DNS queries. Egress policy must force all name resolution through your controlled resolvers (Route 53 Resolver, Azure Private Resolver, Cloud DNS) and block port 53 to everything else.

Reference Configuration: Private Endpoints and Locked-Down Egress in Terraform

The following AWS-flavoured Terraform shows the pattern: a gateway endpoint for S3, an interface endpoint for SQS with private DNS, and a security group with no default outbound rule — only explicit allows.

# Gateway endpoint: free, route-table based, covers S3
resource "aws_vpc_endpoint" "s3" {
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.eu-west-1.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = [aws_route_table.private.id]
}

# Interface endpoint for SQS with private DNS override
resource "aws_vpc_endpoint" "sqs" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.eu-west-1.sqs"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  private_dns_enabled = true
  security_group_ids  = [aws_security_group.endpoints.id]
}

# Workload SG: NO 0.0.0.0/0 egress. Explicit allows only.
resource "aws_security_group" "workload" {
  vpc_id = aws_vpc.main.id

  egress {
    description = "HTTPS to interface endpoints"
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    security_groups = [aws_security_group.endpoints.id]
  }

  egress {
    description = "HTTPS to S3 via gateway endpoint prefix list"
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    prefix_list_ids = [aws_vpc_endpoint.s3.prefix_list_id]
  }

  egress {
    description = "DNS to VPC resolver only"
    from_port   = 53
    to_port     = 53
    protocol    = "udp"
    cidr_blocks = ["${cidrhost(aws_vpc.main.cidr_block, 2)}/32"] # cidrhost(...,2) is the AmazonProvidedDNS address; if you use Route 53 Resolver endpoints or a shared DNS VPC, replace with those resolver IPs.
  }

  egress {
    description = "DNS to VPC resolver only (TCP)"
    from_port   = 53
    to_port     = 53
    protocol    = "tcp"
    cidr_blocks = ["${cidrhost(aws_vpc.main.cidr_block, 2)}/32"]
  }
}

Defining an aws_security_group with only the inline egress blocks shown means Terraform manages exactly those rules — but rules added out-of-band (separate aws_security_group_rule resources, console changes) are not revoked. Verify effective rules with aws ec2 describe-security-groups or flow logs.

For the remaining genuine internet dependencies (OS package mirrors, a third-party API), you may need to add an egress rule to the proxy/NAT path (e.g., 3128 to a proxy SG, or 443 to the NAT/inspection subnet CIDRs) with a comment, or explicitly state that the example covers only the private-endpoint flows and that proxy egress is additional.

Mapping the Design to Well-Architected and Zero-Trust Criteria

This is not an exotic posture — it is what the frameworks ask for. The security pillar of the AWS Well-Architected Framework includes protecting networks and data in transit as explicit design principles, and the AWS Well-Architected Tool will probe exactly these areas during a review. The Azure Well-Architected Framework security pillar recommends network segmentation and private access to PaaS services, and the Google Cloud Architecture Framework makes the same recommendations under its security and networking guidance.

The zero-trust mapping is direct. NIST SP 800-207 defines a model in which no network location is implicitly trusted and access to each resource is granted per-request against policy. Private endpoints enforce per-resource network reachability; default-deny egress enforces that outbound access is intentional; flow logs provide the continuous monitoring the model requires. When an auditor or a Well-Architected reviewer asks how you minimise public exposure, the evidence they want is concrete: endpoint coverage for every managed service in use, route tables and security groups showing no unrestricted egress, DNS resolution paths that terminate on private zones, and flow-log queries demonstrating that data-plane traffic avoids public paths.

Common Failure Modes and a Review Checklist

The failures are depressingly consistent:

  • Endpoint created, DNS not overridden. The endpoint exists but workloads still resolve the public name and hairpin out through the NAT gateway. Everything "works," so nobody notices until a flow-log review.
  • NAT gateway as unrestricted egress. Private subnets route 0.0.0.0/0 to a NAT gateway with allow-all security groups — private in name only.
  • The forgotten service. A new managed service gets adopted that has no private endpoint support, or the team doesn't enable it, and one data flow quietly stays public.
  • Port 53 left open, enabling DNS tunnelling despite an otherwise tight egress policy.
  • Centralised endpoints without hybrid DNS, so on-premises clients can't resolve private names and fall back to public endpoints.

A review checklist that catches these:

  1. Inventory every managed service the workload consumes; for each, record the private connectivity mechanism (or the justified exception).
  2. Confirm private DNS is enabled and that resolution has been tested from workloads and from on-premises.
  3. Dump effective egress rules per subnet/security group; confirm no 0.0.0.0/0 allow exists and port 53 is restricted to managed resolvers.
  4. Query flow logs for unexpected public destinations over a representative period.
  5. Confirm the egress allowlist lives in version control with enforced review.

What to Do Next

Pick one workload this week and run the checklist against it — the gap between intended and actual network posture is almost always larger than expected. Codify the fixes: endpoints, DNS zones, security group rules and allowlists all belong in Terraform or your IaC tool of choice, reviewed in pull requests exactly like application code. Then make it continuous: re-run the flow-log verification after every new managed service adoption, and fold the checklist into your architecture review template so the next workload starts private-by-default rather than being retrofitted.
