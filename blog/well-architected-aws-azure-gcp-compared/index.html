AWS, Azure and GCP Well-Architected: Where They Diverge

Cesar A. Nogueira
April 22, 2025 · 11 min read

Why "well-architected" isn't one portable checklist

Every major cloud provider now publishes a well-architected framework, and at a glance they look like the same document with a different logo. All three organize guidance around pillars like security, reliability, cost and performance. All three claim to help teams avoid the same categories of mistakes. It's tempting to build one review checklist, run it against every workload regardless of cloud, and call the result a standardized governance process.

That temptation breaks down fast in practice. The AWS Well-Architected Framework is built around a formal "workload" object, reviewed through pillar questions and optional lenses, producing a risk report you can save as a milestone. The Azure Well-Architected Framework centers on pillars, design areas, and a self-guided assessment tool paired with continuous Azure Advisor recommendations — there's no persistent "workload" artifact in the AWS sense. The Google Cloud Well-Architected Framework reads primarily as design guidance organized into categories, with reviews assembled from ambient signals via the Recommender API rather than a single formal review tool.

Point a checklist built for AWS's workload/lens model at Azure's questionnaire and you'll find concepts that don't map cleanly — Azure has no "lens" equivalent, and its pillar guidance assumes a browser-based assessment flow rather than an API-driven workload object. Point that same checklist at GCP and the mismatch is starker still: there's no single "create a review" action to call. The frameworks agree on vocabulary at the pillar-name level and diverge everywhere below that — in structure, tooling, and what a "finding" actually looks like. Standardizing a multi-cloud review process means re-mapping pillars, tools and output artifacts across three structurally different systems, not copying one cloud's checklist onto the others.

Pillar-by-pillar alignment: where the three frameworks agree

Lining the three frameworks up side by side shows real convergence on naming, which is exactly what makes the divergence underneath easy to miss.

| Concept | AWS | Azure | GCP | |---|---|---|---| | Operational discipline | Operational Excellence | Operational Excellence | Operational Excellence | | Protecting systems and data | Security | Security | Security, Privacy & Compliance | | Staying up and recovering | Reliability | Reliability | Reliability | | Running efficiently | Performance Efficiency | Performance Efficiency | Performance Optimization | | Spending well | Cost Optimization | Cost Optimization | Cost Optimization | | Environmental impact | Sustainability (dedicated pillar) | Cross-cutting workload consideration | Folded into general design guidance | | Architecture design itself | (implicit across pillars) | Design areas | System Design (named category) |

Cost optimization, operational excellence and performance efficiency/optimization are nearly identical in intent and even in name across all three, which is unsurprising — the underlying engineering concerns (avoiding waste, running predictable operations, matching resources to workload) are cloud-agnostic, and this is also the space the FinOps Framework occupies as a vendor-neutral overlay on top of all three clouds' native cost pillars.

Sustainability is the clearest gap. AWS treats it as a full sixth pillar with its own best-practice questions in the AWS Well-Architected Framework. Azure discusses sustainability as a consideration threaded through workload design rather than as a standalone pillar in its Well-Architected Framework. GCP doesn't surface it as a named pillar in its Architecture Framework at all — it lives inside broader design guidance. If your internal review process treats sustainability as a first-class scored pillar because that's how AWS does it, you'll need an explicit decision about whether to hold Azure and GCP workloads to the same bar, since neither cloud gives you a native pillar to hang that score on.

GCP also names "System Design" as its own category, which doesn't have a direct one-to-one pillar counterpart in AWS or Azure — it's closer to the design-area guidance Azure publishes separately in the Azure Architecture Center, just packaged as a pillar rather than a companion resource.

Where the frameworks structurally diverge

The naming convergence stops being useful the moment you ask "how do I actually run a review," because the three clouds answer that question with fundamentally different mental models.

AWS is workload-centric. You define a workload as a discrete object — a named, bounded unit of architecture — and review it against the base pillar questions. On top of that base, AWS layers a formal lens system: SaaS, IoT, machine learning, serverless and other lenses add extra questions specific to that architecture pattern, without changing the underlying pillar structure. A review is explicitly a "constructive conversation," not an audit, per the framework's own introduction, but it still produces a discrete, saveable artifact.

Azure decouples the pillar guidance from any persistent workload object. The Azure Well-Architected Framework pairs its pillars and design areas with a browser-based self-assessment you run per workload. Completed assessments do persist against your signed-in account in the tool, so you can revisit them — but the assessment exposes no workload-scoped API object comparable to an AWS Well-Architected Tool workload, which is what matters for automation. Azure compensates for that API gap with Azure Advisor, which continuously surfaces recommendations against your actual deployed resources between formal assessments, so drift gets caught passively rather than only at the next scheduled review.

GCP inverts the emphasis further. The Google Cloud Architecture Framework reads as prescriptive design guidance first — how to build well — and only secondarily as something you'd run as a discrete review exercise. There's no GCP equivalent of "create a workload, answer questions, get a risk report" as a single named artifact. Instead, GCP's practical review signal comes from Active Assist and the Recommender API, which continuously generate cost, security, and performance recommendations against live resource configuration.

The practical consequence: AWS and Azure both assume a review is a milestone you schedule and revisit — a point-in-time snapshot you can diff against a later snapshot. GCP assumes continuous recommendation ingestion is the review, with no equivalent snapshot-and-diff workflow built into the platform. Any process spanning all three has to decide which of these two models it's actually building — or reconcile both.

Tooling comparison: what each cloud actually gives you to run a review

The structural differences above show up directly in tooling, and this is where a lift-and-shift checklist fails hardest.

The AWS Well-Architected Tool is the most literal implementation of a review-as-artifact: you define a workload (environment, industry, region scope), answer the pillar questions, optionally attach one or more lenses, and receive a risk report that buckets findings as High or Medium risk. Reviews can be saved as milestones, so you get a real time series of the same workload's risk posture across quarters. Everything is also available through the AWS Well-Architected Tool API, so aws wellarchitected calls can pull workload state and improvement plans into other systems.

The Azure Well-Architected Review is a browser-hosted questionnaire, one per workload, that scores your answers per pillar and hands back a report with prioritized recommendations. It isn't API-first the way AWS's tool is — its natural complement is Azure Advisor, which runs continuously against your actual resource graph and surfaces recommendations by category (Cost, HighAvailability, Performance, Security, OperationalExcellence) independent of whether anyone has run a formal assessment recently. Note that Advisor's HighAvailability category is where the Reliability pillar's uptime and recovery concerns actually live — scripting against Advisor with --category Reliability will fail, because that isn't a valid category value. That combination — periodic formal score plus continuous Advisor drift detection — is functionally Azure's answer to AWS's milestone model, just split across two separate surfaces instead of one.

GCP has no single named tool that plays the same role. Teams instead assemble a review out of the Architecture Framework as static guidance plus the Recommender API's category-specific recommenders (cost, security, performance, and others) as the machine-readable finding source. There's no risk-scored report object to export — you get a stream of individual recommendations, each tied to a specific resource and recommender ID, that a review process has to aggregate itself.

This produces a real cadence difference. AWS's milestone model and Azure's periodic-assessment-plus-Advisor model both nudge organizations toward scheduled reviews — quarterly or semi-annual, with a saved artifact to compare against next time. GCP's recommender model nudges toward continuous polling instead: there's no natural "review date" built into the tooling, so an internal process has to impose one by deciding how often to pull and snapshot recommender output.

Encoding a cross-cloud pillar map for a standardized internal review

The reusable artifact for a multi-cloud review process isn't a shared checklist document — it's a mapping file that ties an internal canonical pillar taxonomy to each cloud's native pillar name and tooling entry point. A checklist gets copy-pasted and drifts; a mapping file is what a review automation script actually reads.

# pillar-map.yaml
canonical_pillars:
  - id: cost_optimization
    aws:
      pillar_name: "Cost Optimization"
      source: "wellarchitected-workload-review"
    azure:
      pillar_name: "Cost Optimization"
      source: "advisor-cost-recommendations"
    gcp:
      pillar_name: "Cost Optimization"
      source: "recommender-cost"

  - id: operational_excellence
    aws:
      pillar_name: "Operational Excellence"
      source: "wellarchitected-workload-review"
    azure:
      pillar_name: "Operational Excellence"
      source: "advisor-operationalexcellence-recommendations"
    gcp:
      pillar_name: "Operational Excellence"
      source: "recommender-operational"

  - id: sustainability
    aws:
      pillar_name: "Sustainability"
      source: "wellarchitected-workload-review"
    azure:
      pillar_name: null   # cross-cutting, not a scored pillar
      source: "design-guidance-only"
    gcp:
      pillar_name: null   # not a named pillar
      source: "design-guidance-only"

Marking pillar_name: null for Azure and GCP sustainability isn't a modeling gap to paper over — it's the honest state of those frameworks, and it tells the review pipeline not to expect a scored finding there.

Against that map, a review automation script invokes each cloud's native entry point per canonical pillar. For AWS, that's the Well-Architected Tool API: creating or updating a workload, then pulling improvement items, for example aws wellarchitected list-lens-review-improvements --workload-id <id> --lens-alias wellarchitected --pillar-id costOptimization. For Azure, since there's no equivalent workload API, the pipeline leans on Advisor: az advisor recommendation list --category Cost --query "[].{resource:resourceMetadata.resourceId, impact:impact, problem:shortDescription.problem}". For GCP, it queries the relevant recommender directly: gcloud recommender recommendations list --project=<project> --location=us-central1 --recommender=google.cloudsql.instance.OverprovisionedRecommender --format=json. Note that the --location value is recommender-specific: Cloud SQL recommenders are regional, so a regional location like us-central1 is required here, while other recommenders genuinely do support global — check the location requirements for each recommender ID you wire into the pipeline.

None of these three calls return the same shape of data. That's expected — the mapping file's job is to let one pipeline know which call answers which canonical pillar for which cloud, not to force the underlying APIs to agree.

Reconciling review artifacts for governance and reporting

Once findings are pulled, the shape mismatch becomes the next problem. AWS's Well-Architected Tool returns a risk report with items bucketed as High Risk or Medium Risk, exportable as PDF or pulled via API as structured improvement items tied to specific best-practice questions. Azure Advisor returns recommendations with an impact field (High/Medium/Low) and a category, but no cross-pillar aggregate score the way an AWS milestone report does. GCP's Recommender API returns individual recommendations, each with its own priority field (P1–P4) and primaryImpact metadata, but no assembled report object at all — assembly is the caller's job.

Three different severity vocabularies (AWS's two-tier High/Medium, Azure's three-tier High/Medium/Low, GCP's four-tier P1–P4) cannot be stacked in a dashboard and compared as if they were the same scale. A GCP workload showing "12 P3 recommendations" is not directly worse or better than an AWS workload showing "3 Medium risk items" — the numbers come from unrelated scoring systems and a stakeholder reading them side by side will draw the wrong conclusion about which workload needs attention first.

The fix is normalization before anything reaches a shared risk register: map each native severity onto one internal taxonomy (say, High/Medium/Low) with an explicit, documented conversion table — AWS High → High, GCP P1/P2 → High, GCP P3 → Medium, GCP P4 → Low, Azure High → High, and so on — and tag every normalized finding with its canonical pillar from the mapping file above. Only after that conversion should findings from different clouds appear in the same report, the same count, or the same trend line.

Standing up one internal review process across all three clouds

Getting this running doesn't require deep tooling investment, but it does require doing the steps in the right order. Fix the canonical pillar list first — six or seven pillars, sustainability included even if it stays unscored for Azure and GCP — before touching any cloud-specific API. Then build the mapping file that ties each cloud's native pillar name and tool entry point to that canonical list, as shown above. Pick one artifact format for normalized findings (severity, pillar, resource, owner, source cloud) regardless of which cloud produced the raw data, and set a single review cadence — even if that means imposing a quarterly snapshot on GCP's naturally continuous recommender stream, or reconciling Azure's periodic assessment with its continuous Advisor feed into one cadence rather than two.

Findings belong in existing backlog tooling — Jira, Linear, whatever the engineering org already triages against — not left sitting in three separate cloud consoles where only the team that owns that specific cloud account will ever see them. A normalized finding with a pillar tag and severity maps cleanly onto a ticket; a raw GCP recommender JSON blob does not.

The goal isn't forcing GCP's Recommender API to behave like AWS's Well-Architected Tool, or making Azure Advisor pretend it has AWS-style milestones. It's building an internal layer — the mapping file, the severity normalization, the single cadence — that absorbs each cloud's native structure so what gets standardized is the review process itself, not the underlying checklist.

What to do next

Start by drafting the canonical pillar list and mapping file for the clouds actually in use — most organizations don't run all three, so trim the YAML above to what's relevant. Pull one real review cycle's worth of native output (an AWS Well-Architected Tool risk report, an Azure Advisor export, a GCP recommender list) and manually normalize it once by hand before automating anything, to validate the severity conversion table holds up against real data. Only then wire the API calls into a scheduled job, and route normalized output into the backlog tool the engineering team already uses — a review process nobody acts on is just a second inventory system.
