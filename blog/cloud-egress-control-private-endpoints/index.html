Locking Down Cloud Egress: Private Endpoints Over Public Routes

Most cloud network reviews start from the wrong question. Teams ask "what's blocked?" when the more useful question is "what's reachable, and did anyone provision it on purpose?" In a default subnet configuration, the answer to the second question is usually "everything on the internet," because reachability was never a decision — it was a side effect of attaching a route table with a 0.0.0.0/0 entry pointing at an internet gateway or NAT device. This article works through how to invert that default: build subnets where nothing leaves except through endpoints someone explicitly created, and show what that looks like in Terraform, route tables, and verification tooling.

The default-open network and why it's a liability

A newly created VPC or VNet subnet, once attached to a route table with an internet gateway or NAT device, can reach any IPv4 address on the public internet unless something explicitly denies it. Security groups and NACLs are commonly used to narrow this down, but they're bolted on after the fact — the underlying network fabric still has a live path out, and the burden of proof sits on the deny rule, not the allow. That's a "reachable unless denied" model, and it has a specific failure mode: a compromised workload, a leaked credential, or a misconfigured library that phones home will find a route to the internet already sitting there waiting to be used, because outbound reachability was never something anyone had to ask for.

The alternative is to treat reachability as a positive assertion rather than a leftover default: a workload can reach exactly the endpoints someone deliberately provisioned, and nothing else, because there is no other path out of the subnet at all. This isn't just a stricter security group — it's a structurally different topology. Instead of "open by default, then narrowed with rules," the goal is "closed by construction, then opened one named endpoint at a time." The rest of this article works through what that looks like across AWS, Azure, and GCP, and how to verify it actually holds rather than just assuming your route table looks the way you think it does.

Private connectivity primitives across the major clouds

Each major cloud has converged on a similar shape for this problem: a service's data plane gets projected into the consumer's private network as a first-class network object, rather than being reached over a public IP.

On AWS, PrivateLink is the umbrella technology. Underneath it are two distinct primitives. Gateway endpoints exist only for S3 and DynamoDB — they add a route table entry that points a specific prefix list at the service, at no additional per-GB cost, and traffic never leaves the AWS network. Interface endpoints are ENI-based: an elastic network interface with a private IP gets created directly in your subnet, and DNS for the service resolves to that private IP instead of a public one. Interface endpoints cover the much larger surface — Secrets Manager, KMS, ECR, Systems Manager, most other AWS APIs, as well as services hosted by other AWS accounts, AWS Marketplace partner services, and your own shared services. Crucially, AWS is explicit about the value proposition here: with PrivateLink, "you do not need to use an internet gateway, NAT device, public IP address, Direct Connect connection, or AWS Site-to-Site VPN connection to allow communication with the service or resource from your private subnets" — and because each endpoint is its own object, "you control the specific API endpoints, sites, services, and resources that are reachable from your VPC," per AWS's PrivateLink documentation.

Azure's equivalent is Private Link and Private Endpoint: a Private Endpoint is a NIC with a private IP from your VNet's address space, mapped to a specific PaaS resource — a storage account, a Key Vault, an Azure SQL server — so the resource's data plane is addressed privately instead of over its public endpoint.

GCP's Private Service Connect follows the same producer-consumer pattern: it lets you expose a service to consumer VPCs, or consume Google APIs and partner/published services, entirely through internal IP addresses inside your own VPC, without the traffic ever needing an external IP on either side.

The common thread across all three is architectural, not just a feature checkbox: each endpoint is an individually provisioned object with its own identity, its own IP, and its own lifecycle — not a blanket routing rule that happens to cover a service. That distinction is what makes an inventory of endpoints auditable in a way that a NAT gateway's route table entry never can be.

Replacing NAT gateways and public IPs with explicit egress paths

A NAT gateway (or NAT instance, or Azure NAT Gateway, or Cloud NAT) solves connectivity by translating private addresses to a public one, giving every workload behind it undifferentiated egress to anywhere on the internet on any port your security groups permit. Google frames Cloud NAT as infrastructure for instances and workloads that need outbound internet connectivity without an external IP — which is exactly the point: it solves "can this workload reach the internet at all," not "can this workload reach this specific service and nothing else."

An interface endpoint or Private Service Connect endpoint answers the second question directly, because it scopes reachability to one named service by construction. This has a compounding effect on auditability. A route table entry pointing at a NAT gateway tells a reviewer nothing about destination — the only way to know what a subnet actually talks to is to correlate flow logs after the fact, if you're logging them at all. A list of VPC endpoints attached to a subnet, by contrast, is a complete and readable inventory of exactly what that subnet can reach, checked in at plan time rather than reconstructed after an incident.

The same logic extends outward to partner and SaaS connectivity. Instead of a workload calling a partner's public API endpoint over the internet — which means trusting the partner's edge, your own egress path, and every network hop in between — the partner can front their service with a PrivateLink endpoint service (or a GCP producer service behind Private Service Connect), and you connect to it as an interface endpoint inside your own VPC. The traffic never transits the public internet, and the partner's own network never needs to know your CIDR ranges or accept inbound peering.

Worked example: a subnet that can only reach S3 and Secrets Manager

Concretely, this looks like a subnet with a route table that has no 0.0.0.0/0 entry at all — only the local VPC route, plus prefix-list routes injected by gateway endpoints. Here's a Terraform example provisioning an S3 gateway endpoint and a Secrets Manager interface endpoint, scoped to one private subnet and route table. It assumes an existing VPC (aws_vpc.main), private subnet (aws_subnet.private), and workload security group (aws_security_group.workload) declared elsewhere in your configuration — it's illustrative of the endpoint and route table shape, not a drop-in file:

resource "aws_vpc_endpoint" "s3" {
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.${data.aws_region.current.name}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = [aws_route_table.private.id]
}

resource "aws_vpc_endpoint" "secretsmanager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${data.aws_region.current.name}.secretsmanager"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = [aws_subnet.private.id]
  private_dns_enabled = true
  security_group_ids  = [aws_security_group.secretsmanager_endpoint.id]
}

resource "aws_security_group" "secretsmanager_endpoint" {
  name_prefix = "secretsmanager-endpoint-"
  vpc_id      = aws_vpc.main.id

  ingress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.workload.id]
  }

  # Terraform's aws_security_group resource is authoritative over
  # ingress/egress: with no egress block declared, it removes AWS's default
  # allow-all egress rule entirely, leaving zero egress rules — which would
  # break the endpoint's own responses. This block scopes egress to HTTPS
  # within the VPC instead of leaving that gap.
  egress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = [aws_vpc.main.cidr_block]
  }
}

# No aws_route with destination_cidr_block = "0.0.0.0/0" exists anywhere
# in this route table — the subnet has no path to an internet gateway
# or NAT device at all.
resource "aws_route_table" "private" {
  vpc_id = aws_vpc.main.id
}

resource "aws_route_table_association" "private" {
  subnet_id      = aws_subnet.private.id
  route_table_id = aws_route_table.private.id
}

Three things matter here. First, the interface endpoint's security group only permits inbound 443 from the workload's own security group — not 0.0.0.0/0 — so nothing outside your workload can even attempt to reach Secrets Manager through this ENI, and its egress is explicitly scoped to HTTPS within the VPC. That explicit block isn't narrowing an allow-all default — Terraform would otherwise strip AWS's default allow-all egress rule entirely and leave the security group with no egress at all, so the block is what keeps the endpoint able to respond in the first place. Second, private_dns_enabled = true means secretsmanager.<region>.amazonaws.com resolves to the endpoint's private IP automatically, so application code doesn't change at all. Third, and most importantly, the route table genuinely has no default route. If you terraform plan a change that adds one, it should be visible as a diff — this is what makes the "closed by construction" claim verifiable rather than aspirational.

Constraining exactly what's reachable: endpoint policies, prefix lists, and DNS

An interface or gateway endpoint narrows reachability to a service, but by default a workload behind it can still call every API action across that service's entire account-wide surface — every bucket, every secret. VPC endpoint policies close that gap: they're IAM-style JSON policies attached directly to the endpoint that permit calls only against specific resource ARNs.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["secretsmanager:GetSecretValue"],
      "Resource": [
        "arn:aws:secretsmanager:us-east-1:111122223333:secret:prod/db-*"
      ]
    }
  ]
}

Attach this to the aws_vpc_endpoint.secretsmanager resource via its policy argument, and the workload can fetch prod/db-* secrets and nothing else — even a fully compromised IAM role behind that endpoint can't enumerate or read unrelated secrets in the same account through this network path.

For security-group-level scoping, AWS-managed prefix lists (com.amazonaws.<region>.s3, and customer-managed prefix lists for interface endpoints where relevant) are the reusable unit: reference pl-xxxxxxx in a security group egress rule instead of hardcoding IP ranges that change as AWS adds capacity. Azure's service tags serve the same purpose, tying a rule to a named, Microsoft-managed tag rather than a raw CIDR block. GCP doesn't have a direct equivalent bound to a managed service tag; its firewall rules are instead scoped by network tags, service accounts, or explicit CIDR ranges — a coarser mechanism aimed at the same underlying problem.

Finally, private DNS is what makes all of this transparent to application code. Whether it's an AWS interface endpoint's private_dns_enabled flag, an Azure private DNS zone linked to the VNet, or GCP's private zones associated with Private Service Connect endpoints, the goal is identical: the service's standard public hostname resolves to the private endpoint's IP inside your network, with zero client-side changes. This matters operationally — it means you can roll private endpoints out without touching connection strings, SDK configuration, or environment variables.

Cross-account and partner reachability without the public internet

The producer-consumer model generalizes past AWS's own services. You can create a PrivateLink endpoint service in one AWS account and share it with another account, or with a partner, without VPC peering, without exposing either side's full CIDR range, and without the connection ever traversing the internet. GCP's Private Service Connect follows the same shape for producer/consumer VPCs. This is a materially different security posture than peering: peering exposes routable reachability between two entire networks, while a PrivateLink/PSC endpoint exposes exactly one service on one port.

At larger scale, when many VPCs need private reachability to shared services, a hub-and-spoke topology built on AWS Transit Gateway (or the Azure/GCP equivalents) avoids the operational sprawl of full-mesh peering — instead of n² peering connections, each spoke VPC attaches once to the hub. But centralizing egress through a hub is a trade-off, not a free win: it also centralizes the choke point for policy enforcement and logging, which is good for auditability but means the hub becomes a single blast-radius point that needs its own scaling, availability, and change-control discipline.

Verifying the control actually holds

None of this is worth anything if you can't prove it after the fact. VPC Flow Logs (or the Azure/GCP equivalents), combined with DNS query logs, let you detect any connection attempt that falls outside the provisioned endpoint set — a workload trying to resolve or reach an address that isn't one of your endpoints is a signal worth alerting on, not just logging.

Reachability-analysis tooling is the second leg: rather than inferring "this subnet has no internet path" from reading a route table by eye, tools that trace actual network paths (AWS Reachability Analyzer, or equivalent path-tracing in other clouds) can confirm programmatically that no live path exists from a given subnet to an internet gateway or NAT device.

The third leg is shifting the check left into CI/CD as policy-as-code: an Open Policy Agent / Conftest / Checkov rule that fails a Terraform plan if it introduces a 0.0.0.0/0 route in a route table tagged as private, or if a subnet gains map_public_ip_on_launch = true without an explicit override tag. This turns "closed by construction" into something enforced at merge time rather than something that has to be re-verified by hand every quarter — the kind of continuous review that the AWS, Azure, and Google Cloud well-architected frameworks all treat as a standing operational discipline rather than a one-time exercise.

Rollout trade-offs and where the model has gaps

This isn't free. AWS interface endpoints carry an hourly charge per AZ plus a per-GB data processing fee, which changes the cost math against a shared NAT gateway. In practice, teams often find that a handful of interface endpoints serving many subnets ends up cheaper than the NAT data-processing charges they replace, but that's a heuristic, not a rule — a proliferation of narrowly-used endpoints across many accounts can add up just as easily, so model both cost curves against your own traffic volume before committing to full coverage. Gateway endpoints (S3, DynamoDB) don't have this problem — they're free and route-table-based.

Coverage is also incomplete. Not every managed service, and not every third-party SaaS API, has a private endpoint option yet. For the exceptions, the right move is a narrowly scoped egress proxy — a forward proxy or firewall that allow-lists specific FQDNs and ports for the handful of workloads that genuinely need it — rather than reopening a general 0.0.0.0/0 route for the whole subnet just to accommodate one dependency. That keeps the "closed by construction" property intact everywhere except the specific, logged, reviewed exception path.

Given the cost and coverage gaps, migration is realistically incremental rather than a single cutover. Start with the subnets holding your most sensitive workloads and credentials — anything touching secrets, PII, or payment data — get gateway and interface endpoints in place there first, remove their default route, and verify with reachability analysis. Then expand endpoint coverage outward to less sensitive tiers as cost and operational familiarity allow.

What to do next

Pick one subnet — ideally one running a workload with access to secrets or sensitive data — and audit its route table for a 0.0.0.0/0 entry. If one exists, inventory what that workload actually calls (flow logs are the fastest way to find out), provision gateway or interface endpoints for each destination, attach endpoint policies scoped to the specific resource ARNs in use, and only then remove the default route. Re-run a reachability check afterward to confirm there's no residual path to the internet, and add a policy-as-code rule in CI so the route can't silently come back on a future change.
