Private Connectivity and Egress Control by Design

Cesar A. Nogueira
April 22, 2025 · 12 min read

The default egress path nobody reviewed

Most private subnets aren't private by design — they're private by naming convention. A workload sits in a subnet labeled "private," yet its route table still sends 0.0.0.0/0 to a NAT gateway, which forwards to an internet gateway, which means that workload can reach any IPv4 address on the public internet unless something else stops it. That route almost always came from a landing-zone template or a Terraform module someone copied from a reference architecture, not from a conversation about what the workload actually needs to talk to.

The practical consequence is that egress destinations are unbounded and unaudited. Nobody can answer "what external services can this workload reach?" by reading the route table, because the answer is "everything." A compromised dependency, a misconfigured SDK pointed at the wrong endpoint, or an attacker with code execution on that host all get the same answer: outbound access to the entire internet, constrained only by whatever security group or NACL happens to be attached — and those are frequently permissive on egress because nobody thought egress needed the same scrutiny as ingress.

The real design problem underneath this is narrower than "block all outbound traffic." Most workloads need to reach a small, enumerable set of destinations: a handful of managed cloud APIs, a couple of internal services in other VPCs or accounts, maybe one or two SaaS vendors, and possibly an on-prem system over a VPN or interconnect. The goal isn't zero egress — it's replacing an implicit, unbounded default with an explicit, bounded one that matches that actual destination list. Everything in this article is about the primitives that make that substitution possible, and the policy layer that makes the result auditable rather than just "differently permissive."

Two connectivity models, one key distinction: directionality

Cloud networking gives you two fundamentally different tools for controlled egress, and the difference that matters isn't cost or performance — it's who initiates the connection and what's exposed on the other end.

Endpoint-based private connectivity — AWS PrivateLink interface endpoints, GCP Private Service Connect — lets a workload initiate a connection to a specific published service over a private IP address that lives inside its own VPC. AWS PrivateLink describes this directly: you don't need an internet gateway, NAT device, public IP, or VPN connection to reach the service, and "you control the specific API endpoints, sites, services, and resources that are reachable from your VPC." Traffic never leaves the private network fabric, there's no return path exposed to the internet, and the service being connected to doesn't need a route back into your VPC at all — it publishes an endpoint, you consume it.

NAT-based egress control — public NAT gateways, private NAT gateways — works the other way. The workload initiates outbound connections to arbitrary external destinations, and the NAT device translates the source address to a small, controlled set of IPs before the traffic leaves. The destination isn't necessarily private, and it doesn't need to publish anything special; it just needs to see requests coming from an allowlistable source.

This isn't a stylistic choice between two roughly equivalent tools. It's determined entirely by whether the destination publishes an endpoint service and how tightly you need to scope the blast radius of a compromised host. If the destination has an endpoint, use it — it removes an entire class of exposure. If it doesn't, NAT is the only option, and the design question shifts to how much you can shrink and monitor what NAT allows through.

When endpoint services are the right primitive

Endpoint services are the correct default for three categories of destination: managed cloud provider APIs (object storage, secrets managers, container registries, KMS), internal services published from another VPC or account inside the same organization, and SaaS vendors that specifically publish an endpoint service for their product.

The value isn't just "no internet gateway required." It's that AWS PrivateLink endpoints support endpoint policies — IAM-like JSON documents attached directly to the VPC endpoint that scope which API actions or resources are reachable through that specific endpoint, independent of the IAM policy attached to the calling principal. This is worth being precise about: an endpoint policy is a second control plane, not a substitute for IAM. A principal might have full s3:* permissions in IAM, but if the S3 endpoint policy only allows GetObject on a specific bucket ARN, that's the ceiling for anything going through that endpoint. That's a meaningfully different security property from "the IAM policy is correct" — it means a misconfigured IAM policy on one workload still can't reach buckets outside the intended set through this network path.

A minimal endpoint policy for an S3 gateway endpoint, scoped to a single bucket:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:PutObject"],
      "Resource": [
        "arn:aws:s3:::app-artifacts-prod",
        "arn:aws:s3:::app-artifacts-prod/*"
      ]
    }
  ]
}

Blast radius stays small because traffic never traverses a shared NAT device or touches public IP space — each endpoint's reachability is scoped independently, so a compromised workload can't pivot through the same NAT and reach whatever another workload's endpoint allows. The remaining risk is DNS: if a private hosted zone isn't wired up to resolve the service's standard DNS name to the endpoint's private IP, an application can fall back to public resolution and — if a route happens to exist — bypass the endpoint entirely. Pinning DNS to the private endpoint closes that gap and should be treated as part of the endpoint configuration, not an optional extra.

When NAT-based egress is the right primitive

NAT is the right tool exactly when the destination doesn't (and won't) publish an endpoint service: third-party REST APIs, public package registries (npm, PyPI, crates.io), webhook targets on customer-controlled domains, and any destination where you don't control whether an endpoint exists. The workload genuinely needs to reach the public internet — the goal is doing that from a controlled, allowlistable source rather than from an unscoped path.

AWS distinguishes two NAT gateway connectivity types, and the distinction is about Elastic IP and internet gateway reachability, not about which type can reach a transit gateway. NAT gateways documentation lays this out: a public NAT gateway sits in a public subnet with an Elastic IP, routes to an internet gateway, and gives instances in private subnets outbound internet access without accepting unsolicited inbound connections — this is what you want for third-party APIs where you need a stable IP to hand the vendor for allowlisting. A private NAT gateway has no Elastic IP and can't route to an internet gateway (traffic sent that way is simply dropped). Both public and private NAT gateways can route traffic through a transit gateway or virtual private gateway to reach peered VPCs or on-prem networks — that path isn't exclusive to private NAT. What actually differentiates private NAT is that it has no Elastic IP and no route to an internet gateway even by mistake: traffic sent that way is dropped, not translated and forwarded. That makes private NAT the right choice specifically when a workload must never be able to reach the public internet, including under a future misconfiguration — reach for public NAT instead when the same workload also needs internet access, since traffic routed to peered/on-prem destinations is sourced from the gateway's private IP either way and the EIP only comes into play for IGW-bound traffic.

The trade-off to hold onto: NAT collapses many source IPs down to a handful, which is exactly what makes vendor-side allowlisting practical — you hand the vendor two or three Elastic IPs instead of asking them to allowlist a whole subnet. But that collapse concentrates blast radius on your side of the connection. Every workload routed through the same NAT gateway shares its reachability envelope; if one workload is compromised, it can reach anything the NAT gateway's route table and any downstream firewall permit, which is often "the entire internet" unless something more granular than the NAT gateway itself is enforcing scope.

Configuring both paths side by side

The split between endpoint and NAT traffic should live in the route table, not in application configuration or convention. A concrete pattern: a private application subnet with no default route to an internet gateway at all, an interface VPC endpoint for the specific managed service the app needs, and a separate NAT gateway carved out in its own egress subnet strictly for the traffic that has no endpoint alternative.

# AWS Network Firewall — the app subnet's default route points here, not at the NAT gateway
resource "aws_networkfirewall_firewall" "egress" {
  name                = "egress-firewall"
  firewall_policy_arn = aws_networkfirewall_firewall_policy.egress.arn # policy resource not shown
  vpc_id              = aws_vpc.main.id

  subnet_mapping {
    subnet_id = aws_subnet.firewall.id
  }
}

# sync_states is a TypeSet keyed internally by hash, not by availability_zone — it can't be
# indexed with a string key, so filter for the AZ we want with a for expression instead
locals {
  firewall_endpoint_id = [
    for s in aws_networkfirewall_firewall.egress.firewall_status[0].sync_states :
    s.attachment[0].endpoint_id if s.availability_zone == "us-east-1a"
  ][0]
}

# Private app subnet — deliberately has no direct 0.0.0.0/0 route to an IGW or a NAT gateway;
# internet-bound traffic is sent to the firewall endpoint first
resource "aws_route_table" "app_private" {
  vpc_id = aws_vpc.main.id

  route {
    cidr_block      = "0.0.0.0/0"
    vpc_endpoint_id = local.firewall_endpoint_id
  }
}

# Interface endpoint for a managed service — private path, no NAT or firewall involved
resource "aws_vpc_endpoint" "secrets_manager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.us-east-1.secretsmanager"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = [aws_subnet.app_private.id]
  security_group_ids  = [aws_security_group.secretsmanager_endpoint.id]
  private_dns_enabled = true

  policy = data.aws_iam_policy_document.secretsmanager_endpoint_scope.json
}

# Public NAT gateway, isolated in its own egress subnet, downstream of the firewall —
# only the firewall subnet's route table (not shown) is allowed to send traffic here.
# depends_on is required: NAT gateway creation needs the IGW already attached to the VPC,
# and omitting this is a known source of intermittent first-apply failures.
resource "aws_nat_gateway" "egress" {
  allocation_id = aws_eip.nat.id
  subnet_id     = aws_subnet.egress_public.id

  depends_on = [aws_internet_gateway.main]
}

Note what's deliberately missing: there's no route in app_private's table that points straight at aws_nat_gateway.egress. Instead, the subnet's only internet-bound route sends traffic to a firewall or forward-proxy endpoint (an AWS Network Firewall endpoint, or a Squid/Envoy proxy's ENI) that enforces an FQDN or CIDR allowlist. Only traffic that clears that check reaches the firewall subnet's own route table (not shown here), which forwards allowed traffic on to the NAT gateway and, from there, to the internet gateway. The app_private route table decides whether traffic can leave the subnet at all; the firewall/proxy layer decides which internet destinations are reachable once it does.

The easy way to undo all of this is a permissive security group — though that specifically applies to interface endpoints, which attach an ENI (and a security group) in each subnet they're deployed to. Gateway endpoints like the S3 example earlier have no ENI and no security group at all; they're reached through a prefix-list entry in the route table instead, so their exposure surface is a route table pointing the wrong subnet at the endpoint, not an inbound security group rule. For an interface endpoint such as secrets_manager above, a tightly scoped endpoint policy is still fully exposed if the security group attached to its ENI allows inbound from 0.0.0.0/0 on all ports — the isolation the endpoint buys you is a network-path property, and a security group misconfiguration re-opens exactly the exposure the endpoint was meant to close. Both the interface endpoint's security group and the NAT egress path's firewall rules need to be scoped as carefully as the route table itself; treating either as an afterthought defeats the purpose of building the split in the first place.

Service perimeters: the policy layer that makes egress auditable

Route tables and endpoint policies are per-resource controls — each one is correct in isolation, but nothing stops someone from adding a new route, a new endpoint with an overly broad policy, or a new NAT gateway in a different subnet six months from now. What's missing is a control plane that sits above individual routing decisions and enforces a boundary regardless of how any single resource is configured.

That's the role of a service perimeter. Google Cloud's VPC Service Controls implements this as a deny-by-default boundary around a set of projects: even a properly authenticated, correctly IAM-permissioned request to a managed service is blocked if it crosses the perimeter boundary in a way the perimeter's policy doesn't allow. AWS doesn't have a single primitive that replicates this — there's no deny-by-default perimeter control that blocks an otherwise-authenticated, correctly IAM-permissioned call to a managed service purely because it crosses an organizational boundary. The closest composite is narrower and split across layers: Network Firewall egress policies, SCPs — which are genuinely organization-wide, enforced via AWS Organizations — restricting which VPC endpoints or NAT resources accounts are allowed to create in the first place, and endpoint policies that remain scoped to the individual VPC endpoint they're attached to, not to the organization. Approximating a VPC-SC-style perimeter on AWS means deliberately composing these layers; it isn't a drop-in equivalent, and the endpoint-policy layer specifically has to be replicated on every endpoint rather than declared once at the org level.

The payoff is that egress stops being "whatever the route table happens to allow today" and becomes a versioned artifact that lives in the same repository as the infrastructure it governs, gets reviewed in the same pull request as a new endpoint or NAT rule, and can be diffed when someone proposes widening it. Combined with VPC flow logs and endpoint access logs, this gives an actual audit trail — which principal, which workload, which destination, at what time — rather than reconstructing intent after the fact from a route table that only says where packets could go, not where they were supposed to go. The AWS Well-Architected Framework and the Google Cloud Architecture Framework both treat this kind of reviewable, evidence-backed control as a core security design principle rather than an operational nice-to-have, and it's the piece that turns egress from a network implementation detail into something a security review can actually reason about.

A decision framework for choosing per traffic pattern

A short table covers most real cases:

| Traffic pattern | Primitive | |---|---| | Managed service, same cloud provider | Endpoint service (interface or gateway), with a scoped endpoint policy | | Internal service, different VPC/account, same provider | Endpoint service / PrivateLink-style peering, or Private Service Connect on GCP | | Third-party SaaS with no published endpoint | Public NAT gateway + egress proxy allowlist + vendor-side IP allowlisting | | On-prem, via VPN or Direct Connect/Interconnect | Public or private NAT gateway routed through a transit/virtual private gateway — either type reaches on-prem; use private NAT specifically when the workload must never be able to reach the public internet, even under a future misconfiguration |

The operational cost side belongs in this decision, not just the security side. Interface endpoints and NAT gateways are both metered resources rather than free network plumbing — check current pricing for either before assuming one is the cheap default. Beyond the metering, each interface endpoint adds a DNS resolution path that has to be maintained (private hosted zone entries, private_dns_enabled flags, and awareness that some SDKs cache resolved IPs aggressively). And centralizing many workloads behind one NAT gateway to save cost is precisely what concentrates blast radius — cheaper and safer pull in opposite directions here, and that tension is a legitimate FinOps input alongside the security one, not an afterthought to be resolved purely on price.

Next steps

Start by pulling every route table with a 0.0.0.0/0 route to a NAT gateway or internet gateway and listing what's actually reachable through it — most environments have never done this audit. For each private subnet found, classify its real destination list against the table above: anything that's a managed-service or internal call almost always has an endpoint alternative available today and can be moved off shared NAT immediately. What's left after that pass — genuine third-party, no-endpoint traffic — is the actual, much smaller footprint that needs an egress firewall or proxy allowlist and ongoing flow-log review, and it's a far more tractable thing to secure and audit than "everything this VPC might someday need to talk to."
