Well-Architected Across AWS, Azure, and GCP: A Pillar Comparison

Cesar A. Nogueira
April 22, 2025 · 11 min read

Why "well-architected" isn't a portable term

Platform teams running multi-cloud estates eventually try to standardize how they review architecture quality across AWS, Azure, and GCP. The instinct is reasonable: all three vendors publish something called a "well-architected" (or architecture) framework, all three organize guidance into named groupings, and all three ship an assessment tool. It's tempting to build one internal rubric, label its rows with vendor pillar names, and call it done.

That instinct breaks down faster than it looks. The frameworks share a family resemblance — trade-off-based design guidance organized into named categories — but they are not the same document wearing three logos. AWS names six pillars explicitly in AWS's own framework documentation; Azure names five in its own pillars matrix — a different count, not a renamed copy of AWS's list, and notably with no standalone sustainability pillar. GCP's public docs describe its framework inside the broader Cloud Architecture Center, but this piece could not independently re-confirm GCP's current top-level terminology and full category list against the live page in this research pass. That gap is called out explicitly below rather than papered over — it's exactly the kind of assumption that causes trouble when someone builds a permanent internal standard on a guess instead of a checked fact.

This article works through what's actually documented for each vendor, what native tooling exists to run reviews, where the three frameworks structurally diverge, and why none of them — AWS included — is a substitute for a dedicated cost-governance practice. It closes with a concrete way to encode a shared control (resource tagging) across all three clouds in Terraform, and how to layer the FinOps Framework on top of vendor-native reviews rather than trying to fold cost governance into any single vendor's pillar.

AWS Well-Architected Framework: six pillars and native tooling

AWS's framework is the most completely documented of the three in the material available for this comparison. Its own docs state the pillar set outright: neglecting "the six pillars of operational excellence, security, reliability, performance efficiency, cost optimization, and sustainability" makes it "challenging to build a system that delivers on your expectations and requirements," per the pillars page of the AWS Well-Architected Framework. Each pillar has its own deep-dive guide with design principles and best practices; the pillars page is the index into that structure.

Two things about the AWS pillar list are worth flagging for teams building a cross-cloud rubric. First, sustainability is a named, first-class pillar — not every vendor framework treats environmental impact as a top-level review category, so don't assume it maps cleanly elsewhere without checking. Second, cost optimization sits as one pillar among six, not as the framework's organizing principle.

For execution, AWS provides the AWS Well-Architected Tool, which lets teams register a workload, answer the pillar questions against it, and get back prioritized "risk items" — the tool's own documentation describes it as reviewing "workloads against current Amazon Web Services architectural best practices" and providing "recommendations on how to improve your architecture." That's a meaningful capability for platform teams: it turns the framework from a PDF into a repeatable, per-workload review artifact with tracked findings, which is what makes it possible to run the same review cadence across dozens of workloads without every team inventing its own checklist.

It's worth being precise about what the cost optimization pillar actually covers, because this is where cross-cloud standardization efforts tend to overreach. The pillar encodes cost-aware design principles — right-sizing, matching supply to demand, choosing the right pricing model at architecture time. It is not a cost-management practice: it doesn't define showback/chargeback processes, anomaly detection workflows, or the cross-functional operating model needed to keep spend under control as workloads evolve after the review is done. That distinction matters for section 6 below.

Azure's five pillars, and what's still unverified for GCP

Azure's Well-Architected Framework names five pillars, laid out in a matrix on its own pillars page: Reliability (resiliency, availability, recovery), Security (data protection, threat detection and mitigation), Cost Optimization (cost modeling, budgets, reducing waste), Operational Excellence (holistic observability, DevOps practices), and Performance Efficiency (scalability, load testing). The Azure Well-Architected Framework landing page lists the same five pillars with one-line summaries and confirms the framework is structured around "Pillars," "Workloads," Azure service guides, "Design essentials," training, and an "Assessment tool."

That's a genuine, checkable difference from AWS, not a documentation gap: Azure has one fewer pillar than AWS's six, and — notably — no standalone sustainability pillar. Sustainability appears on the Azure landing page, but as one of six Workloads (alongside Microsoft Fabric, AI, SaaS, mission-critical, and HPC), not as a top-level pillar alongside Reliability and Security. In other words, Azure treats environmental impact as a workload-specific design concern rather than a permanent review category applied to everything. A cross-cloud rubric that assumes "Azure has the same six pillars as AWS, just renamed" would silently misplace sustainability review coverage — it needs its own row mapped to a workload pattern, not a pillar.

GCP presents its guidance as the Google Cloud Well-Architected Framework, hosted inside the broader Cloud Architecture Center. Unlike the Azure case above, this piece does not have an independently reverified account of GCP's current top-level terminology, full pillar/category list, or navigation structure — the live page could not be re-confirmed in this research pass. Rather than assert specifics that can't be checked, treat GCP's framework as a known unknown: before mapping it into an internal standard, pull the current terminology and full category list directly from docs.cloud.google.com/architecture/framework rather than assuming it mirrors AWS's or Azure's naming or structure.

The Azure case above illustrates why this matters: guessing at Azure's structure instead of checking it would have produced a wrong pillar count and a misplaced sustainability row. GCP is the one piece of this comparison still carrying that risk. Flagging it explicitly — rather than papering over it with an assumed AWS- or Azure-shaped structure — is the difference between a review process that survives a vendor's next framework revision and one that quietly drifts out of sync with reality.

Where the three frameworks structurally diverge

Even with the GCP gap noted above, enough is documented to build a structural comparison across intent and tooling:

| Vendor | Pillar/category terminology | Stated intent | Native review tooling | |---|---|---|---| | AWS | Six named pillars (operational excellence, security, reliability, performance efficiency, cost optimization, sustainability) — documented list | Design-time best practices plus a structured workload review | AWS Well-Architected Tool — per-workload risk items | | Azure | Five named pillars (Reliability, Security, Cost Optimization, Operational Excellence, Performance Efficiency) — pillars page; sustainability is handled as a Workload type, not a pillar | Quality-driven tenets, architectural decision points, review tools — per the framework landing page | An "Assessment tool" referenced on the landing page; verify current form directly | | GCP | Terminology and full category list not independently reverified in this research pass — framework page | Framework guidance embedded in the broader Cloud Architecture Center, alongside per-technology-area guidance | Not confirmed in this research pass — verify directly against the source |

Two conclusions follow directly from that table. First, count and terminology are not interchangeable across vendors — building a spreadsheet that assumes "six pillars, just renamed" for Azure and GCP risks silently dropping or duplicating review coverage the moment the real structure differs, exactly as it would for Azure's sustainability handling above. Second, all three vendors converge on the same operating pattern: pillar/category guidance for design-time decisions, plus a separate tool or portal to operationalize the review against a specific workload. That convergence is what an internal standard should actually anchor to — the shape of "design guidance plus tracked review," not the specific label of any one pillar.

Given the terminology risk, internal reviewers should map vendor guidance to outcomes — availability targets, security controls, cost-aware design choices, operational readiness — rather than trying to build a term-for-term crosswalk between "AWS Reliability" and "Azure Reliability" and hoping the underlying checklist items line up. They might; they might not. Outcome-based mapping survives a vendor renaming or restructuring its pillars, which does happen over a framework's lifetime.

On the cost side specifically, the gap is consistent across all three vendors: each treats cost as one review dimension embedded in a broader framework, evaluated at a point in time against a specific workload. None of the three, as documented, describes a continuous, cross-team operating practice for cost — that's the space the FinOps Framework exists to fill, covered in section 6.

Encoding cross-cloud tagging as a shared control

Whatever pillar or category a vendor files "cost" under, none of the three frameworks enforces tagging consistency on its own — that's an infrastructure-as-code responsibility. A common cost-allocation tag schema (cost_center, environment, owner) applied identically across AWS, Azure, and GCP resources is the practical prerequisite for any review process or FinOps reporting pipeline that needs to reconcile spend across vendors, regardless of which pillar/category each vendor nominally files cost under.

variable "cost_tags" {
  description = "Shared cost-allocation tag schema applied across all clouds"
  type = object({
    cost_center = string
    environment = string
    owner       = string
  })
}

resource "aws_s3_bucket" "data" {
  bucket = "up2cloud-example-data"

  tags = {
    cost_center = var.cost_tags.cost_center
    environment = var.cost_tags.environment
    owner       = var.cost_tags.owner
  }
}

resource "azurerm_resource_group" "example" {
  name     = "up2cloud-example-rg"
  location = "East US"
}

resource "azurerm_storage_account" "data" {
  name                     = "up2cloudexampledata"
  resource_group_name      = azurerm_resource_group.example.name
  location                 = azurerm_resource_group.example.location
  account_tier             = "Standard"
  account_replication_type = "LRS"

  tags = {
    cost_center = var.cost_tags.cost_center
    environment = var.cost_tags.environment
    owner       = var.cost_tags.owner
  }
}

resource "google_storage_bucket" "data" {
  name     = "up2cloud-example-data"
  location = "US"

  labels = {
    cost_center = var.cost_tags.cost_center
    environment = var.cost_tags.environment
    owner       = var.cost_tags.owner
  }
}

The point of sharing a single cost_tags object variable across three resource blocks is that it forces the same schema — same keys, same casing convention, same required-ness — onto every provider at plan time, instead of leaving each team to invent its own tag names per cloud (which is how organizations end up with CostCenter, cost-center, and costCenter all referring to the same thing across three billing exports). Note that GCP labels have stricter character constraints than AWS/Azure tags (lowercase, limited character set), so the schema needs to be designed to the strictest common denominator, not the most permissive one.

This is enforcement at the infrastructure layer, not a substitute for the review process itself. A well-tagged resource can still be badly architected; a well-architected workload with no tags is unattributable in a cost report. The two controls are complementary and neither vendor's well-architected framework, on its own, guarantees the tagging half gets enforced.

Layering the FinOps Framework on top

The FinOps Framework, maintained by the FinOps Foundation, is explicitly not vendor-specific and is built to apply across whatever mix of AWS, Azure, GCP, and SaaS spend an organization actually runs. It is widely described as organizing around a continuous phase cycle — commonly named Inform, Optimize, and Operate — rather than a one-time review checklist; this piece could not independently re-confirm the exact current navigation and category names on the live page in this research pass, so treat the phase names as a starting point and confirm the current structure directly against finops.org/framework/ before citing it in an internal standard.

That phase-based, continuous structure is exactly what distinguishes it from any of the three cloud vendor frameworks covered above. AWS's cost optimization pillar, Azure's Cost Optimization pillar, and whatever cost-related category GCP files its guidance under are each one dimension inside a broader, point-in-time architecture review. None of them is positioned as an ongoing, cross-team financial operating model with defined personas (finance, engineering, procurement) and maturity stages — that's specifically what the FinOps Framework's phase cycle is for. Running a vendor well-architected review once a quarter and treating its cost pillar findings as "the FinOps practice" undersells what FinOps actually requires: allocation, forecasting, unit economics, and rate optimization as continuous, owned work rather than a review checkbox.

The two layers connect naturally rather than competing. Findings from a vendor's cost pillar or cost category review — over-provisioned instances, missing reservations, orphaned storage — are exactly the kind of signal that feeds a FinOps Inform phase, where the goal is accurate, allocated visibility into spend and its drivers. The Optimize phase then acts on that visibility (rightsizing, commitment purchases, architectural changes), and Operate closes the loop by embedding those decisions into ongoing governance — which is where consistent tagging (section 5) becomes load-bearing, since Inform-phase allocation reporting is only as good as the tag data underneath it.

Building an internal review process that survives multi-cloud reality

A workable sequence for a platform team standardizing reviews across AWS, Azure, and GCP:

  1. Document each vendor's actual current pillar/category set and tooling before writing anything internal. AWS's six pillars and Azure's five pillars are both confirmed above, from the AWS pillars page and Azure's pillars page respectively — record them as-is, don't assume one vendor's count or naming carries over to another. For GCP, that means opening docs.cloud.google.com/architecture/framework directly and recording the full current pillar/category names and tooling, since this piece could not independently reverify them.
  2. Define an internal outcome taxonomy (availability, security posture, operational readiness, cost-aware design, and so on) and map each vendor's actual pillars/categories into it. This is the layer that stays stable even if a vendor renames or restructures its own framework.
  3. Treat FinOps Framework adoption as a parallel, cross-cutting workstream, not a line item inside any single vendor's cost pillar review. It needs its own cadence, personas, and phase cycle feeding from — not replacing — the vendor-native reviews.
  4. Revisit the mapping whenever a vendor revises its framework. Pillar sets, category names, and tooling are not guaranteed to stay static over a framework's lifetime — treat any pillar/category count as version-specific and re-check it periodically rather than assuming it's permanent.

Next steps worth taking immediately: pull the current, complete pillar/category list for GCP directly from the vendor docs linked above (Azure's is already documented in this piece); audit whether the tagging schema in section 5 is actually enforced (via policy-as-code, not just convention) across existing Terraform state; and check whether cost pillar/category findings from any past vendor review are currently reaching whoever owns the organization's FinOps Inform-phase reporting, or whether they're dead-ending in a review document nobody revisits.
