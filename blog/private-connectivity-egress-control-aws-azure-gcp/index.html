Private Connectivity and Egress Control Across AWS, Azure, GCP

Cesar A. Nogueira
April 22, 2025 · 15 min read

Why Default-Open Egress Is a Design Liability, Not a Networking Detail

Most VPCs and VNets start life with a NAT gateway, a handful of public IPs on bastion hosts or load balancers, and security groups or NSGs that default-allow outbound traffic on all ports. That configuration works fine for a five-service prototype. It becomes a liability once the service count grows: every workload that reaches a managed database, a secrets store, an object bucket, or a third-party API does so by routing through a NAT gateway to the public internet, then relying on the destination's TLS and IAM to keep things honest. The network itself asserts nothing. An engineer auditing that VPC six months later has no answer to "which of these two hundred instances can reach which external services" beyond reading application code and IAM policies, because the routing layer doesn't encode intent.

This is the crux of what AWS, Azure, and Google Cloud all now treat as a first-class architectural decision rather than an operational afterthought. Each provider's Well-Architected material folds network isolation and controlled data flow into its security pillar — AWS's Well-Architected Tool is built around reviewing workloads against exactly these kinds of structural risks, and the Azure Well-Architected Framework and Google Cloud's Well-Architected Framework both structure their guidance around design choices you make once and then live with, not settings you tune after an incident. The tension every platform team is actually resolving is simple to state and hard to operationalize: workloads need to reach managed services, partner SaaS, and first-party cloud APIs, but every packet that transits the public internet is a packet an auditor has to justify, a path a misconfigured route table can expose, and a potential exfiltration channel if credentials leak. Private connectivity primitives — PrivateLink, Private Link, Private Service Connect — exist to collapse that tension: reachability without a public hop.

AWS PrivateLink: Interface Endpoints, Gateway Endpoints, and Endpoint Policies

AWS splits VPC endpoints into two mechanically different things that get conflated constantly. Gateway endpoints are route-table entries, not network interfaces — they exist only for S3 and DynamoDB, cost nothing extra, and work by adding a prefix-list route in your subnet's route table that sends S3/DynamoDB-bound traffic over AWS's internal network instead of a NAT gateway. Interface endpoints are the general case: an elastic network interface with a private IP, provisioned in your subnet, fronted by AWS PrivateLink, that gives you a private DNS name resolving inside the VPC for the target service — most heavily-used AWS services expose one (Secrets Manager, KMS, ECR, CloudWatch Logs among them), though a handful of services don't support interface endpoints at all, notably the global services IAM and Route 53.

AWS PrivateLink also extends past first-party AWS services. A vendor can front their service with a Network Load Balancer and publish it as a VPC endpoint service; you then connect to it with an interface endpoint in your own VPC, and traffic never touches the public internet or requires VPC peering or a Transit Gateway attachment between your account and theirs. This is how a lot of B2B SaaS and data platforms (observability vendors, data warehouses, security tooling) offer "private connectivity" as a tier — it's PrivateLink under the hood, and it means the vendor's account boundary stays intact while your traffic stays off the internet.

The control point people skip is the endpoint policy — an IAM-like resource policy attached directly to the endpoint, independent of any IAM policy on the calling principal. If you don't attach one, AWS defaults to full access, meaning any principal in the VPC with underlying IAM permissions can call any resource in that service through the endpoint, including resources in other accounts. A restrictive endpoint policy scoped to specific bucket ARNs or a specific Secrets Manager secret is what actually turns "traffic doesn't cross the internet" into "traffic can't reach unintended resources even privately."

Azure Private Link vs. Service Endpoints: Choosing the Right Primitive

Azure gives you two primitives that look similar in a diagram and behave very differently in practice. A Service Endpoint extends your VNet's identity onto the Azure backbone for a specific service (Storage, SQL, Key Vault) — traffic leaves the subnet over Microsoft's network rather than the public internet, but it still resolves to the service's public IP, and no interface is created in your VNet. A Private Endpoint, by contrast, provisions an actual NIC with a private IP address from your VNet's address space, and that IP becomes how the service is reached — which means on-premises networks connected via ExpressRoute or VPN, and peered VNets, can reach it too, something a Service Endpoint cannot do because Service Endpoints don't propagate across peering by default.

Azure Private Link states this plainly: it lets you access Azure PaaS services and Azure-hosted partner services "over a private endpoint in your virtual network," with traffic to the service traveling the Microsoft backbone rather than the public internet, and — notably — you can publish your own service behind a Private Link service and deliver it to other tenants, mirroring PrivateLink's producer/consumer model on AWS.

The practical difference shows up in three places. First, NSGs: because a Private Endpoint has a real NIC and private IP, you can write NSG rules and Azure Firewall rules against it like any other VNet resource — but only once network policy enforcement is turned on for that subnet. NSG and UDR enforcement on a private-endpoint subnet is disabled by default (the subnet-level privateEndpointNetworkPolicies setting), so deploying a Private Endpoint does not, by itself, put it under an existing NSG's control; that setting has to be explicitly enabled first, per Azure Private Link. A Service Endpoint isn't a addressable object in that sense, so your control is limited to what the service-level firewall on the PaaS resource allows. Second, DNS: Private Endpoint requires a private DNS zone (or your own DNS override) so that the PaaS resource's standard hostname resolves to the private IP instead of the public one — Service Endpoint needs no DNS change since the public hostname is retained. Third, cross-boundary reach: Private Endpoint is the only option if on-premises or a peered VNet in another subscription needs access, or if you need strict IP-based allow-listing on the resource itself.

Rule of thumb: reach for Service Endpoints when everything lives in one VNet, you want zero DNS overhead, and the built-in resource firewall (VNet rules) is sufficient. Reach for Private Endpoint the moment on-premises connectivity, cross-VNet/cross-tenant access, or compliance requirements demanding a private IP and full NSG-level control enter the picture — and remember to enable subnet network policies before assuming NSG rules are actually being enforced against it.

Google Cloud's Layered Model: Private Google Access, Private Service Connect, VPC Service Controls

Google Cloud splits the problem into three independent layers that compose rather than substitute for each other.

Private Google Access is the baseline: a per-subnet setting that lets VM instances or GKE nodes without external IP addresses reach Google APIs and services (Cloud Storage, BigQuery, Pub/Sub) over Google's internal network instead of through a NAT gateway. On its own, the subnet flag routes that traffic to the APIs' normal public IP ranges over Google's network — it does not change what those hostnames resolve to. Resolving to the restricted (restricted.googleapis.com) or private (private.googleapis.com) virtual IP ranges is a separate, optional DNS configuration layered on top of the subnet flag, not an automatic consequence of enabling it. It's the equivalent of "give my internet-less compute a route to first-party APIs" and requires essentially no infrastructure beyond the subnet flag; the restricted/private VIP behavior requires the additional DNS step.

Private Service Connect (PSC) is the producer/consumer layer, and it's the closest conceptual match to AWS PrivateLink and Azure Private Link. On the consumer side, PSC lets you create an endpoint with an internal IP address in your VPC that forwards to a Google API bundle or to a published service — including third-party and partner services published by another organization's VPC. On the producer side, you can publish your own service behind an internal load balancer and expose it to consumer VPCs (including across organizations) without VPC peering, without exposing anything publicly, and without the consumer needing routes back into your network. It's a strict superset in intent of Private Google Access: not just Google's own APIs, but any service a producer chooses to publish.

VPC Service Controls sits above both of those and solves a different problem entirely — it is not a connectivity mechanism, it's a data-exfiltration perimeter. VPC Service Controls lets you draw a boundary around a set of Google Cloud resources (a set of projects, typically) such that API calls to services inside that perimeter are blocked from contexts outside it, regardless of IAM permissions. The scenario it's designed for is a stolen service account key or an insider with valid credentials: even with valid IAM rights to a BigQuery dataset, a request originating outside the approved perimeter (a personal laptop, a compromised host in another project) gets denied at the network/API layer, not just the identity layer. This is the piece platform teams most often skip, because Private Google Access and PSC solve "how do I reach it privately," while VPC Service Controls solves "how do I stop it from leaving even if someone gets in."

Worked Example: Restricting Egress to a Managed Service with Terraform

Concretely: a private subnet with instances that need to read a secret from Secrets Manager and objects from S3, with no NAT gateway and no 0.0.0.0/0 egress rule. The before-state security group typically looks like this, and it's the thing you're removing:

resource "aws_security_group_rule" "legacy_egress_all" {
  type              = "egress"
  from_port         = 0
  to_port           = 0
  protocol          = "-1"
  cidr_blocks       = ["0.0.0.0/0"]
  security_group_id = aws_security_group.app.id
}

Replace it with interface and gateway endpoints scoped by policy, and security group rules that only allow egress to those endpoints. Note that the interface endpoint (Secrets Manager) and the gateway endpoint (S3) need to be authorized differently at the security-group layer, because a gateway endpoint has no ENI or security group of its own:

resource "aws_vpc_endpoint" "secretsmanager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.region}.secretsmanager"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.endpoints.id]
  private_dns_enabled = true

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = "secretsmanager:GetSecretValue"
      Resource  = aws_secretsmanager_secret.app.arn
    }]
  })
}

resource "aws_vpc_endpoint" "s3" {
  vpc_id            = aws_vpc.main.id
  service_name      = "com.amazonaws.${var.region}.s3"
  vpc_endpoint_type = "Gateway"
  route_table_ids   = aws_route_table.private[*].id

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = ["s3:GetObject", "s3:PutObject"]
      Resource  = "${aws_s3_bucket.app_data.arn}/*"
    }]
  })
}

data "aws_ec2_managed_prefix_list" "s3" {
  name = "com.amazonaws.${var.region}.s3"
}

# Interface endpoint traffic: app -> endpoints SG, both directions required.
resource "aws_security_group_rule" "app_egress_endpoints" {
  type                     = "egress"
  from_port                = 443
  to_port                  = 443
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.endpoints.id
  security_group_id        = aws_security_group.app.id
}

resource "aws_security_group_rule" "endpoints_ingress_app" {
  type                     = "ingress"
  from_port                = 443
  to_port                  = 443
  protocol                 = "tcp"
  source_security_group_id = aws_security_group.app.id
  security_group_id        = aws_security_group.endpoints.id
}

# Gateway endpoint traffic: no ENI/security group exists for S3, so egress
# is authorized against the endpoint's own prefix list, not a security group.
resource "aws_security_group_rule" "app_egress_s3_prefix_list" {
  type              = "egress"
  from_port         = 443
  to_port           = 443
  protocol          = "tcp"
  prefix_list_ids   = [data.aws_ec2_managed_prefix_list.s3.id]
  security_group_id = aws_security_group.app.id
}

Note the endpoint policy blocks: without them, both endpoints default to AWS's full-access policy (Principal: "*", Action: "*", Resource: "*"), which allows any action against any resource reachable through that service — not scoped to the calling account, so a caller with sufficiently permissive IAM can reach resources in other accounts through the same endpoint. This defeats the purpose of scoping access. The s3:GetObject/PutObject restriction to a single bucket ARN and the secretsmanager:GetSecretValue restriction to a single secret ARN are what make this "least-privilege private access" rather than "private access to everything." Two security-group details are easy to miss and will silently break this setup if skipped: the S3 gateway endpoint has no ENI or security group, so it must be authorized via prefix_list_ids on the app's egress rule, not source_security_group_id; and the interface endpoint needs an explicit ingress rule on aws_security_group.endpoints from the app's security group, since security groups are stateful per-resource, not automatically bidirectional between two different groups.

The same shape exists on the other two providers, differing mainly in whether you're creating a NIC-based resource or a route-based one. On Azure, azurerm_private_endpoint attaches to a subnet and links to a private_connection_resource_id (a Key Vault, Storage Account, or SQL server), paired with an azurerm_private_dns_zone and zone-group association so the resource's standard hostname resolves internally. On GCP, the producer side uses google_compute_service_attachment behind an internal load balancer, and the consumer side uses google_compute_forwarding_rule with a target of that service attachment (or a Google APIs bundle) to create the PSC endpoint. The Terraform resource names differ; the architectural decision — provision a private, policy-scoped path instead of default egress — is identical.

DNS, Routing, and the Failure Modes Private Connectivity Introduces

The most common bug report after standing up any of these endpoints is "I created the endpoint but traffic is still going out through the NAT gateway / public internet." It is almost always DNS. AWS interface endpoints only intercept the service's default hostname if private_dns_enabled is true and the VPC has DNS resolution and DNS hostnames enabled; if your application hardcodes a regional or non-standard hostname, the private DNS zone won't match, and traffic falls through to the public route. Azure Private Endpoint requires an explicit private DNS zone linked to the VNet — if that link is missing, the PaaS resource's FQDN still resolves publicly, and NSG or firewall rules become irrelevant because the traffic never targets the private IP at all. GCP's PSC endpoints rely on correct DNS records pointing at the endpoint's internal IP, and the restricted/private VIP ranges for Private Google Access require their own DNS records layered on top of the subnet flag; using the wrong domain suffix silently sends traffic to the public API surface.

The second class of failure is transitive routing. VPC peering on AWS is explicitly non-transitive — if VPC A is peered to VPC B, and VPC B has the interface endpoint, VPC A cannot reach it through B without its own peering connection or a route through a Transit Gateway. The same limitation applies to VNet peering on Azure. This pushes most multi-VPC/VNet architectures toward a hub-spoke pattern: centralize interface/private endpoints in a shared services VPC or VNet, and use Transit Gateway (AWS) or hub VNet peering plus DNS forwarding rules (Azure) so spoke networks can resolve and route to the shared endpoint without each spoke needing its own copy.

A practical troubleshooting checklist, in the order that catches the most issues fastest:

  1. DNS resolution — does the service hostname resolve to a private IP from inside the affected subnet? (dig/nslookup from an instance, not your laptop.)
  2. Route tables — for gateway endpoints, is the prefix-list route present in the route table actually attached to the subnet in question?
  3. Security group/NSG pairing — egress allowed from the client to the endpoint, and ingress allowed on the endpoint's security group from the client subnet; both directions are checked independently and a mismatch on either side silently drops traffic. On Azure, also confirm subnet network policies are enabled — an NSG attached to a private-endpoint subnet has no effect on that traffic until privateEndpointNetworkPolicies is turned on.
  4. Endpoint policy scope — is the specific action/resource combination the application needs actually permitted, or was the policy written against the wrong ARN/resource ID?

Enforcing Egress as Policy, Not Convention

An endpoint that exists is not the same as an endpoint that's mandatory. Without an enforcement layer, nothing stops a future engineer from re-adding a NAT gateway route or attaching a public IP to a new instance, and the private path quietly becomes optional rather than the only path.

On AWS, Service Control Policies (SCPs) at the organization or OU level can deny calls to a service unless the request is routed through an approved VPC endpoint, using the aws:sourceVpce or aws:SourceVpc condition keys — this converts "we built an endpoint" into "the endpoint is the only way in," enforced at the identity layer regardless of what any individual account's IAM policies allow. Pair this with VPC Flow Logs on the endpoint's ENIs (or on the subnets) so that every connection attempt, including denied ones, is auditable after the fact.

On Azure, Azure Policy definitions can enforce publicNetworkAccess: Disabled on PaaS resources (Storage, Key Vault, SQL) at scale across a subscription or management group, rejecting deployments that leave the public endpoint open even if a Private Endpoint also exists alongside it. NSG flow logs, ideally routed through Traffic Analytics, give the same audit trail as VPC Flow Logs.

On GCP, Organization Policy constraints — compute.vmExternalIpAccess to restrict external IPs, for example — apply the same "structurally impossible to misconfigure" enforcement. Teams increasingly pair Org Policy with PSC-only access patterns for specific services rather than relying on a single named constraint to do that job, and VPC Service Controls perimeters add a second, independent layer that holds even if an Organization Policy is misapplied or a resource is moved into an unexpected project.

The common thread: policy-as-code enforcement is what makes "private by convention" into "private by construction." A private endpoint that anyone can route around with a new public IP and a permissive IAM policy is documentation, not control.

A Decision Framework for Multi-Cloud Egress Control

Not every service needs the same treatment, and treating VPC Service Controls-grade isolation as the default for every managed service is its own kind of failure — operational cost with no corresponding risk reduction. Decide per service, using a short set of criteria:

  • Service type: first-party cloud API (S3, Key Vault, Cloud Storage) vs. partner/marketplace service vs. a custom internal service you're publishing to other teams or tenants. First-party APIs usually justify the lightest-weight option (gateway endpoint, Service Endpoint, Private Google Access); custom cross-account/cross-project services need the producer/consumer model (PrivateLink, Private Link, PSC).
  • Blast radius if exposed: a service holding secrets, PII, or financial data justifies interface/Private Endpoint plus a restrictive resource policy at minimum, and a service-control perimeter if the compliance framework demands defense against credential compromise, not just network compromise.
  • Compliance/audit requirements: if an auditor needs to demonstrate that a data store was never reachable from the public internet, Service Endpoints and Private Google Access alone are insufficient evidence for stores requiring IP-level isolation — Private Endpoint/interface endpoints with flow logs make the stronger claim.
  • Operational complexity budget: DNS zones, hub-spoke routing, and per-service policy tuning are ongoing maintenance, not one-time setup. A small platform team should not put every service behind a full private endpoint if same-VNet Service Endpoints or gateway endpoints cover the actual risk.

A workable per-service checklist: confirm whether the service supports a route-based option first (cheapest, least DNS overhead); if on-prem, cross-VNet, or cross-account reach is required, move to the interface/Private Endpoint/PSC tier; attach a resource-level policy scoped to the minimum actions and resources needed, never leave it default-open; verify DNS resolution from an actual workload, not a management console; and decide explicitly whether this service's data sensitivity warrants a perimeter control (VPC Service Controls or an SCP-enforced endpoint mandate) on top of the connectivity layer.

That last decision is the one worth revisiting rather than filing away. Each provider's Well-Architected guidance frames this as a structural property of the environment, checked repeatedly as new resource types and services are adopted — not a migration project with a defined end date. Every new managed service a team adopts is a fresh instance of the same question: does this need a private path, and if so, which tier, and what policy actually constrains it once it exists.

What to Do Next

Audit one production VPC or VNet for 0.0.0.0/0 egress rules and cross-reference against which AWS/Azure/GCP managed services your workloads actually call — that list is usually shorter than expected and is the immediate candidate set for gateway/interface endpoints or Private Endpoints. Enable VPC Flow Logs or NSG flow logs on whatever egress path exists today before changing anything, so you have a before/after baseline to compare traffic patterns against. Check whether any endpoint you've already deployed has a default (fully open) resource policy — this is the single most common gap and is usually a five-line Terraform fix once identified. Finally, if compliance requirements are driving this work, confirm with whoever owns the audit relationship whether IP-level private connectivity is sufficient evidence or whether a perimeter control (VPC Service Controls, or an SCP mandating endpoint-only access) is actually required — that answer changes the scope of the work substantially.
