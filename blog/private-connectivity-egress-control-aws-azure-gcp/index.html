PrivateLink vs Private Link vs VPC Service Controls: Egress Design

Cesar A. Nogueira
April 22, 2025 · 15 min read

Why NAT gateways and public IPs aren't an egress control strategy

Most VPC and VNet designs still route outbound traffic to managed services and third-party SaaS through a NAT gateway or internet gateway by default. That path works, but it means every call to a managed database endpoint, an object-store API, or a SaaS billing provider leaves the private network, transits the public internet (even if only for a few router hops before hitting the provider's edge), and re-enters through a public IP — regardless of whether both the caller and the callee sit inside the same cloud account or the same organization. The AWS Well-Architected Framework, the Azure Well-Architected Framework, and the Google Cloud Well-Architected Framework all converge on the same idea: minimize public exposure of resources and traffic as a security principle. None of them hands a platform team a single concrete implementation path — because there isn't one. Each provider ships a different primitive, and the primitives are not interchangeable.

The actual risk isn't abstract "traffic on the internet." It's blast radius. A workload with a route to 0.0.0.0/0, even one locked down with an egress security group rule scoped to a specific SaaS IP range, can be redirected by a compromised dependency, a misconfigured proxy, or an attacker who has gained code execution to reach any public endpoint that IP range happens to front — including one the attacker controls after a CNAME or IP reassignment. A NAT gateway with an "allow port 443 to *" rule is not an egress control, it is a statement that egress control has been deferred to whatever's on the other end. Private-endpoint mechanisms change the model: instead of filtering by destination IP on a shared public path, they make the approved destination privately routable and nothing else reachable from that route table entry at all. That's the property worth designing around, and it's also where AWS, Azure, and GCP diverge sharply enough that no single Terraform module or Sentinel policy can express all three. The rest of this piece works through each provider's model on its own terms, then the points where a platform team will get burned trying to treat them as equivalent.

AWS PrivateLink: interface endpoints and the ENI model

AWS PrivateLink works by placing an elastic network interface (ENI) with a private IP address directly inside the consumer's subnet. That ENI is the unit of control — not the VPC as a whole, not a route table entry pointing at a gateway. Traffic to the service resolves to that ENI's private IP and never leaves AWS's network fabric. AWS's documentation describes PrivateLink as a way to privately connect a VPC to services and resources without an internet gateway, NAT device, public IP, Direct Connect connection, or Site-to-Site VPN.

It's worth separating two things AWS bundles under "VPC endpoints." Interface endpoints are the actual PrivateLink mechanism — ENI-based, covering most AWS services plus third-party SaaS and cross-account services published as VPC endpoint services. Gateway endpoints are older, route-table-based, and limited to S3 and DynamoDB — no ENI, no PrivateLink DNS integration, just a prefix-list entry added to the route table that points at the service instead of the internet gateway. They solve a narrower problem more cheaply (no hourly or per-GB charge for the endpoint itself) but don't generalize the way interface endpoints do.

The enforcement layer that actually matters for egress control is the endpoint policy — a resource-based IAM policy attached to the interface endpoint itself, independent of the security group attached to the ENI. The security group controls what can reach the ENI on the network layer; the endpoint policy controls what API actions and resources are reachable once traffic arrives. Cross-account exposure (consuming a service published by another AWS account, or a SaaS vendor operating in their own account) requires the provider side to create a VPC endpoint service and explicitly allowlist the consuming account or principal — it isn't ambient the way public DNS resolution is.

A concrete example: an interface endpoint for AWS Secrets Manager, locked down with both an endpoint policy and a security group so the allowlist is enforced at two independent layers. The security group's ingress rule references aws_security_group.app_workload, which is defined later in this article under the deny-by-default egress pattern — the two snippets are meant to be combined, not applied in isolation. Because that pairing makes each security group reference the other, the ingress and egress rules below are written as standalone aws_security_group_rule resources rather than inline ingress/egress blocks: inline blocks are part of the parent aws_security_group resource itself, so two security groups with inline rules pointing at each other would form a dependency cycle Terraform can't resolve during plan/apply.

resource "aws_vpc_endpoint" "secretsmanager" {
  vpc_id              = aws_vpc.app.id
  service_name        = "com.amazonaws.${var.region}.secretsmanager"
  vpc_endpoint_type   = "Interface"
  subnet_ids          = aws_subnet.private[*].id
  security_group_ids  = [aws_security_group.secretsmanager_endpoint.id]
  private_dns_enabled = true

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = ["secretsmanager:GetSecretValue", "secretsmanager:DescribeSecret"]
      Resource  = "arn:aws:secretsmanager:${var.region}:${var.account_id}:secret:app/*"
      Condition = {
        StringEquals = { "aws:PrincipalAccount" = var.account_id }
      }
    }]
  })
}

resource "aws_security_group" "secretsmanager_endpoint" {
  name   = "secretsmanager-endpoint-sg"
  vpc_id = aws_vpc.app.id
}

resource "aws_security_group_rule" "secretsmanager_endpoint_ingress" {
  type                     = "ingress"
  from_port                = 443
  to_port                  = 443
  protocol                 = "tcp"
  security_group_id        = aws_security_group.secretsmanager_endpoint.id
  source_security_group_id = aws_security_group.app_workload.id
}

One prerequisite this snippet doesn't show: private_dns_enabled = true only takes effect if the VPC itself (aws_vpc.app) has both enable_dns_support and enable_dns_hostnames set to true. Without those two VPC-level attributes, the interface endpoint fails DNS validation regardless of this setting.

The endpoint policy restricts which secrets and actions are reachable through this specific ENI, regardless of the IAM permissions attached to the calling role — a second allowlist layer that only exists because PrivateLink makes the endpoint itself a policy attachment point.

Azure Private Link: private endpoints, mandatory DNS integration, and NSGs

Azure Private Link achieves a similar outcome — accessing PaaS services and partner services over a private endpoint in the consumer's virtual network, keeping traffic on Microsoft's backbone network instead of the public internet — but with a different cardinality. A Private Endpoint provisions a dedicated NIC, per resource instance, in the consumer's VNet. Where AWS's interface endpoint ENI is typically shared across a subnet or spread across availability zones for a single logical service, Azure's model attaches one NIC per private endpoint resource. That has direct IP-planning consequences: a subnet hosting private endpoints for a dozen storage accounts, key vaults, and SQL servers needs a dozen-plus IP addresses reserved for those NICs alone, and that count grows linearly with the number of resources you privately connect, not with the number of consuming subnets.

The part of Azure's model that causes the most production incidents is DNS. Private Link does not override public DNS resolution by itself — it depends on a Private DNS Zone linked to the consumer VNet (or an equivalent split-horizon DNS setup) that resolves the resource's existing public FQDN to the private endpoint's private IP instead. Skip that linking step, or get the zone name wrong, and the resource's public FQDN keeps resolving to its public IP. The private endpoint exists, traffic could use it, but nothing tells the client to. This is the single most common way teams believe they've eliminated public exposure and haven't: the control plane shows a healthy private endpoint, and the workload is still calling out over the internet path because DNS never got repointed.

There's a second, quieter gotcha alongside DNS: by default, NSGs (and user-defined routes) don't apply to traffic on a private endpoint's NIC at all. That enforcement only kicks in once "Private endpoint network policies" is explicitly enabled on the subnet hosting the private endpoint. A team that attaches an NSG to the subnet and assumes it's filtering private-endpoint traffic the same way it filters everything else on that subnet is often wrong — until network policies are turned on, the NSG simply isn't evaluated for that NIC, which is a second, independent way teams believe they have network-layer control over private endpoint traffic and don't.

Azure also has three mechanisms that sound like they overlap but sit at different layers. Network Security Groups (NSGs) filter traffic at the subnet or NIC level by IP, port, and protocol — they can block or allow egress, but they don't make a public service privately reachable. Azure Firewall does similar filtering centrally, often with FQDN-based rules, and can force traffic through a hub for inspection. Service endpoints extend the VNet's identity onto Azure backbone routing for a specific service, but the traffic can still traverse a path visible to the service's public endpoint — it doesn't provide the fully private, provider-side-published model that Private Link does. Service tags are a separate mechanism: a named alias for a service's published IP prefixes (e.g., Storage, Sql) used to simplify NSG, Azure Firewall, or route-table rules — they don't extend VNet identity or provide backbone routing on their own, they're just a rule-authoring shortcut. Only Private Link, correctly DNS-integrated, actually removes the public path; NSGs, Azure Firewall, and service endpoints filter or route what's already there.

Azure also has a more recent, perimeter-shaped control worth flagging: Network Security Perimeter (NSP). It's a newer addition to Azure's toolkit aimed at applying perimeter-style governance around PaaS resources rather than purely routing-based control. It's still evolving, and its detailed access-rule model and regional availability aren't covered by the Private Link overview cited in this article — verify the current mechanics against Microsoft's own Network Security Perimeter documentation before relying on it in a design. What's worth taking away conceptually is narrower than the mechanics: Azure isn't limited to NSGs, Firewall, and service endpoints — it also has a perimeter-shaped primitive, which matters when comparing it against GCP's perimeter model below, where "perimeter-level control" is often treated as a GCP-only concept.

Finally, Microsoft's naming splits provider and consumer roles in a way that trips people up: a Private Link service is what a service owner creates to publish their service for private consumption (the equivalent of an AWS VPC endpoint service), while a Private Endpoint is what a consumer creates in their own VNet to reach it (the equivalent of an AWS interface endpoint). Reading "Private Link" and "Private Endpoint" as synonyms in a design doc is a reliable way to misconfigure which side owns which piece.

GCP VPC Service Controls: perimeters instead of endpoints

GCP's core private-connectivity model breaks the endpoint pattern entirely. VPC Service Controls is not an endpoint mechanism — there's no ENI or NIC standing in for a service. It defines a service perimeter around one or more projects, and the control point becomes "which identity, calling which API, from which network context, is allowed to cross this perimeter" rather than "which interface does the packet route to." That's a fundamentally API/identity-centric model layered on top of the network, not a network-layer substitute for a public route — and, as the Network Security Perimeter note above shows, GCP is no longer the only provider with a perimeter-shaped primitive, even though VPC-SC remains the more mature, identity/API-centric version of the idea.

This leads teams toward the wrong primitive constantly, because GCP actually ships three related-but-distinct mechanisms and they get conflated:

  • Private Google Access lets VM instances without external IP addresses reach Google APIs and services over Google's internal network — it's a routing/DNS configuration on a subnet, not an access-control boundary.
  • Private Service Connect is the closest GCP equivalent to AWS PrivateLink and Azure Private Link — it publishes a service (Google-owned or third-party) as an internal IP endpoint inside the consumer's VPC.
  • VPC Service Controls is the perimeter-level control that restricts data exfiltration by governing which resources and API calls can cross a defined boundary, independent of how the network path got there.

A team that reaches for VPC-SC to solve "how do we call BigQuery without a public IP" is solving the wrong problem — that's Private Google Access or Private Service Connect. A team that reaches for Private Service Connect to stop a compromised service account from copying data to an external project is solving the wrong problem too — that requires a perimeter.

VPC-SC's failure modes are asymmetric and both dangerous in different ways. An overly strict perimeter breaks legitimate cross-project calls immediately and loudly — a data pipeline that reads from one project and writes to another suddenly gets PERMISSION_DENIED errors, someone notices within minutes, and it gets fixed. A missing or incomplete perimeter is the opposite: it fails silently. Nothing breaks, nothing errors, and a path to exfiltrate data to an unauthorized project or the public internet just sits there unused until someone (ideally your security team, not an attacker) finds it. That asymmetry means perimeter configuration needs deliberate negative testing — actively attempting known-bad cross-project calls in a non-production perimeter and confirming they're denied — not just confirming that legitimate calls succeed.

For the legitimate exceptions that do need to cross a perimeter, GCP provides perimeter bridges (allowing specified projects on either side of separate perimeters to interact) and access levels via context-aware access (conditions like source IP range, device policy, or identity that grant access to a perimeter from outside it). Both are effectively firewall-rule-equivalent trust decisions and should go through the same change-review process as a firewall rule change — an access level added without review is exactly the kind of quiet exfiltration path VPC-SC exists to prevent.

Where the three models actually diverge

Laid side by side, the differences are structural, not cosmetic:

| Dimension | AWS PrivateLink | Azure Private Link | GCP VPC Service Controls | |---|---|---|---| | Unit of control | ENI (interface endpoint) | Per-resource NIC (private endpoint) | API-level project perimeter | | DNS requirement | Optional but recommended (private_dns_enabled) | Mandatory (Private DNS Zone linking) for correctness | Not endpoint-based; N/A | | Cross-account/org | Endpoint service + explicit allowlist | Private Link service + explicit approval | Perimeter bridges + access levels | | Perimeter-level control | No direct equivalent (endpoint policies are per-resource, not a project-wide boundary) | Network Security Perimeter (newer, perimeter-style control; verify current mechanics against Microsoft docs) | VPC Service Controls (identity/API-context perimeter) | | Default posture | Default-deny once endpoint replaces public route | Default-allow public FQDN until DNS is fixed | Default-allow until perimeter is defined |

The most dangerous shared failure mode is the silent fallback to a public path. Azure's DNS-dependency issue is the clearest example — a misconfigured Private DNS Zone doesn't throw an error, it just leaves the public FQDN resolving publicly. AWS has an analogous risk if private_dns_enabled is left false or a client hardcodes the public regional endpoint instead of using the service's DNS name — the interface endpoint exists and works, but nothing forces traffic onto it. GCP's version is a perimeter that was never extended to cover a newly created project, so calls that should be blocked simply aren't yet, with no signal that anything is missing. None of these fail closed by default; they all require someone to verify the private path is actually being used, not just provisioned.

This is exactly why an AWS PrivateLink allowlist design — endpoint policy plus security group — cannot be transliterated into Azure or GCP configuration. The enforcement point sits in a structurally different place in each model: a resource-attached IAM-style policy on an ENI in AWS, a DNS-resolution correctness problem plus NSG filtering (itself conditional on network policies being enabled) in Azure, and an identity/API perimeter with no per-connection artifact at all in GCP. A platform team that builds tooling assuming "endpoint policy" is a universal concept will find nothing to attach it to in GCP's perimeter model.

A deny-by-default egress pattern, implemented per cloud

The pattern that holds across all three, even though the implementation doesn't, is deny-by-default egress at the network layer plus an explicit allowlist of private endpoints or perimeters for approved destinations. Concretely: no default route to an internet gateway or NAT device from workload subnets, and network-layer egress rules that only permit traffic to the ENIs, NICs, or API surfaces that have been explicitly provisioned.

Extending the earlier AWS example, a VPC with private workload subnets that have no route to a NAT gateway at all, and a workload security group whose only egress path targets the endpoint's security group — again expressed as a standalone aws_security_group_rule rather than an inline block, to avoid a cycle with aws_security_group.secretsmanager_endpoint defined earlier:

resource "aws_route_table" "private_no_internet" {
  vpc_id = aws_vpc.app.id
  # Deliberately no 0.0.0.0/0 route via nat_gateway_id or internet_gateway_id
}

resource "aws_security_group" "app_workload" {
  name   = "app-workload-sg"
  vpc_id = aws_vpc.app.id
  # No 0.0.0.0/0 egress rule — anything not an approved endpoint is unreachable
}

resource "aws_security_group_rule" "app_workload_egress_secretsmanager" {
  type                     = "egress"
  from_port                = 443
  to_port                  = 443
  protocol                 = "tcp"
  security_group_id        = aws_security_group.app_workload.id
  source_security_group_id = aws_security_group.secretsmanager_endpoint.id
}

Any service the workload needs that isn't fronted by an interface endpoint simply won't be reachable, which forces the dependency inventory to be explicit rather than discovered later via a NAT gateway bill or a security incident.

The equivalent enforcement points to replicate elsewhere: in Azure, an NSG with a deny-all outbound rule as the last priority, paired with Private Endpoints (and correctly linked Private DNS Zones, plus network policies enabled on the subnet so the NSG actually governs the private endpoint NIC) for every approved PaaS dependency; in GCP, VM instances provisioned with no external IP addresses at all, combined with Private Service Connect endpoints for approved services and a VPC Service Controls perimeter around the projects holding sensitive data. None of these three configurations share a Terraform module, a policy file, or even a mental model beyond "default deny, explicit allow" — but that shared intent is what a platform team should be validating, not a shared implementation.

Provisioning correctly is necessary but not sufficient. VPC Flow Logs, Azure VNet Flow Logs (Microsoft's currently recommended flow-log mechanism), and GCP VPC Flow Logs are the mechanism to catch a route or rule that reopens a public egress path after the fact — someone adds a NAT gateway route for a debugging session and forgets to remove it, someone adds an overly broad NSG rule, someone widens a VPC-SC access level. Flow log analysis run continuously (not just checked at deploy time) is what catches drift between the design and the live state.

Sequencing the rollout: per-cloud primitives before cross-cloud policy

The practical rollout order is to fully validate the native primitive on one cloud — including the DNS behavior and the failure modes described above — before attempting to unify policy across providers. Trying to design a cross-cloud abstraction first tends to produce a lowest-common-denominator policy that doesn't actually use any provider's strongest guarantees, because the abstraction has to avoid assuming features one provider lacks.

A workable checklist:

  1. Inventory every SaaS and managed-service dependency each workload actually calls — not the ones assumed, the ones observed in flow logs or egress traffic over a real measurement window.
  2. Map each dependency to its cloud-native private-connectivity primitive: AWS interface endpoint or gateway endpoint, Azure Private Endpoint with DNS zone, or GCP Private Service Connect / Private Google Access, and decide whether it also needs a VPC-SC perimeter (or, on Azure, a Network Security Perimeter).
  3. Enforce the resulting design with policy-as-code per provider — OPA or Conftest against Terraform plans for AWS and GCP, Sentinel policies in Terraform Cloud, or Azure Policy definitions for NSG and Private Endpoint requirements — rather than relying on manual review to catch a missing endpoint policy or an unlinked DNS zone.
  4. Validate continuously, not just at provisioning time: scheduled checks that attempt known-bad cross-perimeter or cross-account calls and confirm they fail, alongside flow log review for any egress path that reappears.

A shared policy language or a unified dashboard can reasonably sit on top of all three clouds' egress posture, reporting compliance in one place. What doesn't transfer is the enforcement mechanism itself — the ENI, the per-resource NIC and DNS zone, and the API perimeter are different enough in kind that porting a design 1:1 from one cloud to the next will leave a gap, usually the quiet kind that doesn't show up until an audit or an incident finds it.
