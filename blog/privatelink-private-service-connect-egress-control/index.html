PrivateLink, Private Link, and PSC: Egress Without NAT

Cesar A. Nogueira
April 22, 2025 · 13 min read

1. NAT gateways and internet gateways solve the wrong problem for managed-service traffic

Most private-subnet egress designs start with a NAT gateway or a NAT instance because it's the default answer to "how do workloads with no public IP reach the internet." That default works fine for genuinely internet-bound traffic — package repositories, arbitrary third-party APIs — but it's a poor fit for the traffic that actually dominates in a cloud-native workload: calls to the provider's own managed services (object storage, secrets managers, message queues) and to a small set of well-known SaaS APIs. Routing that traffic through a NAT device forces a binary choice: either open a broad 0.0.0.0/0 egress rule and rely on the NAT device or a downstream proxy to sort out what's actually allowed, or try to maintain IP-based allow-lists for services whose endpoints are shared across every tenant on the platform and rotate without notice. Both options are bad. The first abandons any meaningful egress control at the network layer. The second is a maintenance trap — cloud providers publish IP ranges for services like S3 or Azure Storage precisely because those ranges change often enough that hardcoding them breaks connectivity on a schedule you don't control.

There's also a cost and scaling dimension that gets underweighted in the initial design conversation. NAT gateways bill per-GB processed in addition to an hourly charge, and every workload behind the NAT shares its throughput ceiling. In a high-fan-out environment — dozens of services in a cluster all talking to a managed database, a queue, and a handful of SaaS integrations — the NAT gateway becomes both a cost center and a single choke point that shows up in latency graphs under load. None of this is a new observation, but it's worth stating plainly because it reframes what "egress control" should mean. A firewall rule keyed on destination IP can't express "this specific workload may reach this specific service and nothing else on that provider's platform" — it can only express "this workload may or may not reach this IP range," which is a coarser and more fragile statement. The three private-connectivity mechanisms covered here — AWS PrivateLink, Azure Private Link, and Google Private Service Connect (PSC) — exist to make the finer-grained statement possible, by turning "can this workload reach that service" into a question you answer per endpoint rather than per subnet or per route table.

2. Three implementations, one underlying model

All three clouds converge on the same shape: a private, provider-backbone path between a specific consumer network and a specific published service, with no traversal of an internet gateway, NAT device, or public IP anywhere in the path.

AWS PrivateLink works through interface VPC endpoints — each one provisions an elastic network interface (ENI) directly in your consumer subnet, with a private IP drawn from that subnet's CIDR. On the producer side, the service being exposed sits behind a Network Load Balancer (or Gateway Load Balancer, for appliance-style services) and is published as a VPC endpoint service. AWS's own framing is worth quoting directly: PrivateLink lets you "privately connect your VPC to services and resources as if they were in your VPC," without an internet gateway, NAT device, public IP, Direct Connect, or Site-to-Site VPN — and because the connection is scoped to a specific endpoint, "you control the specific API endpoints, sites, services, and resources that are reachable from your VPC" (What is AWS PrivateLink?). AWS-native services, endpoint services hosted by other AWS accounts, and AWS Marketplace partner services all use the identical mechanism.

Azure Private Link uses a private endpoint — a network interface with an IP allocated from your VNet — mapped either to a Private Link service (the Azure equivalent of a producer-published custom service) or directly to a PaaS resource such as a Storage Account or Key Vault. Microsoft's documentation describes it the same way: "Traffic between your virtual network and the service travels the Microsoft backbone network. Exposing your service to the public internet is no longer necessary" (What is Azure Private Link?). The distinguishing feature on Azure's side is an explicit connection-approval workflow between consumer and provider, discussed more in section 4.

Google Private Service Connect splits the model into consumer endpoints — internal IP addresses backed by forwarding rules — reaching producer services that are published via a service attachment. PSC also supports "PSC interfaces," a mechanism for producer-side workloads to reach into a consumer VPC for cases that need more than a simple client-to-service call. Google's documentation frames Private Service Connect as connectivity for consuming and producing services privately from a VPC network (Private Service Connect overview).

The common thread across all three is worth stating explicitly because it's the thing that makes this a different security model, not just a networking optimization: the connection is scoped to a single service, not to a network. A PrivateLink endpoint, a Private Link private endpoint, or a PSC forwarding rule each represents one specific, nameable relationship between a consumer and a producer — which is exactly the granularity a perimeter firewall rule can't express.

3. Standing up a private endpoint in each cloud

The Terraform shape is similar across providers: a consumer-side resource that creates the private network interface, plus references back to the producer-side service being consumed.

AWS — an interface VPC endpoint for S3 (or a partner PrivateLink service), attached to a private subnet and gated by a security group:

resource "aws_vpc_endpoint" "s3_interface" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.eu-west-1.s3"
  vpc_endpoint_type    = "Interface"
  subnet_ids           = [aws_subnet.private_a.id, aws_subnet.private_b.id]
  security_group_ids   = [aws_security_group.s3_endpoint.id]
  private_dns_enabled  = true
}

resource "aws_security_group" "s3_endpoint" {
  name   = "s3-endpoint-sg"
  vpc_id = aws_vpc.main.id

  ingress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.app.id]
  }
}

Worth flagging since S3 is the example above: S3 and DynamoDB are the two services that also support Gateway Endpoints — a separate, non-PrivateLink mechanism that adds a route via a prefix list in the subnet's route table instead of provisioning an ENI, and carries no hourly or per-GB charge. For pure in-VPC access to S3 or DynamoDB, the Gateway Endpoint is the default choice; the Interface Endpoint shown above earns its cost when you need on-premises/Direct Connect/Transit Gateway reachability, cross-region access, or want a single endpoint type for consistency with the other PrivateLink-backed services in the environment.

Azure — a private endpoint targeting a Storage Account, with the private DNS zone group linked so the storage account's public hostname resolves to the private IP:

resource "azurerm_private_endpoint" "storage_pe" {
  name                = "pe-storage-account"
  location            = azurerm_resource_group.main.location
  resource_group_name = azurerm_resource_group.main.name
  subnet_id           = azurerm_subnet.private_endpoints.id

  private_service_connection {
    name                           = "storage-privateserviceconnection"
    private_connection_resource_id = azurerm_storage_account.main.id
    subresource_names              = ["blob"]
    is_manual_connection           = false
  }

  private_dns_zone_group {
    name                 = "storage-dns-zone-group"
    private_dns_zone_ids = [azurerm_private_dns_zone.blob.id]
  }
}

GCP — a PSC forwarding rule pointed at a service attachment, using INTERNAL load balancing scheme:

resource "google_compute_address" "psc_endpoint_ip" {
  name         = "psc-endpoint-ip"
  subnetwork   = google_compute_subnetwork.private.id
  address_type = "INTERNAL"
  region       = "europe-west1"
}

resource "google_compute_forwarding_rule" "psc_endpoint" {
  name                    = "psc-forwarding-rule"
  region                  = "europe-west1"
  network                 = google_compute_network.main.id
  ip_address              = google_compute_address.psc_endpoint_ip.id
  load_balancing_scheme   = "" # empty string required for PSC consumer endpoints
  target                  = google_compute_service_attachment.producer.id
}

Every one of these examples needs a producer-side counterpart — accepting the connection, in the case of a custom PrivateLink or Private Link service, or simply publishing the platform PaaS resource for a first-party service like S3 or Storage Accounts, where the "acceptance" is implicit. That pairing — an explicit consumer-side resource plus an explicit producer-side publication or approval step — is what keeps the model endpoint-scoped. There's no way to accidentally create a private endpoint that reaches "everything in the provider's network"; each one is bound to exactly one service.

4. Egress control moves next to the service, not the perimeter

Once you have endpoints, the interesting part is what policy can attach to them, because each provider gives you a distinct enforcement point that has no equivalent in a plain security-group/route-table model.

On AWS, VPC endpoints accept an endpoint policy — an IAM-style JSON document attached directly to the endpoint that restricts which API actions or resources are reachable through it, independent of any security group or NACL sitting on the ENI. A typical restrictive S3 endpoint policy only allows s3:GetObject on a named bucket ARN:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": ["s3:GetObject", "s3:ListBucket"],
      "Resource": [
        "arn:aws:s3:::app-artifacts-bucket",
        "arn:aws:s3:::app-artifacts-bucket/*"
      ]
    }
  ]
}

That policy means the endpoint itself refuses any S3 call outside that one bucket, even if the security group and IAM role attached to the calling instance would otherwise permit it — a second, independent layer of control that lives on the network path rather than the identity path.

On Azure, the enforcement point is the connection itself: a private endpoint request to a Private Link service starts in a Pending state and must be explicitly Approved by the resource owner, unless the owner has pre-authorized specific subscription or resource IDs for auto-approval. Network security groups on the private endpoint subnet add a second layer, though NSGs are disabled by default on private endpoint NICs and have to be deliberately enabled.

On GCP, service attachments carry consumer accept and reject lists — you specify which consumer projects or networks are permitted, and the attachment's acceptance setting governs whether unlisted consumers get through — a control point that sits on the connection itself rather than in a firewall rule. Consumer-side firewall rules on the internal forwarding rule provide a second layer, matching the AWS and Azure pattern of endpoint-level plus network-level control.

The payoff of all three models is the same: an auditor asking "what can workload X reach outside its own VPC/VNet" no longer has to parse a firewall rule table cross-referenced against a list of provider IP ranges. They can enumerate the endpoints attached to that workload's subnet and read the policy or approval state on each one directly.

5. DNS is where private connectivity quietly breaks

The most common way this model fails in practice has nothing to do with the endpoint itself — it's DNS. A private endpoint only replaces the public routing path if the service's public hostname also resolves to the private endpoint's IP address from inside the consumer network. Get that wrong and the endpoint sits there fully provisioned and completely unused, while traffic keeps flowing out the NAT gateway to the public IP because that's what the hostname still resolves to.

Each provider solves this with private DNS: AWS uses private hosted zones (and the private_dns_enabled flag on the endpoint, as in the Terraform example above) so that s3.eu-west-1.amazonaws.com resolves privately inside the VPC; Azure uses private DNS zones linked via a private_dns_zone_group, matching the zone name to the specific PaaS subresource (privatelink.blob.core.windows.net for blob storage, for instance); GCP uses Cloud DNS private zones. In every case, the DNS association is a separate resource from the endpoint itself, and it's entirely possible to provision the network path correctly while forgetting the DNS half.

The failure mode gets worse in hub-spoke or Shared VPC topologies. A private DNS zone created in a hub VNet or a Shared VPC host project isn't automatically usable by every spoke — Azure requires explicit VNet links from each spoke VNet to the private DNS zone, and GCP requires explicit DNS peering or the private zone to be visible in the Shared VPC's DNS policy. Skip that step for one spoke and workloads there silently fall back to public DNS resolution and public routing, with no error at the network layer — the connection simply succeeds over the internet path instead of the private one, which is the opposite of a fail-closed outcome. Cross-account (AWS), cross-subscription (Azure), or cross-project (GCP) consumption has the same trap: the DNS zone has to be shared or replicated into every consuming account alongside the endpoint, and it's easy to provision the endpoint during a multi-account rollout while forgetting that the DNS side needs the same fan-out. In practice, split-horizon DNS misconfiguration — not endpoint misconfiguration — is the most frequent root cause when a team reports that "PrivateLink isn't working."

6. Making endpoint traffic auditable

Because each private connection is a distinct, nameable resource, the observability story is naturally per-endpoint rather than per-subnet, which is a meaningful improvement for anyone who has to produce audit evidence.

On AWS, VPC Flow Logs and CloudTrail both record VPC endpoint traffic with endpoint-specific identifiers, and PrivateLink exposes its own CloudWatch metrics (connection counts, bytes processed, RST packets) separate from general ENI-level metrics — so you can look at one endpoint's traffic in isolation rather than filtering it out of a subnet-wide flow log. On Azure, NSG flow logs on the private endpoint subnet combine with Private Link's own diagnostic logs and the connection state field (Approved, Pending, Rejected, Disconnected) to give a per-endpoint audit trail that includes not just traffic volume but the approval history of the connection itself. On GCP, VPC Flow Logs plus PSC connection status give the same per-endpoint visibility, and teams running VPC Service Controls can layer a service-perimeter boundary on top of PSC connections as an additional data-exfiltration control, independent of the PSC policy itself.

The structural benefit shows up most clearly at audit time. Instead of handing an auditor a firewall rule set and asking them to trace which rules apply to which workloads and what those destination IPs actually resolve to, the artifact becomes a list: these are the endpoints attached to this environment, this is the policy or approval state on each, and here is the traffic log filtered to that endpoint's identifier. It's a materially smaller and more direct thing to review, and it maps cleanly onto access-review requirements from frameworks like those referenced in the AWS, Azure, and Google Cloud Well-Architected guidance, all of which treat least-privilege network access as a first-class design pillar rather than an afterthought.

7. Migrating off NAT without a big-bang cutover

None of this requires ripping out NAT gateways in one change window, and attempting that is the fastest way to break something. The practical path is incremental.

Start by mining existing VPC Flow Logs (or the Azure/GCP equivalents) for the actual destinations current NAT or internet-gateway traffic is hitting. Rank those destinations by volume and by whether the destination is a managed service or well-known SaaS API with direct PrivateLink, Private Link, or PSC support — that's the traffic with the clearest migration path and the best cost payoff, since (with the exception of the free S3/DynamoDB Gateway Endpoints noted in section 3) these endpoints carry their own hourly charge plus per-GB data processing fees on top of that. Migrating a rarely-used integration to a private endpoint can cost more than it saves; migrating a high-fan-out path like application-to-secrets-manager or application-to-message-queue traffic, where dozens of workloads hit the same destination constantly, is where an Interface Endpoint's cost is easiest to justify against the NAT gateway's per-GB processing cost and throughput ceiling. For pure VPC-to-S3 or VPC-to-DynamoDB traffic specifically, check for the free Gateway Endpoint first — it's usually the more economical move off NAT, and a priced Interface Endpoint for those two services is only worth it for the on-premises/cross-region/consistency cases described above.

During migration, run the NAT path and the private endpoint in parallel rather than cutting over the route table immediately — deploy the endpoint, confirm DNS resolves privately (verify with dig or nslookup from inside the subnet, not just from a jump host that might have different resolver settings), and confirm traffic is actually flowing over the endpoint using the per-endpoint metrics or flow logs from section 6 before touching anything else. Only once that's confirmed should you tighten the route table or remove the 0.0.0.0/0 route for the migrated destination — and even then, only for that specific destination, not as a blanket change.

It's worth being explicit that this model complements NAT rather than replacing it outright. Any destination that's a genuinely arbitrary public endpoint — a customer's webhook receiver, a long-tail SaaS integration with no PrivateLink/Private Link/PSC offering — still needs a NAT or explicit forward-proxy egress path. The end state for most environments isn't "no NAT gateway," it's a NAT gateway with a much smaller, well-understood set of destinations behind it, and a growing set of high-value destinations moved onto endpoint-scoped private connectivity instead.

What to do next

  • Pull a week of VPC Flow Logs (or NSG/VPC equivalent) and group by destination to find your highest-volume NAT/IGW-bound traffic — that's your migration priority list, not a guess.
  • Before creating any endpoint, confirm the target service actually publishes a PrivateLink/Private Link/PSC integration; not every managed service does, and Marketplace/partner support varies by provider. For S3 and DynamoDB specifically, check whether a free Gateway Endpoint covers the use case before provisioning a priced Interface Endpoint.
  • When you stand up the first endpoint in a new environment, verify DNS resolution privately from inside the actual subnet before declaring success — this is the step most likely to be silently wrong.
  • For hub-spoke or Shared VPC layouts, audit DNS zone associations (VNet links / DNS peering) across every spoke before assuming the private path is live everywhere it should be.
  • Add endpoint policies (AWS), connection approval allow-lists (Azure), or consumer allow-lists (GCP) from day one rather than leaving endpoints open and tightening later — it's a much smaller change to write a scoped policy up front than to retrofit one onto live traffic.
