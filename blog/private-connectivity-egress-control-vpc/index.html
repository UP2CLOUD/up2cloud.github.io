Private Connectivity and Egress Control for Cloud VPCs

Cesar A. Nogueira
April 22, 2025 · 12 min read

Why Default Internet Routing Is a Liability, Not a Convenience

Provision a VPC from any starter template — Terraform module, cloud console wizard, eksctl — and the resulting network topology almost always assumes the internet as the default transport. Private subnets get a route table entry pointing 0.0.0.0/0 at a NAT gateway; the NAT gateway sits in a public subnet behind an internet gateway. That path exists so that instances with no public IP can still pull OS patches, call pip install, or reach the AWS/GCP control plane. It works, and it's the path of least resistance, which is exactly the problem: it becomes the default even for traffic that has no business touching the public internet at all.

Two distinct risks fall out of this. The first is outbound: once a workload can reach 0.0.0.0/0 on port 443, a compromised process — a vulnerable dependency, a supply-chain-poisoned package, an SSRF turned into a pivot — has a ready-made channel for command-and-control callbacks or bulk data exfiltration to an attacker-controlled endpoint. A NAT gateway performs address translation; it does not perform intent-based filtering. Unless you bolt on egress restrictions separately, "instances can reach the internet to patch themselves" and "instances can reach any host on the internet on any port" are the same rule.

The second risk sits on the inbound side of the equation, and it's easier to miss because it doesn't look like a firewall gap. When a private subnet resolves s3.amazonaws.com, secretmanager.googleapis.com, or a partner SaaS API to a public IP and routes there via the same NAT path, you're depending on that service's public endpoint, its TLS posture, and its IAM/network ACL controls as your only perimeter. There's no network-layer guarantee that traffic stays inside the cloud provider's backbone, and no way to enforce "only this VPC's resources may call this specific bucket" at the network layer — you're relying entirely on identity policy.

The fix for both is the same idea applied in two directions: replace implicit, internet-routed reachability with explicit connectivity primitives. For inbound access to managed and partner services, that means AWS PrivateLink-backed VPC endpoints or Google's Private Service Connect. For outbound, it means NAT gateways paired with allow-lists rather than NAT gateways as an all-you-can-eat internet on-ramp. Neither is a checkbox — both require you to enumerate what your workloads actually need to reach, which is the real work of least-privilege network design.

Inbound to Managed Services: AWS PrivateLink and VPC Endpoints

AWS gives you two distinct mechanisms under the VPC endpoint umbrella, and conflating them leads to either wasted spend or missed coverage.

Gateway endpoints exist only for S3 and DynamoDB. They're free, and they work by inserting a route table entry that directs traffic destined for the service's IP prefix list to a gateway target instead of the NAT device — no ENI, no per-AZ resource, no additional latency. If your workload's only private-connectivity need is S3 or DynamoDB, start here.

Interface endpoints are the PrivateLink mechanism proper: an elastic network interface with a private IP, deployed into your subnet, fronting the target service. According to AWS, PrivateLink lets you "privately connect your VPC to services and resources as if they were in your VPC" without an internet gateway, NAT device, public IP, Direct Connect, or Site-to-Site VPN — and because you explicitly create each endpoint, "you control the specific API endpoints, sites, services, and resources that are reachable from your VPC." That's the load-bearing sentence for a least-privilege design: reachability becomes an explicit allow-list of endpoints rather than an implicit "anything routable."

Interface endpoints cover the vast majority of AWS services (Secrets Manager, KMS, SQS, SNS, ECR, CloudWatch Logs, Bedrock, and hundreds more), services published by other AWS accounts via their own VPC endpoint services, and AWS Marketplace partner services — the same underlying primitive serves all three use cases.

Two features make PrivateLink usable at scale rather than just theoretically private:

Endpoint policies are IAM-style JSON policies attached directly to the endpoint resource. They're a second enforcement layer that's independent of the caller's IAM identity policy — even if a role's IAM policy permits secretsmanager:GetSecretValue on every secret in the account, an endpoint policy can restrict what's reachable through that specific network path to a named set of secret ARNs. This matters because IAM policy and network policy fail differently: a misconfigured IAM policy is often the first thing compromised in a credential-theft scenario, but the endpoint policy still gates what the network path itself will carry.

Private DNS integration rewrites the standard public service hostname (e.g., secretsmanager.us-east-1.amazonaws.com) to resolve to the endpoint's private IP inside the VPC, when enabled on the endpoint. Applications and SDKs keep using the same hostname they always have — no code changes, no custom endpoint URLs hardcoded into application config. This is usually the difference between a migration that ships in an afternoon and one that requires touching every service's client configuration.

A representative Terraform snippet for an interface endpoint with a scoped policy:

resource "aws_vpc_endpoint" "secrets_manager" {
  vpc_id              = aws_vpc.main.id
  service_name        = "com.amazonaws.${var.region}.secretsmanager"
  vpc_endpoint_type    = "Interface"
  subnet_ids           = aws_subnet.private[*].id
  security_group_ids   = [aws_security_group.vpce.id]
  private_dns_enabled  = true

  policy = jsonencode({
    Version = "2012-10-17"
    Statement = [{
      Effect    = "Allow"
      Principal = "*"
      Action    = "secretsmanager:GetSecretValue"
      Resource  = "arn:aws:secretsmanager:${var.region}:${var.account_id}:secret:prod/*"
    }]
  })
}

Inbound on Google Cloud: Private Service Connect and VPC Service Controls

Google Cloud's analogue to PrivateLink is Private Service Connect (PSC), and the mental model transfers directly: PSC endpoints are internal IP addresses in your VPC that forward traffic to a published service — either a Google API bundle or a service published by another VPC (your own, a partner's, or a third-party vendor's) as a PSC service attachment. As with PrivateLink, traffic never traverses the public internet path and never needs a NAT gateway or external IP on the consuming resource.

Before reaching for full PSC, most workloads need only Private Google Access, which is the baseline mechanism for letting resources without external IP addresses reach Google APIs (Cloud Storage, BigQuery, Pub/Sub, and so on) over Google's internal network. It's a subnet-level setting rather than a per-service endpoint, so it's the cheapest and lowest-effort layer to enable first; PSC endpoints become worth the extra resource overhead when you need per-service DNS control, connections to a specific third-party SaaS producer, or cross-VPC service publishing that Private Google Access doesn't cover.

Where GCP diverges structurally from AWS is VPC Service Controls, and it's worth being precise about what layer it operates at because it's easy to conflate with PSC. PSC controls the network path — whether traffic can reach a service without transiting the public internet. VPC Service Controls defines a data perimeter around a set of Google Cloud resources (typically grouped by project or VPC) that restricts which API calls can cross the perimeter boundary, independent of whether the caller has valid IAM credentials. A service account with roles/storage.objectViewer on a bucket inside the perimeter still can't exfiltrate that data to a client running outside the perimeter — the perimeter denies the call regardless of whether the caller has valid IAM permissions to access the underlying resource. This closes a specific attack class that identity-only controls can't: a stolen service account key or a compromised workload that has legitimate IAM permissions but is trying to move data somewhere outside the trust boundary.

The two compose rather than substitute for each other: PSC gets you a private network path to Google APIs and published services; VPC Service Controls constrains what data can leave the perimeter regardless of which path it takes. A workload can have a perfectly private PSC endpoint to Cloud Storage and still be blocked from returning data to a caller outside the perimeter — that's VPC Service Controls doing its job, not a misconfiguration.

Configuring Least-Privilege Egress: NAT Gateways and Explicit Allow-Lists

Private connectivity primitives solve inbound reachability to known managed services. They don't solve the general case of a workload that legitimately needs outbound internet access — pulling container images from a public registry, calling a third-party API with no PrivateLink/PSC offering, fetching OS updates. For that traffic, the NAT gateway is still the right primitive, but it needs to be paired with explicit restriction rather than left as an open pipe.

AWS's own documentation describes the default behavior plainly: a public NAT gateway lets "instances in private subnets connect to the internet through a public NAT gateway, but the instances can't receive unsolicited inbound connections from the internet," per the NAT gateway documentation. That's directional control only — it says nothing about which outbound destinations or ports are permitted, which is the gap security groups and NACLs need to close.

resource "aws_route" "private_egress" {
  route_table_id         = aws_route_table.private.id
  destination_cidr_block = "0.0.0.0/0"
  nat_gateway_id          = aws_nat_gateway.this.id
}

resource "aws_security_group" "app" {
  name   = "app-scoped-egress"
  vpc_id = aws_vpc.main.id

  # Allow HTTPS only to a known partner API range, not the whole internet
  egress {
    from_port   = 443
    to_port     = 443
    protocol    = "tcp"
    cidr_blocks = ["203.0.113.0/24"]
  }

  # Allow HTTPS to the VPC endpoint SG for AWS services, no public CIDR needed
  egress {
    from_port       = 443
    to_port         = 443
    protocol        = "tcp"
    security_groups = [aws_security_group.vpce.id]
  }
}

The gap this leaves is destination-IP volatility: package registries, CDN-fronted APIs, and SaaS vendors often rotate IPs behind names like registry.npmjs.org or pypi.org, so a CIDR-based security group either breaks unpredictably or has to stay wide enough to be nearly useless. That's the case for a proxy-based egress layer — a Squid forward proxy or a managed egress firewall (AWS Network Firewall, GCP Secure Web Proxy) — that filters on FQDN/SNI rather than IP, sitting between the private subnet and the NAT path. The NAT gateway still performs the address translation to the internet; the proxy is what actually enforces "only these hostnames" as policy, and it's the layer worth auditing when the request is "why did this workload talk to a domain nobody recognizes."

Two further placement decisions matter operationally. First, per-subnet (or per-team/per-environment) NAT gateway placement contains blast radius: if one team's workload gets compromised and starts hammering an exfiltration destination, a shared NAT gateway makes it harder to attribute and rate-limit that traffic without affecting every other tenant behind it. Second, per-NAT-gateway cost and traffic metrics (CloudWatch BytesOutToDestination, VPC Flow Logs filtered by ENI) give you a cost-attribution signal for free that a shared gateway doesn't.

Private Cross-VPC and Partner Connectivity Without Peering Sprawl

Connecting workloads across VPC boundaries — to another business unit's VPC, a partner's environment, or a multi-account landing zone — has three broad architectural options, and they scale very differently.

VPC peering gives full L3 reachability between two VPCs' CIDR ranges. It's simple to reason about for a single pair, but it doesn't transit — peering connection A↔B and B↔C doesn't let A reach C — so any many-to-many topology devolves into a mesh of point-to-point connections that becomes unmanageable past a handful of VPCs, and each peered VPC gets full network reachability to the other's address space unless you layer route tables and security groups carefully on top.

Transit Gateway (AWS) or Network Connectivity Center (GCP) solves the mesh problem with a hub-and-spoke model: each VPC attaches once, and route tables on the hub control which spokes can reach which. This is the right tool when multiple VPCs genuinely need broad network-level reachability to each other — shared services VPCs, hybrid on-prem connectivity, multi-account landing zones.

PrivateLink/PSC service-provider models solve a narrower but more common problem: when the actual requirement is "consumers need to call one service," not "consumers need network reachability to an entire VPC." Publishing that service behind a PrivateLink endpoint service or a PSC service attachment means the provider exposes exactly one endpoint, not a routable CIDR — a consumer VPC gets a private IP that resolves to that service and nothing else. For many-to-one topologies (dozens of consumer teams calling one internal platform API) or many-to-many partner integrations (a SaaS vendor serving many customer VPCs), this scales far better than peering or even Transit Gateway attachments, because the provider never has to reason about what else lives in the consumer's address space, and the consumer never gains reachability beyond the published service.

The mechanism that keeps this auditable on the provider side is consumer allow-listing: AWS PrivateLink endpoint services support explicit principal allow-lists (which AWS accounts/VPCs may create an endpoint against your service), and PSC service attachments support equivalent producer-side accept lists and connection preferences. Both give the service owner a single, reviewable list of who has network access — a much smaller audit surface than reasoning about route table propagation across a peering mesh or Transit Gateway route table.

Auditing and Enforcing the Perimeter Continuously

None of this holds without continuous verification, because network configuration drifts — a new subnet gets created without the endpoint route, a security group gets a temporary 0.0.0.0/0 rule during an incident that never gets reverted, a new NAT gateway inherits the wrong route table.

Flow logs (VPC Flow Logs on AWS, VPC Flow Logs on GCP) are the detection mechanism. Filtering flow log records by NAT gateway ENI or by traffic destined for 0.0.0.0/0 on ports outside your expected allow-list surfaces both drift back to unrestricted egress and unexpected inbound paths that bypassed the endpoint architecture entirely. This is worth wiring into a scheduled query or SIEM rule rather than checking manually — drift detection that requires a human to remember to look is drift detection that doesn't happen.

Policy-as-code enforcement catches the same class of problem earlier, before it merges. A Conftest or OPA policy run against terraform plan JSON output can fail a pull request that introduces a security group egress rule with cidr_blocks = ["0.0.0.0/0"], or a subnet resource with map_public_ip_on_launch = true where the convention says private. This is cheaper than incident response and turns the private-connectivity architecture from a one-time migration into a standing invariant that CI defends. Both the AWS Well-Architected Framework and the Google Cloud Architecture Framework treat this kind of automated guardrail as core to the security pillar rather than an optional hardening step.

Be honest about the tradeoff, though: every interface endpoint or PSC endpoint is a billed, provisioned resource with its own DNS behavior to reason about, and multiplying that across every AWS service and every environment adds real operational surface — endpoint sprawl, DNS resolution edge cases when private and public hosted zones interact, and a non-trivial Terraform module to maintain. It's rarely worth migrating every workload on day one. Scope the initial rollout to subnets handling regulated data, secrets, or anything in a compliance boundary, prove the pattern there, and expand outward once the DNS and policy tooling is battle-tested.

What to Do Next

Start by inventorying what your private subnets actually call today — flow log analysis or a few days of BytesOutToDestination on the NAT gateway will tell you more than any architecture diagram. Convert the top few destinations (S3, Secrets Manager, your container registry) to gateway or interface endpoints first, since those are usually the highest-volume, lowest-risk migrations. Add an endpoint policy to at least one high-sensitivity endpoint (Secrets Manager or KMS) as a proof of concept for the "second enforcement layer beyond IAM" pattern. On GCP, confirm Private Google Access is enabled on every subnet before reaching for PSC endpoints — it's free and covers most of the inbound need. Finally, add one Conftest/OPA check to CI that fails on a new 0.0.0.0/0 egress rule, so the next engineer who reaches for the convenient default gets stopped at plan time instead of at incident response time.
